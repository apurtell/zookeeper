# zk-jute and zk-proto: the sans-IO protocol core

## 0. Summary

This document is the single source of truth for the zk-proto API. Other documents use these names: `Connection`, `Tokens`, `Output`/`poll_output`, `Action`/`poll_action`, `Compat`, `DriverMode`, `Request`/`Op`, `SubmitError`/`Stage`, `TransportFailure`, `TlsConfigStep`, `TlsResourceAt`, `ProbeOutcome`/`ProbeTlsFailure`, `Cause`, `SaslCall`/`SaslStep`, `Endpoint`, `Millis`, `Rng`, `LogFilter`, `DefaultWatcher`, `LogRecord`/`LogSite`, `SecretBytes`.

- **Pull/outbox model.** The core never calls application code. Every user-visible effect leaves as an ordered `Output`, log lines included, so their order relative to callbacks is preserved. Log lines that C prints on the delivering thread just before a callback travel inside that output (`delivery_logs`, §5.1). The caller of each core call pumps that call's outputs before it releases the lock. The C shim runs callbacks only from C frames, after the `zkrs_*` call has returned, on every thread (§5.2).
- **Barrier/resume.** A teardown is a staged continuation. A barrier output suspends the remaining work until the driver calls `resume()`. Barriers are: a `Route::Direct` completion, an `Auth` output that has a continuation, every `AuthLockpoint`, and every `Session` output under `SessionDelivery::Inline` (st). A run of consecutive Direct results that one stage emits with no callback item between them shares one barrier (§5.3). Pending-request rcs are computed after the callback returns, so a close from an st session callback gives ZCLOSING (§5.3, §12).
- **One `Compat` struct, owned here.** Its field names are defined here; the compatibility ledger (07 §2.1) owns its values. Associated consts `Compat::LEGACY_C` and `Compat::NATIVE`. Per-driver settings are in `DriverMode {interest, session_delivery}` only (§14).
- **Deviations.** `Compat::LEGACY_C` is the one value the drop-in uses. It carries the core behavior fixes DV-FIX-1, 2, 3, 4, 7, 8 and 9 (00 §5.1; §14.3 of this document); the shim carries DV-FIX-5 and DV-FIX-6 (05 §13, §18). Every other difference from C removes UB, a crash, corruption or a deadlock-class failure (§16).
- **Session fan-out order** comes from a safe-Rust port of `hashtable.c` (`LegacyWatchTable`). It is bit-identical to C, including C `char` signedness in djb2.
- **TLS.** The core owns the TLS phases, the timers, the rcs and the log lines. The TLS engine is rustls in zk-driver for both profiles (`RustlsConn`; 06 §3). The verifier policy is the `Compat::tls_verify` field (`LegacyChainOnly` under `LEGACY_C`, `WebPki` under `NATIVE`). The core never sees certificates, keys or the passphrase (§4.3).
- **SASL.** The core owns the ZooKeeper-level SASL sequencing and every mechanism quirk (`SaslNegotiation`). In the drop-in, Cyrus is called only by hardened shim C from SASL outbox items, with a 32-bit generation number on every call (§7.4; 06 §4).
- **Auth lock parity.** The core emits an `AuthLockpoint` barrier at each site where legacy takes `zoo_lock_auth` on the IO or closing thread (§5.4).
- **Dependencies.** zk-jute has no third-party dependency; its records are generated by the Java `RustGenerator` (`Rcc -l rust`, 01 §8). zk-proto depends on zk-jute and `zeroize` only. Diagnostics are structured `LogRecord`s. There is no tracing.
- **Clippy.** All code complies with `indexing_slicing`, `arithmetic_side_effects`, `unwrap_used`, `expect_used` and `panic` at `deny`, and with `as_conversions` under `-D warnings` (§17).
- **Milestone.** zk-jute and zk-proto land at M0 (core and native API). The TLS and SASL inputs are exercised by the drop-in at M3.

## 1. Scope, crate boundaries and invariants

| Crate | Owns | Does not own |
|---|---|---|
| `zk-jute` (`apache-zookeeper-jute`) | Generated wire records (§2.1). The bounded `Reader` and the infallible `Writer`. The length-prefix `FrameDecoder`. The fixed-layout handshake codec. `ReplyHeader::peek`. The `MultiHeader` stream codec. Op-code, special-xid and rc constants. | C layouts (zk-ffi and the C shim own those, 05). The generator (zookeeper-jute's `RustGenerator`). |
| `zk-proto` (`apache-zookeeper-proto`) | The session state machine: phase and legacy state, xids, send queue and reply FIFO, reply decoding, the watcher registry (legacy hashtable port and native ordered tables), host list, rebalancing and cursor policy, timers, the TLS phase machine and its rcs, auth list and auth lockpoints, SASL sequencing including the mechanism quirks, SetWatches, read-only probe scheduling, staged teardown, close sequencing, legacy validation order, chroot (both profiles), and the pinned log-site enum. Pure legacy functions: `isValidPath`, `prepend_string`, `sub_string`, `addrvec_eq`, host-string parsing, TTL check. | Sockets, the TLS engine, trust stores, key files (zk-driver `net::tls`), DNS, Cyrus (shim C), clocks, threads, C memory, application callbacks, log formatting. |

**Crate graph** (00 §3 K1; directories under `crates/`):

```
zk-jute ← zk-proto ← zk-driver ← zk-client (native API) ← zk-recipes
                         ↑
                       zk-ffi   (never depends on zk-client)
```

Drivers live in `zk-driver`. CI checks with `cargo tree` that zk-ffi cannot reach zk-client.

**Dependencies.**
- zk-jute has no third-party normal or build dependency. Its `build.rs` is std-only and only checks that the generated file exists (§2.1).
- zk-proto has one: `zeroize` (`default-features = false`, `features = ["alloc"]`, no derive). It holds secrets: the auth list, SASL tokens and sensitive frames. It is in the audited drop-in closure, `cargo-vet safe-to-deploy`.
- Dev-dependencies are limited to `proptest`, `proptest-state-machine` and `arbitrary` (01 §3.3 R2). Tests that need `zk-testkit` (LegacyModel, ServerSim) live in `zk-testkit/tests/`, so zk-testkit is not a dev-dependency of zk-proto.

**Unsafe.** Both crates declare `#![forbid(unsafe_code)]`. The only third-party `unsafe` below zk-ffi on this path is inside `zeroize` (volatile writes and a compiler fence), which is audited and pinned.

Core invariants:

1. **No I/O, threads, clocks, globals or locks.**
   - Time enters as `Millis`.
   - Randomness enters through the injected `Rng`. In the drop-in, the shim implements it with libc `random`/`drand48`, and the `srandom`/`srand48` reseed runs in the driver's unlocked resolve step (§3.3, §9.4). The application-visible PRNG side effects are identical to C.
   - Log-level checks go through the injected `LogFilter`. The shim implements it by reading `logLevel` (Pure leaf `log_enabled`).
   - The default watcher is read through the injected `DefaultWatcher` (Pure leaf `snapshot_default_watcher`).
   - Every injected hook is called under the driver's lock, so its implementation must be Pure: it must not block, and it must not reach application code (00 §3 K4).
   - The core holds no process-global state. C's global xid counter and `addr_rw_server` become per handle (proto P5, proto P13).
2. **The core never calls application code.** All user-visible effects are `Output`s. Mechanism work leaves as `Action::Sasl`. A driver can therefore hold its handle lock around any core call.
3. **Outputs belong to the call that produced them.** After every core call, the caller pops all outputs before it releases the lock (the "pump"). The only exception is a barrier (§5.3).
4. **Total and bounded.** No input causes a panic. Every method runs in time proportional to its input. Arithmetic is checked, saturating, or explicitly wrapping where C wraps (§17).
5. **Linear tokens.** Completion and auth tokens are move-only. A token moves into the core when it is accepted and leaves exactly once: in an `Output`, in `Submitted::Local`, in a `SubmitError`/`AddAuthError`, or through `into_leftovers()`. No core path drops a token on purpose. If a token is dropped anyway (for example a `Connection` dropped without `into_leftovers`), its own `Drop` disposes of it: zk-ffi's `CReq` calls the Pure leaf `discard_token` (a sync record gets ZCLOSING and is signalled; CC-9, 00 §4), and a native slot token drops without a value, so its receiver sees the client's terminal error (04 §5.2).
6. **Single owner.** One `Connection` holds all mutable session state. This removes C's `addrs` use-after-free (SRV-10) and the unlocked watcher and context writes (WAT-15).

## 2. zk-jute

### 2.1 Generated records

The records are generated by the Java `RustGenerator` in `zookeeper-jute` (`org.apache.jute.compiler`, beside `CGenerator`), selected by `Rcc -l rust`. 01 §8 owns the build integration; this section owns the generated types.

- **Execution.** The `generate-Rust-Jute` execution in `zookeeper-jute/pom.xml` runs at `generate-sources`, exactly as `generate-C-Jute` does. It writes `crates/zk-jute/src/generated/` from `zookeeper-jute/src/main/resources/zookeeper.jute`. The output has the `data` and `proto` modules only and no cargo features.
- **Not committed.** The generated directory is git-ignored, as `zookeeper-client-c/generated/` is.
- **Missing-file check.** `zk-jute/build.rs` (std-only, `#![forbid(unsafe_code)]`) generates nothing. It checks that the generated file exists. If the file is missing, the build fails with a message that mirrors configure.ac's jute check (configure.ac:73-74): "jute files are missing! Run `mvn -pl zookeeper-jute generate-sources` from the top level directory."
- **Packaging.** `Cargo.toml` `include = [...]` lists the generated file. The native crates are not published to a registry and are not packaged (`publish = false`); they ship in the ASF source release (01 §10).
- **Drift.** A CI check runs the generator twice and fails if the outputs differ (determinism). The three-way Java/C/Rust codec test over every record checks generator correctness (08 §8.4).

Each record:

```rust
#[derive(Debug, Clone, PartialEq, Eq, Default)]
pub struct GetDataResponse { pub data: JBuffer, pub stat: Stat }
pub trait Record: Sized {
    fn encode(&self, out: &mut Vec<u8>);                       // infallible; allocator failure aborts
    fn decode(r: &mut Reader<'_>) -> Result<Self, DecodeError>;
    fn encoded_len(&self) -> usize;                            // exact size for try_reserve_exact
}
```

| jute | Rust | Wire and decode rules |
|---|---|---|
| int, long | i32, i64 | Big-endian. Needs 4 or 8 bytes, otherwise `Truncated`. |
| boolean | bool | 1 byte. Any non-zero byte decodes as true (recordio.c:226-238). |
| ustring | `JString` (`Null` or `Bytes(Vec<u8>)`) | -1 means `Null`. A length below -1 is `NegativeString`. UTF-8 is not validated. C decodes -1 as -EINVAL (recordio.c:272); no well-formed server sends it for a field the client reads, and `c_rc` is reached only by SASL replies, which carry a buffer. |
| buffer | `JBuffer` (`Null` or `Bytes`) | -1 means `Null`. A length below -1 is `NegativeBuffer`. |
| vector<T> | `JVec<T>` (`Null` or `Items(Vec<T>)`) | -1 means `Null`, which the shim delivers as `data=NULL, count=-1` (DAT-04). A count below -1 is `NegativeCount`. Preallocation is `min(count, remaining/min_elem)`. Element errors propagate. |

Null is preserved everywhere, so no override list of nullable fields is needed. A C caller's NULL `Id.scheme` or NULL reconfig string becomes `JString::Null`, which writes -1 as `oa_serialize_string` does (recordio.c:163-171).

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum DecodeError { Truncated { need: usize, have: usize }, NegativeString(i32), NegativeBuffer(i32), NegativeCount(i32) }
impl DecodeError {
    /// The rc that C ia_deserialize gives for the same input (recordio.c:193-283).
    /// SAS-08: a SASL reply decode error goes back raw from zookeeper_process.
    pub const fn c_rc(self) -> i32 { match self { Self::Truncated{..} => -E2BIG, Self::NegativeString(_) => -EINVAL,
                                                   Self::NegativeBuffer(_) | Self::NegativeCount(_) => -ENOMEM } }
}
```

Decoders never read past their slice and tolerate trailing bytes. Trailing bytes must be tolerated because a `Create2Response` is parsed as a `CreateResponse` for `zoo_acreate` (zookeeper.c:3391-3406). Generated code contains no `unsafe`, no `unwrap` and no indexing; the generator emits code that passes the §17 lints.

### 2.2 Frame codec

```rust
pub enum FrameError { Empty, Negative(i32), TooLarge(u32) }
pub enum Pushed { NeedMore, Frame(Vec<u8>), Error(FrameError) }
impl FrameDecoder {
    pub fn new(max_len: Option<u32>) -> Self;                  // legacy: None (WIRE-01)
    pub fn want(&self) -> usize;                                // bytes left in this frame; 0 while stalled
    pub fn push(&mut self, input: &[u8]) -> (usize, Pushed);   // stops at the end of one frame
    pub fn stall(&mut self); pub fn reset(&mut self);
}
pub fn encode_frame(body: &[u8], out: &mut Vec<u8>);
```

- The body buffer grows as bytes arrive, at most `min(remaining, 64 KiB)` at a time.
- A zero length gives `Empty`. The core tears down with ZCONNECTIONLOSS, which is what C produces (WIRE-03).
- A negative length gives `Negative`. In legacy mode the core stalls the decoder: READ interest is dropped and the 2/3·T receive timeout fires with ZOPERATIONTIMEOUT. That is the same rc and timing as C, without C's busy loop (WIRE-02, proto P19).
- A length above `max_len` gives `TooLarge` (native only; legacy has no cap).
- Under `negative_frame_len = Disconnect` (NATIVE) a negative length tears down with `Cause::ProtocolError`. `TooLarge` also tears down with `Cause::ProtocolError`; under NATIVE pending requests see ZCONNECTIONLOSS (§12.1).
- `want()` lets the st driver read exactly one plaintext frame per `zookeeper_process`, as C does (DSP-17). Under TLS, the st driver repeats the one-frame cycle while its decrypted buffer holds a complete frame (TLS-04, §4.2).

### 2.3 Handshake, constants, multi

- **ConnectRequest** is a fixed 45-byte body (protocolVersion 0, lastZxidSeen, timeOut, sessionId, `passwd` length 16 plus 16 bytes, readOnly), sent in a 49-byte frame. It is byte-identical to zookeeper.c:2362-2386 (WIRE-05).
- **ConnectResponse** is 37 bytes, or 36 bytes from an old server, which means readOnly=0. `passwd_len` and protocolVersion are ignored (zookeeper.c:1968-1988). Any other length tears down with ZCONNECTIONLOSS (proto P6).
- **Constants:**
  - `OpCode` covers every value in proto.h:25-49. It also defines the native-only values 22, 103-107. Legacy compat never emits these (WIRE-12).
  - `xid::{WATCHER_EVENT=-1, PING=-2, AUTH=-4, SET_WATCHES=-8}`.
  - `rc::*` mirrors `ZOO_ERRORS`. Server codes pass through raw (RC-17).
- **Multi request:** `MultiHeader{type, done=0, err=-1}` per op, terminated by `{-1, 1, -1}` (MUL-10).
- **Multi response:** `decode_multi(r, expected, kind) -> Vec<MultiItem>` reads by the wire `MultiHeader.type` (proto P15, MUL-07):
  - -1 is `ErrorResponse`.
  - 1 is a create path (CreateResponse).
  - 15 is path plus Stat (Create2Response); the server reports create2, createTTL and createContainer sub-results as 15 (FinalRequestProcessor.java:244-251).
  - 5 is Stat.
  - 2 and 13 have no body.
  - 4 (getData) and 8 (getChildren) are accepted only when `kind == MultiRead` (native hook A1, §15).

  Any other type (19 and 21 included), a missing `done`, or a count mismatch is a decode error.

## 3. zk-proto core types

### 3.1 Tokens

```rust
pub trait Tokens {
    type Completion;              // async callback or sync waiter; moved in once, out once
    type Watcher: Clone + Eq;     // identity only; == is the dedup relation
    type Auth;                    // zoo_add_auth completion
}
```

| Implementor | Completion | Watcher | Auth |
|---|---|---|---|
| zk-ffi | `CReq(NonZeroUsize)`: a `zks_req*` as an integer. Rust never converts it back. It reaches C once, as a RESULT outbox item; `Drop` calls the Pure leaf `discard_token`. | `CWatcher{fn_: usize, ctx: usize}`: C's `(fn, ctx)` pointer identity (zk_hashtable.c:151-160) | `CReq` |
| zk-client native | `NativeCompletion` (`Reply(Arc<Slot<..>>)` or `Discard`; 04 §5.1) | `WatchId(u64)` | `Arc<Slot<i32>>` |

`Connection<T>` moves, clones (watchers only) and compares tokens. Nothing else is possible. A single trait with associated types gives one bound and one name.

### 3.2 State and phase

```rust
#[repr(i32)] #[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum State { Closed = 0, Connecting = 1, Associating = 2, Connected = 3, ReadOnly = 5,
                 SslConnecting = 7, NotConnected = 999, ExpiredSession = -112, AuthFailed = -113 }
enum Phase { Idle, TcpConnecting, TlsHandshaking { deadline: Millis }, TlsConfigFailed,
             Associating, Sasl(SaslNegotiation), Established }
```

`state()` returns the C-visible value. The internal `Phase` drives the logic. The two differ only where C shows a stale value:

| Situation | `state()` (C value) | Phase | C ref |
|---|---|---|---|
| Initial; after a forced close | 999 | Idle | 1405, 1225, 4153-4160 |
| After a recoverable teardown, including the T/60 delay | 0 | Idle | 2116-2118 |
| EINPROGRESS without TLS | 1 | TcpConnecting | 2704-2705 |
| EINPROGRESS with TLS: TCP phase, then handshake | 7 | TcpConnecting, then TlsHandshaking | 2701-2703, 3079-3094 |
| Immediate connect with TLS, handshake in progress | **unchanged (0 or 999)**. C blocks inline in this state; the core keeps it visible until the handshake completes | TlsHandshaking | 2715-2722 |
| TLS configuration failed (no teardown) | unchanged: 7 on the EINPROGRESS path, 0/999 on the immediate path | TlsConfigFailed | 2717-2720, 3093-3094 |
| ConnectRequest queued, SASL in progress | 2 | Associating / Sasl | 2391, 3181-3193 |
| Session established | 3 or 5 | Established | 2987-2988 |
| Expired | -112 | Idle | 3170 |
| Auth failed (digest or SASL) | -113 | Idle after a digest or SASL teardown; unchanged (Sasl) after `mark_sasl_failed` | 2163; zk_sasl.c:135-141 |

During a teardown's session callback, `state()` still reports the pre-teardown value (3 or 5). C sets state 0 only after `cleanup_bufs` (zookeeper.c:2101-2118), and the staged teardown reproduces that (§12).

### 3.3 Time, randomness, logging, secrets, config, policy

```rust
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
pub struct Millis(pub u64);           // monotonic ms from any origin; tests use integers
                                      // drivers map Instant -> Millis

/// Legacy host-order randomness. Called under the driver lock: must not block.
pub trait Rng: Send {
    fn on_resolution(&mut self);      // reseed point of setup_random() (zookeeper.c:753-782),
                                      // called just before a shuffle
    fn random(&mut self) -> i64;      // libc random(): 0..=2^31-1 (Windows: rand(), 0..=RAND_MAX)
    fn drand48(&mut self) -> f64;     // libc drand48(): [0, 1) (Windows: rand()/RAND_MAX, [0, 1])
}

pub trait LogFilter: Send { fn enabled(&self, level: LogLevel) -> bool; }   // shim: zookeeper_log.h:32-39

/// The default (fn, ctx) pair. zk-ffi reads the C pair cell; native returns None.
pub trait DefaultWatcher<W>: Send { fn snapshot(&self) -> Option<W>; }

/// Secret bytes. Zeroed on drop. Debug shows the length only.
pub struct SecretBytes(zeroize::Zeroizing<Vec<u8>>);
```

**Rng implementations.**
- Drop-in (`ShimRng`): `random` and `drand48` call the Pure leaves `rng_random`/`rng_drand48`. `on_resolution` is empty. The real reseed (`srandom`/`srand48` from `/dev/urandom`, getpid fallback) is the Blocking leaf `rng_reseed`, which the driver calls with no Rust lock held, after the last host's `handle_host_resolved` and before it relocks to call `handle_resolved` (§9.4). It does so only when `shuffle` is true and at least one address resolved. That is C's condition (zookeeper.c:1028-1038), and the libc PRNG calls of that thread keep C's order: reseed, then the shuffle's `random()` calls, then the rebalance `drand48()` calls (SRV-04 RE). On Windows `rng_reseed` does nothing, `rng_random` calls `rand()` and `rng_drand48` returns `(double)rand()/RAND_MAX`, as legacy.
- Test double (`LibcRandomClone`, zk-testkit): reseeds in `on_resolution`.
- Native: per-handle SplitMix64 in zk-client; `on_resolution` is empty.

**Log records.**

```rust
pub struct LogRecord { pub site: LogSite, pub level: LogLevel, pub args: Vec<LogArg> }
pub enum LogArg { I64(i64), U64(u64), Ptr(u64), Str(JString), Endpoint(Option<SocketAddr>),
                  ErrnoStr(i32), GaiStr { gai_rc: i32, errno: i32 } }
```

- `LogSite` is a pinned enum generated from `zookeeper-client-c/abi/log-sites.tsv` into the committed `zk-proto/src/generated/log_sites.rs`, with the matching `shim/zks_log_sites.h`. Both are produced and drift-checked by `cargo xtask gen log-sites`. The table itself is pinned to the final legacy C-core commit on main before the Rust core becomes the default: `cargo xtask log-sites` extracts `abi/log-sites.tsv` from the C core at that commit and re-extracts it whenever the pin moves (05 §16.2).
- The core emits a record only if `LogFilter::enabled(level)`. It stamps no time: zk-ffi stamps the wall-clock time when it pumps each `Log` into the outbox, so zk-proto stays clock-free. C re-checks `logLevel` when it emits the line. For a record carried in `delivery_logs` (§5.1), zk-ffi stamps the time when it pumps the carrying output; C re-checks `logLevel` when the delivering thread emits it.
- `Str(JString::Null)` renders as `(null)` (shim log hardening, LOG-09/10). `GaiStr` renders `gai_strerror(gai_rc)` or `strerror(errno)` per platform, as zookeeper.c:982-988 does. `Endpoint` renders through the shim's per-thread ENDPOINT buffer (DAT-15).

**Config and DriverMode.**

```rust
pub struct Config {
    pub timeout_ms: i32,               // not validated (INIT-08)
    pub client_id: ClientId,           // {session_id: i64, passwd: [u8;16]}; non-zero id sets seen_rw_before

                                       // native: from dns_refresh, -1 by default (§3.3, §9.4)
    pub xid_seed: i32,                 // shim: (int32_t)time(0); native: 1
    pub c_char_signed: bool,           // shim: CHAR_MIN < 0, passed in zkrs_init_args.c_char_signed (05 §6).

    pub connect_timeout_ms: Option<u32>, // native hook A12 (§15); bound of the TCP-connect phase (§9.1);
                                       // legacy always None; native: connect_timeout, default T/3 (04 §3)

                                       // Backoff::Deadline (§7.2); legacy 0 (unused); native: reconnect_delay, default 1000
    pub reconnect_jitter_pct: u8,      // native hook A13; ± percent of reconnect_delay_ms; legacy 0; native 25
    pub close_timeout_ms: u32,         // native hook A15 (§15); Drain close deadline (§13); legacy 0 (unused:

}
```

**Native builder mapping.** zk-client contains no protocol logic (04 §19.1), so every native knob of 04 §3 and §16.1 that changes protocol behavior is a zk-proto input. `dispatch_queue_capacity` and `persistent_watch_buffer` are zk-driver and zk-client settings (03 §7, 04 §9.2), and `resolver`, `runtime`, `update_servers_from_config`, `metrics` and `name` are zk-client settings; none of them is a zk-proto input. zk-client fills `Config` and the NATIVE `Compat` fields from the builder as follows (04 §19.1, §19.2):

| Builder knob (04 §3, §16.1) | zk-proto input | Default |
|---|---|---|
| `Client::builder(connect_string)` | `Config.hosts`, and `Config.chroot` from the suffix, through `native::parse_connect_string` | required |
| `session_timeout(t)` | `Config.timeout_ms = t` (whole ms, saturating at `i32::MAX`) | 30 000 ms |
| `allow_read_only(b)` | `Config.allow_read_only = b` | false |
| `session(id, pw)` | `Config.client_id = {id, pw}` | session id 0, zero password (a new session) |
| `chroot(p)`, or the connect-string suffix | `Config.chroot = Some(p)` (`chroot(p)` overrides the suffix) | `None` |
| `tls(opts)` | `Config.tls = true` | false |
| `sasl(cfg)` | `Config.sasl = true` | false |
| `auth(s, d)` | one `Connection::add_auth` call per credential, in builder order, after `Connection::new` | none |

The defaults and their reasons are in 04 §3, §14 and §16.1. zk-ffi always passes (05 §15.1) the legacy values of the four native-only timing fields (`connect_timeout_ms = None`, and 0 for `reconnect_delay_ms`, `reconnect_jitter_pct` and `close_timeout_ms`), `max_pending = None` and `restore_watches = true`, keeps `resolve_cadence = EveryIterationWhileDisconnected` and `resolve_delay_ms` as C sets it, so `LEGACY_C` behavior does not depend on these knobs.

`DriverMode` has these two fields only (CC-16, 00 §4). The native dispatch choice `DispatchMode {Thread, IoThread}` is a zk-driver type.

Time arithmetic uses i64 milliseconds through helpers in `zk_proto::time`:
- `elapsed(now, then)` saturates at 0.
- `two_thirds(t)` and `third(t)` use C's truncating division, computed in i64 so that C's `int` overflow cannot occur.

**Driver requirements.** The core meets the driver requirements DR1-DR5 of 03 §2:
- DR1: `Output::AuthLockpoint` at the four legacy `zoo_lock_auth` sites (§5.4).
- DR2: `SaslCall` carries the generation; at most one Start/Step is outstanding; `Dispose` of the previous mechanism session is yielded immediately before the next `Start`, and by `destroy` after `CloseTransport`; a teardown or forced close yields no `Dispose`; a stale `gen` is ignored (§7.4).

- DR5: the core emits one line per failed host entry, at the platform's legacy site: ERROR `getaddrinfo: %s`, or `Win32 message: %s` on Windows (zookeeper.c:982-988), in host order, when that host's `HostResolution` is passed in (§9.4).

### 4.1 The interest iteration in C order

`poll_action()` yields at most these actions, in this order, which follows zookeeper.c:2618-2824:

1. **`Resolve{gen, hosts, initial}`** when resolution is due (§9.4).
   - Under `dns_failure = LegacyRcPreserved`, with **no transport**, a whole-list failure ends the iteration's action list. `finish_interest` returns `rc = resolver rc` with outputs unwritten.
   - Under `dns_failure = LegacyRcPreserved`, with **a transport open** (proto P10, SRV-06 FU), the failure counts as "no change". The timer step (4) still runs and the outputs are written. The rc is the resolver rc unless a teardown occurs in the call, whose rc wins (CC-22, 00 §4).
   - Under `UseLastGood` a failed resolution changes nothing: the action list continues with the connect decision and the outputs are written.
2. **Connect decision**, when no transport exists:
   - `Connect{endpoint, tls}`, where `tls = cfg.tls.then_some(compat.tls_verify)`; or
   - nothing (backoff, or, under `dns_failure = LegacyRcPreserved`, `BlockConnect` after a resolve failure).

   The empty-list attempt fails pending work with ZSYSTEMERROR (SRV-08). If `socket()` or `connect()` fails, the driver calls `handle_transport_failed(SocketCreate | TcpRefused)`.
3. **`Sasl(SaslCall)`** when the SASL negotiation needs mechanism work.
4. **Timers** run inside the core, with no action: receive deadline, TCP-connect bound (native, §9.1), TLS handshake deadline, ping, RO probe timer. A teardown here yields `CloseTransport`. An RO probe yields `ProbeRw{endpoint, tls}`.
5. **`CloseTransport`** whenever the core has decided the socket must be closed: teardown or forced close. It is always yielded before any later `Connect`. A teardown or forced close yields no `Sasl(Dispose)`: the mechanism session stays until the next `Start` or `destroy` (§7.4), as legacy `cleanup` and the forced-close paths call only `close_zsock` (zookeeper.c:2103, 1222-1226, 4155-4158).

`poll_action()` is also called after other inputs. It then yields only the actions that those inputs produced: `Sasl` after `handle_read` or `handle_sasl_*` (after a prime response, `Sasl(Dispose)` of the previous session, if one exists, and then `Sasl(Start)`); `CloseTransport` after a teardown or a forced close; `CloseTransport` and then `Sasl(Dispose)` after `destroy`.

```rust
pub enum Action { Resolve { gen: u64, hosts: Vec<HostSpec>, initial: bool },

                  CloseTransport, ProbeRw { endpoint: Endpoint, tls: Option<TlsVerify> }, Sasl(SaslCall) }

pub struct InterestOutcome { pub rc: i32, pub outputs: Option<Interest> }
pub struct Interest { pub has_socket: bool, pub read: bool, pub write: bool, pub timeout_ms: u32 }
```

**`InterestOutcome.outputs` is `None` exactly where C returns before writing `*fd/*interest/*tv`:**
- unrecoverable state (zookeeper.c:2633-2634), via `begin_interest`;
- whole-list resolution failure with no transport, under `dns_failure = LegacyRcPreserved` (2645-2648).

The st shim leaves the caller's variables untouched in those cases (SRV-14 RE). The mt driver never exposes these values and waits T/60 on the waker itself (DRV-15).

When the outputs are written:
- **No transport:** `read = write = false`. `timeout_ms` is T/60 after a backoff `Wait` under `OneShotSkip`, `not_before - now` while a `Deadline` pause runs (§7.2), otherwise 0. These are the values C computes. They cover the paths where C writes `fd=-1, interest=0, tv=0` before it returns early: `socket()` failure, `connect()` failure, and a TLS configuration failure on the immediate path (`rc = ZSSLCONNECTIONERROR`; 2650-2653, 2717-2720).
- **Transport present:** `read = true`. `write` follows `DriverMode::interest`:
  - **LegacyExact (st):** `(!tx.is_empty() && (connected || sasl_in_progress)) || phase == TcpConnecting || connect_frame_unwritten` (2817-2821; SAS-07). In TlsHandshaking the core reports `write = false`, and the driver ORs in the TLS engine's wants. In TlsConfigFailed `write` is false (ST-17: no spin).
  - **Precise (mt, native):** `write` is true only if `poll_transmit` would return bytes.
- **`timeout_ms`** = `max(0, min(recv_to, send_to, rw_left, tls_left, connect_left))`, as C computes `get_timeval(min(recv_to, send_to))` (2806; `get_timeval` clamps negatives to 0, 2422-2431):
  - `recv_to = T*2/3 - idle_recv`;
  - `send_to` is T/3, or `T/3 - idle_send` while connected (reset to T/3 when ≤ 0);
  - `rw_left` applies only in ReadOnly;
  - `tls_left` applies only in TlsHandshaking.
  - `connect_left = connect_timeout_ms - elapsed(now, connect_started_at)` applies only in TcpConnecting and only when `connect_timeout_ms` is `Some` (native, §9.1).
  - When `connect_timeout_ms` is `Some`, in phase TcpConnecting (state 1 or 7) `recv_to` is left out: `timeout_ms = max(0, min(send_to, connect_left))`. The state 7 rule below applies only when `connect_timeout_ms` is `None`.
  - **TCP-connect phase of state 7:** the receive timeout is exempt, as in C (2749). In state 7, when `recv_to <= 0`, `tv = T/3`; otherwise `tv = min(recv_to, T/3)`, as in C (ST-16a; proto P9). `send_to` is T/3 in this phase, so `min(recv_to, T/3)` is C's `min(recv_to, send_to)`: T/3 for the first T/3 of elapsed time, then falling to `recv_to`. Where C reaches `tv = 0` and spins, the core reports T/3.
  - The driver forces `timeout_ms = 0` while its TLS engine holds a complete, unprocessed plaintext frame (TLS-04, DRV-11).
- **Socket closed during this call** (timeout, RW switch): `has_socket = false`, so the shim writes `fd = -1` instead of C's stale fd (SRV-13, proto P23). A forced close found in this call comes before C writes `*fd` (2645, 2650), so no stale fd exists on that path, and the connect decision runs in the same call.

`next_deadline` is recorded from these values for the next WARN check.

### 4.2 Other input rules

- **An immediate connect never exposes state 1.** Without TLS, the driver calls `handle_connect_started(Immediate)`, `handle_tcp_connected` and `handle_transport_ready` under one lock hold. With TLS, it calls `handle_connect_started(Immediate)`, then `TlsConnector::new_conn` with no lock held, then `handle_tcp_connected` on success or `handle_transport_failed` on failure (§4.3). The visible state stays 0 or 999 throughout.
- **`handle_read` processes complete frames in order.** It stops when:
  - a barrier is pending;
  - the phase is waiting on mechanism work (an `Action::Sasl` is outstanding);
  - the decoder stalls.

  Leftover bytes stay in the decoder. While no transport exists, `handle_read` returns `rc = ZINVALIDSTATE` and consumes nothing. That is C's `sock == -1` code (3075-3076), and it protects against reads from a socket that a forced close has condemned.
- **TLS reads (TLS-04, FU).** Under TLS the driver feeds decrypted plaintext only. The st driver feeds `want()` bytes at a time and drains after each frame, so each frame is followed by its drain as in C; it repeats while a complete plaintext frame is buffered. One st `zookeeper_process` call may therefore dispatch more than one frame under TLS (00 §5.2).
- **`ReadOutcome.rc`** has the following meanings:

  | rc | Meaning |
  |---|---|
  | ZOK | at least one frame was processed |
  | ZNOTHING | partial frame |
  | the teardown rc | a frame or error caused a teardown |
  | ZAUTHFAILED | digest auth failure |
  | ZINVALIDSTATE | a reply arrived after `begin_close` (3604-3610), other than a FIFO match or the CLOSE_OP reply under `Drain` (§7.1, §13) |
  | the SASL rc | SASL failure (§7.4) |

- **`poll_transmit` pins every frame it copies.**
  - A priority insert never lands before a pinned frame. This fixes the mt race in which the IO thread is mid-send without the lock.
  - `handle_transmitted(n)` advances frames. A frame completes only when its last byte is acknowledged; then `last_send = now` (5214-5220).
  - When the transport is lost, all pins are cleared and a late `handle_transmitted` for that transport is ignored, so it cannot advance a frame queued afterwards. T3 (§12.1) then fails the requests of every frame queued for that transport, so none of them is resumed or replayed on a later connection.
  - The core keeps ownership of every unsent byte until T3 drops it.
  - The driver's transmit copy buffer is a `Zeroizing<Vec<u8>>`, because it can hold sensitive frames (§6.3).

### 4.3 TLS inputs

The TLS engine is zk-driver's `RustlsConn` (`zk-driver/src/net/tls/`, module names per 06 §3.1, cargo feature `tls`, which zk-ffi enables) behind the `TlsConn`/`TlsConnector` driver contract (03 §8.2.1, 06 §3.2). It is built per attempt and per probe. In the drop-in, certificate files are re-read each time (TLS-02); natively, `ReloadPolicy` decides (04 §16.1). The core sees only the phase events below and never sees certificates, keys or the passphrase.

**Driver order on TCP-connect completion** (EINPROGRESS: WRITE event with `SO_ERROR == 0`; immediate: right after `connect`; 03 §4.3.1). The driver takes `now` and calls `TlsConnector::new_conn(&self, &Unlocked, purpose, &Endpoint)` with no lock held. It then takes the lock and acts on the result:
- on success it calls `handle_tcp_connected(now)`, which starts the handshake phase with its deadline from TCP-connect completion, and sends the first flight;
- on a configuration failure it calls `handle_transport_failed(TlsConfig{step, file})`;
- on a resource failure it calls `handle_transport_failed(TlsResource{at, errno})`.

`new_conn` comes first because it does the work of C's `SSL_CTX_new`, the trust and identity loads and `SSL_new` (zookeeper.c:2865-2928), which C also runs before the handshake starts. In the drop-in, LOG items still pending when the IO step reaches these file reads are delivered first (§9.4). The core therefore hears of TCP completion through `handle_tcp_connected` only when a TLS session exists.

**Data phase.** `TlsConn::read_plaintext` returns the plaintext already decrypted first and then returns the latched failure on the next call (03 §8.2.1). Every frame that arrived before a TLS error or EOF is therefore processed before the teardown.

**Verifier policy (`Compat::tls_verify`).** The core passes the policy in `Action::Connect` and `Action::ProbeRw`. The driver builds the verifier from it (rules owned by 06 §3.4-§3.5; summary in 00 §2.5.2):

| Value | Profile | Behavior |
|---|---|---|
| `LegacyChainOnly` | `LEGACY_C` | Reproduces the OpenSSL trust decision of zookeeper.c:2876-2890 (`SSL_VERIFY_PEER \| FAIL_IF_NO_PEER_CERT`, CA file plus default verify paths, no name check, no SNI, no `X509_V_FLAG_PARTIAL_CHAIN`). The rules are exactly 06 §3.5. (a) A v3 leaf chains to a trust anchor through webpki's `verify_server_cert_signed_by_trust_anchor`, followed by the keyCertSign post-check, the rejected-issuer post-check and the OpenSSL path post-check of 06 §3.5 (the last runs the issuer selection and finish rules of 06 §3.14.3 over the leaf, the sent certificates and the trust set, with the leaf's own purpose and subjectAltName); the leaf is accepted only when webpki and all three post-checks accept. A v1 leaf, at any depth below a valid chain, goes through zk-driver's in-tree v1-leaf verifier (`forbid(unsafe_code)`): it checks the leaf signature against its issuer with the provider's `SignatureVerificationAlgorithm`, then verifies the issuer chain to an anchor by OpenSSL's rules. v1 intermediates are rejected, as OpenSSL rejects them, and v1 self-signed anchors are accepted (06 §3.14). (b) A leaf byte-identical to a trust-set certificate is accepted **only when that certificate is OpenSSL-self-signed** (`EXFLAG_SS`, defined in 06 §3.4) and not a rejected input. The leaf must also pass the mimic rule, be time-valid, pass the `ssl_server` purpose check, which an aux trust list naming serverAuth or anyExtendedKeyUsage satisfies, as in 06 §3.14.3 Purpose, and have no critical extension outside the processed set of 06 §3.14.3 (error 34; aux trust does not override it). A `CA:TRUE` self-signed leaf is included. A non-self-signed leaf placed in the CA file gets no special treatment under rule (b): it goes through rule (a), as in OpenSSL (06 §3.5). (c) No SNI (`enable_sni = false`). The peer name given to rustls is `ServerName::IpAddress` of `endpoint.addr`, and there is no hostname check: `verify_server_name` is never called. (d) As specified in 06 §3.5: only OpenSSL-self-signed, CA-capable, purpose-compatible trust inputs valid at now become anchors, plus `TRUSTED CERTIFICATE` inputs whose aux trust list names serverAuth or anyExtendedKeyUsage (explicit trust, 06 §3.4). A `TRUSTED CERTIFICATE` input whose reject list names serverAuth or anyExtendedKeyUsage, or whose non-empty trust list names neither, is a rejected issuer: it is never an anchor, a bridge or a rule-(b) match; it stays an issuer candidate, and the chain fails (error 28) when OpenSSL's chain building would select it (06 §3.4; on the v3 path the rejected-issuer post-check of 06 §3.5). Trust inputs that are neither self-signed nor explicitly trusted are bridges, offered only as intermediates, so a chain must end at an anchor, as OpenSSL requires; a self-signed input that is not an anchor can be accepted only through path (b); in issuer selection (06 §3.14.3) it stays a trusted candidate, and a chain that selects it fails, as in OpenSSL (06 §3.4). Handshake signatures use the provider's `signature_verification_algorithms`. The reference OpenSSL lines are 3.0 and 3.5 LTS. |
| `WebPki` | `NATIVE` | Checks the name against `endpoint.host` (the connect-string host token; IP-literal tokens against IP SANs) and sends SNI for DNS names only (06 §3.12). |

Trust inputs, client-identity loading and the accepted key formats are specified in 06 §3.4 and §3.6. Drop-in and native share one loader, `trust.rs`:
- **CA file:** PEM blocks labeled `CERTIFICATE`, `X509 CERTIFICATE` and `TRUSTED CERTIFICATE`. `TRUSTED CERTIFICATE` aux data is honored by the OpenSSL rules. The `CaFile` step succeeds when the file yields at least one certificate or at least one CRL, as OpenSSL `X509_load_cert_crl_file` does. CRLs are parsed and counted but not used, because legacy sets no CRL-check flags. The step logs "Failed to load CA file %s" and fails when the file cannot be read, when a PEM block is malformed (06 §3.4), when `ca` is NULL, or when it yields neither a certificate nor a CRL.
- **`SSL_CERT_DIR` and the default directory:** OpenSSL hash-name lookup (`<hash>.<n>`, subject-name hash, the `by_dir` rule). Other files are ignored. OpenSSL 3.0 also consults a default `X509_LOOKUP_store` over the same directory value when it is a single path and the `by_dir` pass finds no certificate with the wanted subject; that lookup reads `<hash>.<digits>` names with the hex part compared case-insensitively and no stop at a suffix gap. OpenSSL 3.5 adds no default store location. The loader applies the `by_dir` rule alone; where OpenSSL 3.0 accepts through the store lookup, or where OpenSSL 3.0 or 3.5 keeps a certificate that comes before a corrupt block in a hash-named file, or a certificate in a hash-named file of another subject, the stricter verdict is DV-TLS-3 (06 §3.4).
- **Default paths:** `SSL_CERT_FILE` and `SSL_CERT_DIR` are honored only when `tls_env_allowed` is set. The shim sets that field to false in set-uid and set-gid processes (`getauxval(AT_SECURE)` on Linux, `issetugid()` on BSD and macOS). zk-client computes it with rustix as `getuid() == geteuid() && getgid() == getegid()` on Unix, and sets it on Windows. Otherwise the loader uses the compile-time `ZK_TLS_DEFAULT_CERT_FILE` and `ZK_TLS_DEFAULT_CERT_DIR`. configure and CMake set them from `--with-rust-tls-default-paths`, which defaults to the OPENSSLDIR that `openssl version -d` prints for the OpenSSL installation the legacy probe selected (`$with_openssl/bin/openssl` for `--with-openssl=DIR`, `OPENSSL_ROOT_DIR/bin` in CMake, otherwise the first `openssl` on `PATH`), else to the first existing entry of the platform list of 01 §6.1. A native cargo build with the variables unset applies the same list on the build host in zk-driver's build.rs (06 §3.4). Nothing is probed at run time, and `openssl_probe::probe()` is never called.
- **Client identity:** loaded only when cert, key and passwd are all non-NULL. Accepted keys are unencrypted PKCS#8, PKCS#1 RSA and SEC1 EC; encrypted PKCS#8 with PBES2 (PBKDF2 with HMAC-SHA1, -SHA224, -SHA256, -SHA384 or -SHA512, or scrypt, with AES-128/192/256-CBC and DES-EDE3-CBC); and traditional PEM encryption (`Proc-Type: 4,ENCRYPTED`, `DEK-Info`, EVP_BytesToKey MD5, AES-*-CBC, DES-EDE3-CBC, DES-CBC). scrypt parameters whose memory need is over 32 MiB are rejected before allocation, as OpenSSL's default `EVP_PBE_scrypt` maxmem does. PKCS#12 PBE and ciphers or PRFs outside these sets are rejected (DV-TLS-5); PBES1 fails in both cores under the reference default providers. The `aws-lc-rs-fips` provider build accepts only unencrypted keys and PBES2 with PBKDF2-HMAC-SHA256/384/512 and AES-CBC, and rejects the MD5- and DES-based formats, PBKDF2-HMAC-SHA1/-SHA224 and scrypt (DV-TLS-6, 06 §3.15.3). A key/cert mismatch of the same key type fails at the `ClientKey` step, as `SSL_CTX_use_PrivateKey_file` does. The `CheckPrivateKey` step keeps the SPKI comparison for any remaining case.

The visible deviations of the rustls engine are DV-TLS-1..5 (06 §3.13: protocol floor, policy source, algorithm and certificate acceptance, linkage, key formats), and DV-TLS-6 (key formats of the FIPS build) in the `aws-lc-rs-fips` provider build. None of them is a core behavior.

### 5.1 Outputs

**Paths are stripped where they are decoded.** All paths in outputs are already chroot-stripped by the core, where they are decoded, for both profiles (CC-21, 00 §4). Legacy uses the `sub_string` rules; a mismatch keeps the raw path (PTH-03). zk-client does not strip again.

Under `ChrootPolicy::Component` (NATIVE) the core joins the chroot component-wise on submit (the root path maps to the chroot itself; `GetEphemerals` sends `chroot + prefix`) and strips it only on a component boundary where the path is decoded. A reply path outside the chroot emits an ERROR `Log` and fails the request with ZMARSHALLINGERROR. A watch event outside the chroot is dropped with the same log, except an event whose path is exactly `/zookeeper/config`, which is matched against its absolute key and delivered unstripped. The `Reply::Ephemerals` decoder keeps only entries inside the chroot on a component boundary, strips them, and drops the others without a log. `GetConfig` carries no chroot in either profile.

**`delivery_logs` (07 P8, PTH-03).** Legacy runs `sub_string` and some DEBUG lines at delivery, not at receipt: on the mt dispatch thread, or inline in st, right before the callbacks (zookeeper.c:3468-3487, 3391-3420; zk_hashtable.c:283-294, 329-335). So the log lines that C prints at that point travel inside the output and are emitted on the delivering thread, in C order, immediately before its callbacks. This keeps the thread id in the mt log prefix and the order relative to callbacks:
- **Watch:** first DEBUG "Calling a watcher for node [%s], type = %d event=%s" (3476-3478), then, if the strip found a mismatch, ERROR "server path %s does not include chroot path %s" (1733-1734). Under `LEGACY_C` the core emits a `Watch` output for every node event, even when the collected list is empty (WAT-07: these are the delivery-thread lines for an empty watcher list), because C queues every event and calls `do_foreach_watcher` (and so `sub_string`) on an empty list (zookeeper.c:3561-3580; zk_hashtable.c:286-293, 296-327). The shim then delivers nothing and only logs. `NATIVE` emits a `Watch` only when the list is non-empty.
- **Session:** the same DEBUG "Calling a watcher for node []" line, because a session event is processed by the same code (queue_session_event uses the watcher xid, 3229-3246). The path is not stripped.
- **Completion:** first the DEBUG line that legacy prints when it runs the completion, then, for STRING and STRING_STAT kinds (create and sync replies, multi create sub-results included), the strip mismatch ERROR. For a `Route::Queued` completion that legacy runs through `deserialize_response`, the first line is "Calling COMPLETION_<KIND> for xid=%#x failed=%d rc=%d" (3343-3441; the STRING and STRING_STAT texts are "failed=%d, rc=%d"), with the request's xid and legacy's `hdr.err != 0` and `hdr.err` from the reply header or the faked teardown header (3482, 2046-2048). A MULTI completion carries "Calling COMPLETION_MULTI" (`failed=0 rc=0` for a decoded reply) and then, per sub-op in order, the line of the sub-op's kind (STRING for creates, STAT for setData, VOID for delete and check) with the multi's xid, failed = the sub-result is an error result and rc = its err (for a failed multi, 1 and the multi's rc for every sub-op), each followed by that sub-op's strip ERROR (3298-3336, 3440-3449). For a `Route::Direct` completion the delivering thread is the IO thread, which is where C's `process_sync_completion` logs and strips (5425-5426, 5478-5506): the first line is "Processing sync_completion with type=%d xid=%#x rc=%d", for MULTI followed by the same per-sub-op lines (5530). Auth completions, the local remove-watches completion and the teardown of a sync waiter carry no line (2032-2038, 5021-5029). The shim formats no delivery line itself; it emits these records before the callback, as C does.

Records in `delivery_logs` obey `LogFilter::enabled` at production. C re-checks `logLevel` at emission.

### 5.2 Routing: who runs application code

Rust never calls an application function pointer. The thread that made the core call pumps its outputs into an ordered per-call **outbox**. The C shim drains the outbox and runs callbacks from C frames, after every Rust lock is released. The mt IO and dispatch loops are C loops over Rust step functions (`zkrs_io_step`, `zkrs_wait_dispatch`), so this holds on every thread (00 §3 K2; CC-1, 00 §4).

| Output | mt | st (inside interest/process/close) | native |
|---|---|---|---|
| Completion Queued, Watch, Session | dispatch FIFO. The C dispatch loop gets batches with `zkrs_wait_dispatch` and runs them in C | local FIFO, drained at a Session barrier, at DrainPoint and at the end of the call | slots, per-watcher queues and the session state, routed by the IO side (04 §4) |
| Completion Direct | RESULT barrier item in the producing thread's outbox. zk-ffi's audited raw writers (`abi::raw`) build the legacy result layout in the heap `zks_sync` record and C signals the waiter; after it wakes, the waiting thread does the sync copy-out into the caller's buffers through the raw writers (05 §13). There is no slot (CC-18, 00 §4; 05) | never occurs (st has no sync API) | never occurs: zk-client always submits `Route::Queued`; the blocking facade waits on the request's `Slot` (04 §5.2, §15) |
| Auth, AuthLockpoint, Log | outbox of the calling thread. The C IO loop drains the IO thread's outbox; app threads drain theirs after `zkrs_*` returns | outbox | futures / tracing; AuthLockpoint is never emitted |
| ClientId | Pure leaf `store_client_id`, under the lock | same | ignored; zk-client reads `Connection::client_id()` under the core lock (04 §4) |
| DrainPoint | ignored | drain the FIFO now | ignored |

zk-ffi maps outputs to the private outbox item kinds (CC-2, 00 §4): `Log` → LOG; `Completion` and each `Auth` token → RESULT (async, sync and auth told apart by the `zks_req` mode); `Watch` and `Session` → WATCH; `AuthLockpoint` → AUTH_LOCKPOINT; `Action::Sasl` → SASL{START, STEP, DISPOSE}. The `delivery_logs` of a Completion, Watch or Session travel inside its RESULT or WATCH item, and C emits them before it invokes the callbacks.

Consequences:
- A C++ exception thrown from any callback, or a `longjmp` out of it, passes through C frames only, as in legacy (DSP-14 RE).
- Logs produced inside `zoo_a*` on an app thread, such as the DEBUG "Sending request xid=..." line (4202-4203), are emitted on that thread after the call returns. The order and the thread are the same as in C.

### 5.3 Barrier/resume

- Popping a barrier output suspends the continuation that produced it. Barriers: `Completion{route: Direct}`, `Auth{barrier: true}`, `AuthLockpoint`, `Session{barrier: true}`. While a continuation is suspended:
  - `poll_output` returns only outputs produced by other calls made since the suspension (each of those callers drains its own);
  - `handle_read`, `poll_action` and `handle_transmitted` must not be called (`is_suspended()`);
  - API calls (`submit`, `add_auth`, `begin_close`, ...) stay legal.
- **Direct runs share one barrier.** When one stage fails FIFO entries (T3 in §12.1, `begin_close` and `destroy` in §13), a run of consecutive `Completion{route: Direct}` outputs with no callback item between them is one barrier. The stage keeps producing while the next output is a Direct completion, or a Queued completion (in mt a FIFO publish entry, which runs no application code on the draining thread). It suspends after the last Direct completion of the run. The drain signals the run's waiters in output order, and the driver calls `resume` once for the run. The order is unchanged, because nothing observable runs between them; C's `free_completions` also signals the sync waiters one after another in FIFO order, with no callback between them (zookeeper.c:2028-2059). Any other output ends the run. A run never spans input processing: `handle_read` stops after each Direct reply (§7.1, step 5). st has no Direct entries, so st is unchanged.
- The delivering thread calls `resume(now)` after the item is handled. The continuation then runs with the state those calls left behind:
  - requests submitted from a session callback before T3 are failed by the remaining teardown, as C's `cleanup_bufs` would fail them, except under a forced close, whose T3 fails only the trigger's snapshot (§12.3);
  - a `begin_close` from the callback has already failed the FIFO with ZCLOSING, so nothing is left for ZCONNECTIONLOSS.
- A driver may also stop after a non-barrier output. `resume()` with nothing suspended is a no-op, and so is resuming after `destroy`.
- If C unwinds out of its drain (an exception from a callback), it requeues the untaken items (`zkrs_outbox_requeue`). The suspension persists. The next driving call on the handle delivers those items first and then resumes (CC-32, 00 §4).

### 5.4 Auth lockpoints (zoo_lock_auth parity)

Legacy takes `zoo_lock_auth` on the IO and closing threads at four sites. Under `auth_completion == LegacyBroadcast` (always true under `LEGACY_C`, never under `NATIVE`), the core emits an `AuthLockpoint` barrier at each site, before the state change or collection that the lock protects in C. C does `lock; unlock` on `zh->auth_lock` with no Rust frame and no Rust lock, then resumes. The mutex is initialized exactly as legacy initializes its auth lock: `pthread_mutex_init(&zh->auth_lock, 0)` (default attributes; legacy `pthread_mutex_init(&zh->auth_h.lock, 0)`, mt_adaptor.c:253). An application that holds the lock therefore stalls IO-side auth processing, as in legacy (LA-01 parity, CC-7, 00 §4). In st, `zoo_lock_auth` is a no-op and so is the item.

| Site | Lockpoint position | C ref |
|---|---|---|
| AUTH reply | before the state change and token collection (§8) | 2160-2170 |
| Teardown collection | after the FIFO failures, before the auth tokens are collected (§12.1 T3); a forced close took its tokens at the trigger and emits the lockpoint at T3, before those tokens (§12.3) | 2062-2066 |
| Close collection (`begin_close`, `destroy`) | before the auth tokens are collected (§13) | 2062-2066 via 4016, 676-713 |
| Auth resend | in finalize, before the auth packets are queued (§7.5) | 2216-2226 |

`zoo_add_auth` holds the lock in C around `zkrs_add_auth` (lock order auth → core). Rust never takes the auth lock.

- a native-only op with `native_ops == false` fails with `Stage::NotEnabled`, code ZUNIMPLEMENTED (hook A9);
- multi (row 4) accepts the sub-op types {1, 15, 19, 21, 2, 5, 13} when `native_ops` is true; any other type returns ZUNIMPLEMENTED, as in row 4 (hook A9);
- when `Config.max_pending` is `Some(n)`, a submit beyond `n` fails with `Stage::TooManyPending`, code ZTHROTTLEDOP (hook A8; zk-client maps it to `Error::TooManyPendingRequests`). With `None`, the native default, there is no limit and `TooManyPending` never occurs;
- the native API maps codes to its `Error`.

Shape is chosen from the op:
- Exists → Stat; Create → Path or PathStat.
- Sync → Path; GetConfig and Reconfig → Data.
- SetAcl, Delete and remove-watches → Void.
- Native: GetEphemerals → Ephemerals, GetAllChildrenNumber → ChildrenCount, WhoAmI → WhoAmI, MultiRead → MultiRead (hook A1).

This reproduces WIRE-08 and PTH-07.

### 6.2 xids

Each `Connection` has its own counter, seeded from `cfg.xid_seed` (1 if ≤ 0). It increments by 1 and wraps from `i32::MAX` to **1**, so it never produces 0 or the reserved -1/-2/-4/-8. User requests, SASL requests and CLOSE_OP all draw from it (WIRE-11). xids are drawn inside `submit` under the driver lock, so wire order is xid order (00 §3 K8, K21).

The per-handle counter takes the place of C's process-global counter (WIRE-10, proto P5). Xid values are visible only on the wire and in DEBUG logs (07 P6), and the shim seeds with `time(0)`, so log magnitudes match. A failed submit draws no xid; C draws one before validating, which is also 07 P6.

### 6.3 Send queue and FIFO

```rust
struct OutFrame { bytes: FrameBuf, written: usize, pinned: bool, kind: FrameKind, sensitive: bool }
enum FrameKind { Connect, Request { xid: i32 }, Ping, Auth, SetWatches, Sasl, Close }
tx: VecDeque<OutFrame>;  fifo: VecDeque<Pending<T>>;   // Pending { xid, shape, route, token, watch, unwatch, written: bool }
```

- **`submit` is atomic.** It allocates the xid, encodes the frame, appends it to the back of `tx`, and appends to the back of `fifo` (4193-4197).
- **Priority inserts** (Auth, SetWatches, Sasl, Connect) go before the first frame that is neither started nor pinned. Successive inserts at that boundary come out in reverse call order, which reproduces auth_n..auth_1 followed by SetWatches (AUT-01); under `auth_resend = Forward` the core inserts the entries last to first (§7.5). They never split a frame (proto P3, AUT-02).
- **Tail inserts:** requests, Ping and Close. Under `auth_completion == PerRequest` (native), a new `add_auth` packet also goes to the tail, in call order; reconnect re-sends still go first (hook A10, §15).
- **Sensitive frames** (Connect, which holds the session password; Auth; Sasl) are marked `sensitive`. `FrameBuf` zeroes their bytes when the frame completes or is dropped.
- **Gating by phase:**

  | Phase | May send |
  |---|---|
  | Established | anything |
  | Sasl | Sasl frames only; stop at the first non-SASL head (SAS-02) |
  | Associating without SASL | Connect only |
  | Closing flush | anything, if the session was established when `queue_close_op` ran |
  | Any other phase, or no transport | nothing |

- A Request frame whose last byte is acknowledged marks its Pending entry `written`.
- **Unsent requests survive failed attempts only until the next teardown fails them** (ST-07). A forced close fails those queued at its trigger, and a request submitted after the trigger stays queued for the next connection (§12.3).

## 7. Receive pipeline and session establishment

### 7.1 Frame dispatch

Every complete frame sets `last_recv = now` (3139). Frames are then dispatched by phase:

1. **Associating, handshake pending:** the ConnectResponse (§7.3).
2. **Sasl phase:** the frame is a SASL reply, consumed without an xid check in both profiles; this is not a `Compat` knob (§7.4; SAS-02).
3. **Otherwise:** `ReplyHeader::peek`. Fewer than 16 bytes tears down with ProtocolError, rc ZCONNECTIONLOSS (proto P6). Then dispatch on xid:

| xid | Action |
|---|---|
| -2 | drop; DEBUG latency log |
| -1 | DEBUG "Processing WATCHER_EVENT" (3567); decode `WatcherEvent`; strip the path (a mismatch ERROR goes into `delivery_logs`); collect watchers now (§10); emit `Watch` with its `delivery_logs` (§5.1). Under `LEGACY_C` the output is emitted even for an empty list (WAT-07: no callback, the lines only); under `NATIVE` only when the list is non-empty |
| -8 | DEBUG "Processing SET_WATCHES"; drop (errors ignored) |
| -4 | DEBUG "Processing AUTH_XID"; §8 |
| other | FIFO match |

FIFO match:
- **Empty FIFO, or head not written:**
  - while closing, a reply with the recorded CLOSE_OP xid under `close_mode = Drain`: the close completes, rc ZOK (§13);
  - any other reply while closing: DEBUG log, drop the frame, rc ZINVALIDSTATE (3604-3610);
  - otherwise: teardown XidMismatch, ZRUNTIMEINCONSISTENCY (proto P4; C asserts).
- **Head xid differs:** teardown XidMismatch (DSP-07). The head stays and is failed with the rest.
- **Match:**
  1. pop the head;
  2. if `hdr.zxid > 0`, set `last_zxid = hdr.zxid`, error replies included (WIRE-09);
  3. arm `watch` per the checker table, and apply `unwatch` if err == 0, both **before** the completion is emitted (DSP-06);
  4. if `err != 0`, `reply = None` and the body is not parsed, except for a `Route::Direct` multi whose frame has bytes after the `ReplyHeader`: that body is decoded by wire type and `rc` is computed from the sub-results, as `process_sync_completion` does (zookeeper.c:5529-5531; 08 MU-04). A header-only Direct multi has `reply = None` and `rc` = header err (proto P16, MUL-06). Otherwise decode by shape, stripping paths; a strip mismatch ERROR goes into `delivery_logs`, after the delivery DEBUG line of §5.1 ("Calling COMPLETION_*" for a Queued completion, "Processing sync_completion" for a Direct one), which every reply's `delivery_logs` starts with. For `Reply::Multi`, `rc` is the first item err other than 0 and ZRUNTIMEINCONSISTENCY, else 0 (MUL-03, zookeeper.c:3319-3328), and the `delivery_logs` line still prints the header values (§5.1). A decode failure pushes the head back and tears down with ProtocolError (proto P6, WIRE-04);
  5. emit `Completion{route, delivery_logs}`. A Direct completion is a barrier, so `handle_read` stops after it and the waiter is signalled before later frames are processed, as legacy does.

### 7.2 Connect decision (2655-2741)

1. **Delay pending:**
   - `OneShotSkip` (legacy): clear the flag, log the "Delaying connection after exhaustively trying all servers [%s]" WARN, reset `last_recv`, `last_send`, `last_ping` and `last_ping_rw`, set `rw_timeout = 200`, and yield no action. `finish_interest` writes `tv = T/60`. The next iteration connects regardless of elapsed time (ST-14).
   - `Deadline` (native, hook A13): wait until `not_before`. `not_before: Option<Millis>` is set where legacy sets `delay`, that is, when a full host-list pass ends, except a first pass through `new` and `old` (§9.2), or the list is empty (step 3): `not_before = now + d + offset`, with `d = reconnect_delay_ms` and `j = d * reconnect_jitter_pct / 100` (truncating, in i64), and `offset = rng.random().rem_euclid(2*j + 1) - j`, one `Rng::random` draw, so the pause lies in `[d - j, d + j]`. While `now < not_before` there is no action, and `finish_interest` writes `timeout_ms = not_before - now`. When `now >= not_before`, the core clears `not_before` and continues with step 2 in the same iteration. With `d = 0` the pause is empty and no draw is made.
2. **Resolution failed this iteration with no transport, under `dns_failure = LegacyRcPreserved`:** no action (`BlockConnect`, as C).
3. **Endpoint:** `rw_target.take()` if set, otherwise `select_next_server()` (§9.2).
   - An empty list runs teardown SocketCreate (ZSYSTEMERROR) and sets `delay` (proto P12, SRV-08).
4. Yield `Connect{endpoint, tls}`.
5. **Timestamp reset.** C resets `last_recv`, `last_send`, `last_ping`, `last_ping_rw` and `rw_timeout = 200` only when the connect block finishes without an early return (2735-2740). The core does the same: the reset runs on `handle_connect_started(InProgress)`, or on the immediate path after the transport becomes ready (or, with TLS, after the handshake phase starts). It does not run after `socket()`/`connect()` failure or after an immediate-path `TlsConfig` failure, which returns at 2717-2720 before the reset. The un-reset `last_recv` then drives the receive deadline, as in C (CC-14, 00 §4).

### 7.3 Handshake

`handle_transport_ready`:
- Pushes the `ConnectRequest` as a priority `Connect` frame:
  - `session_id` = `seen_rw_before ? client_id.session_id : 0`;
  - `passwd` = the stored 16 bytes;
  - `timeOut` = `recv_timeout` under `handshake_timeout = Negotiated`, which is the negotiated value after the first session (ST-10); under `Requested` (NATIVE) it is `Config.timeout_ms` on every handshake;
  - `lastZxidSeen` = `last_zxid`; `readOnly` = `cfg.allow_read_only`.
- Sets state 2 (2391).

ConnectResponse (3160-3193):

```text
old_id = seen_rw_before ? client_id.session_id : 0;   seen_rw_before |= !resp.read_only
expired = (old_id != 0 && old_id != resp.session_id) || (compat.expiry == Java && resp.timeout_ms <= 0)
if expired: state = -112; teardown(SessionExpired)    // rc ZSESSIONEXPIRED, errno hint ESTALE (ST-09)
else: recv_timeout = resp.timeout_ms; client_id = {resp.session_id, resp.passwd}
      emit ClientId(client_id)
      if cfg.sasl: phase = Sasl(SaslNegotiation::new())
                   if let Some(old) = mech_gen.take(): yield Action::Sasl(SaslCall{gen: old, kind: Dispose})
                                                       // zoo_sasl_connect disposes first (zk_sasl.c:215-217)
                   yield Action::Sasl(SaslCall{gen: next, kind: Start}); mech_gen = Some(next)
                   // state stays 2
      else: finalize()
```

### 7.4 SASL (sequencing in the core; mechanism in C for the drop-in)

```rust
pub struct SaslStep { pub token: Option<SecretBytes>, pub done: bool }   // done=false: SASL_CONTINUE
/// A mechanism error. rc is ZSYSTEMERROR for mechanism errors.
/// Native mechanisms fill the two strings. zk-ffi passes them empty (the glue logs them).
pub struct SaslError { pub rc: i32, pub errstring: Vec<u8>, pub errdetail: Vec<u8> }
/// gen is never 0 and wraps from u32::MAX to 1. Start takes a new value, Step carries the
/// live value, and Dispose carries the gen of the Start that created the session it ends.
pub struct SaslCall { pub gen: u32, pub kind: SaslCallKind }
pub enum SaslCallKind { Start, Step(Option<SecretBytes>) /* None: server token -1 */, Dispose }
/// Which socket-address read failed before START or before the native `SaslContext` was built (both drivers).
pub enum SaslAddr { Local /* getsockname */, Peer /* getpeername */ }

/// Native mechanism contract (zk-client DIGEST-MD5, GSSAPI). zk-ffi does not implement it.
pub trait SaslSession: Send {
    fn start(&mut self) -> Result<(String, SaslStep), SaslError>;
    fn step(&mut self, challenge: Option<&[u8]>) -> Result<SaslStep, SaslError>;
}
```

`gen` is `u32` because it crosses the private C ABI as `uint32_t` (`zkrs_sasl_call.gen` and `zkrs_sasl_result`, owned by 05 in `zkrs.h`; the glue functions `zks_sasl_start`, `zks_sasl_step` and `zks_sasl_dispose` take `uint32_t gen`, 06 §4.7.2). Server tokens and mechanism tokens are secrets, so both `Step` and `SaslStep` hold `SecretBytes` (§1).

**Who runs the mechanism.**
- **Drop-in (06 §4).** zk-ffi turns each `Action::Sasl` into a SASL{START, STEP, DISPOSE} outbox item, drained on the IO owner (the mt IO thread, the st caller, or, for the DISPOSE of the final close, the thread that runs the final close after the IO thread is joined or has exited) with no Rust frame below it. Shim C calls Cyrus only from `shim/zks_sasl_cyrus.c` (`zks_sasl_start`, `zks_sasl_step`, `zks_sasl_dispose`) and returns the result with `zkrs_sasl_result(core, gen, view)`. zk-ffi copies the view at once and calls `handle_sasl_started`/`handle_sasl_stepped`. Every byte argument that crosses to C is a bounded `zks_bytes` view built from data the core has already bounds-checked; a -1 server token is `is_null=1, p=NULL, len=0` (SAS-10). The driver reads the local and peer addresses with rustix `getsockname`/`getpeername` on its own socket; no fd is lent (CC-31, 00 §4). zk-ffi writes each address as the platform `sockaddr_in` or `sockaddr_in6` image into the START item's `zkrs_sasl_call.local`/`peer` (`zkrs_bytes`; 05 §19.2 owns `zkrs.h`). The glue's `zks_sasl_start` takes them as `zks_bytes local, zks_bytes peer`, validates family and length, calls `getnameinfo(NI_NUMERICHOST|NI_NUMERICSERV)` and formats `"%s;%s"` with `snprintf` into bounded buffers. On a `getnameinfo` error it logs "getnameinfo: %s\n" at the legacy site (zk_sasl.c:185). Legacy formatting is therefore byte-identical, IPv6 scope suffixes included (06 §4.7.2). If either rustix read fails, the driver builds no START item and calls `handle_sasl_addr_failed(gen, which, now)` (table below). The DISPOSE item that precedes that Start in the same outbox is still built, so the old Cyrus connection is disposed in that case too, as `zoo_sasl_connect` disposes before it calls `getsockname` (zk_sasl.c:215-224). Cyrus and `getpass` callbacks are application code and run only in those C frames. Secrets from password callbacks stay in C: the library password callback runs with no ZooKeeper lock held and writes into a per-session sink owned by the trampoline (06 §4.7.6-4.7.7; DAT-13 FU). Only the mechanism tokens enter Rust, as `SecretBytes`.
- **Native.** The driver calls `SaslSession` with no core lock held, inline on the IO thread or through `spawn_blocking`.

**Generation and serialization.**
- `gen` advances at each `Start` and at each teardown, wrapping from `u32::MAX` to 1 and never 0. `Start` takes the new value and `Step` carries the live value. The advance at teardown makes a late result for the closed connection stale. A result whose `gen` is not the live one is ignored by the core. The glue also rejects a stale `gen` itself, with status STALE and no Cyrus call, so the libFuzzer harness covers the check; the drain records `gen` through `zks_sasl_set_gen`, which is defined in `shim/zks_sasl_cyrus.c` (06 §4.7.2).
- At most one `Start`/`Step` is outstanding per handle. The core yields the next call only after the previous result arrives.
- **Dispose timing is legacy timing.** The core records `mech_gen`, the `gen` of the last `Start` handed to the mechanism. The mechanism session survives teardown, forced close and SASL failure, as the legacy Cyrus connection does. `Dispose{gen: mech_gen}` is yielded in exactly two places, and each clears `mech_gen`:
  - immediately before the next `Start`, in the same outbox, because `zoo_sasl_connect` disposes the old connection first (zk_sasl.c:215-217: `if (sc->conn) sasl_dispose(&sc->conn);`);
  - at `destroy`, after `CloseTransport`, because legacy destroy closes the socket (zookeeper.c:719-723) before `zoo_sasl_client_destroy` disposes the connection (744-749, zk_sasl.c:122-124).

  A teardown alone yields no `Dispose`. If a `Start`/`Step` result is still outstanding when a `Dispose` is due, the `Dispose` (and any `Start` behind it) waits for that result, which is then ignored as stale. Any result for the outstanding call ends this wait, also one whose `gen` is no longer live. In the drop-in, C can leave a `START` or `STEP` item unanswered: an application Cyrus callback throws during an st item, or the glue's stale check fires. zk-ffi then records the `gen` of that item. After the receive timeout tears the connection down and advances `gen` (§12.1 T1), zk-ffi passes `handle_sasl_started` or `handle_sasl_stepped(old_gen, Err(SaslError{rc: ZSYSTEMERROR, ..}))` in that same core call (05 §5, §19.2). The core ignores the result as stale, and the wait ends. The next prime response therefore yields `Dispose` and then `Start`, as legacy `zoo_sasl_connect` disposes the stalled connection and starts again (zk_sasl.c:215-217; zookeeper.c:3188-3189). Dispose therefore goes through the same outbox ordering as every other SASL item and is never concurrent with one (06 §4.7.4). A Cyrus callback that dispose triggers (a `SASL_CB_LOG`, for example) runs at the legacy point, on the IO owner.
- A SASL failure keeps the session until `destroy`, as C keeps the Cyrus connection until close (zookeeper.c:744-749). The failure is terminal, so no later `Start` comes.

**Log-line ownership.** Lines that need live Cyrus results (`sasl_errstring`, `sasl_errdetail`, the raw Cyrus `sr`) are emitted by the core only for native mechanisms. In the drop-in the glue emits them in C, in the drain (05 §19.2), and zk-ffi passes `SaslError` with empty strings, so the core stays silent for those lines. The rows below mark these lines "native only". The core (Rust) sites in both profiles are "SASL authentication failed. rc=%d", the "getsockname" and "getpeername" failure lines, and "SASL intermediate server_data_len:%d" (`abi/log-sites.tsv`). The C glue does not log them. The glue alone emits "getnameinfo: %s\n" (zk_sasl.c:185), DEBUG "Zookeeper Host: %s %s" (246-247) and "allocating SASL connection state: %s" (260-262); they have no core counterpart.

`SaslNegotiation{is_gssapi, gssapi_last_packet, awaiting_final}` is created fresh at every prime response (SAS-04 FU).

| Event | Core behavior | Log site (zk_sasl.c / zookeeper.c) |

**SASL failure (`Compat::sasl_failure = Teardown`, both profiles; DV-FIX-3, ST-18).** Every failure in the table above takes the path of C's digest-auth failure (`handle_error(zh, ZAUTHFAILED)`, zookeeper.c:3590-3597), in place of C's SASL path, which only sets the state and leaves pending work waiting for `zookeeper_close` (zk_sasl.c:135-141; zookeeper.c:3147-3150, 3190-3193):
- **State.** AUTH_FAILED (-113), set in the core call that sees the failure. It is terminal. The log lines stay those of the table above, and no T0 line is added, as `zoo_sasl_mark_failed` logs nothing and the digest path has no T0 line.
- **Teardown.** A `Cause::SaslTeardown` teardown runs (§12.1). T1 closes the transport, advances the SASL `gen` and drops the negotiation. T2 emits `Session{-113}` with its DEBUG line, for the default watcher and the path watchers as on the digest path. T3 fails every entry of `tx` and the FIFO with ZAUTHFAILED (Direct entries as barrier runs, §5.3) and then emits `AuthLockpoint` and `Auth{all pending, ZAUTHFAILED, barrier: legacy}`. T4 leaves the state at -113 and emits `DrainPoint`. T5 sets `delay`, which no later connect reads, and `cur = addrs.peek()`, so `zoo_get_current_server` then reports the address at the cursor (the server to be tried next), as on the digest path; C's SASL path leaves it on the failed connection's server.
- **The rc of the call** stays the SASL rc: `handle_*`/`ReadOutcome` return it, so st `zookeeper_process` returns it, as C returns it from `check_events` (3147-3151, 3190-3193). It is not replaced by ZAUTHFAILED. A server rejection normally is ZAUTHFAILED already. When a requeued SASL item fails inside `zookeeper_interest`, that call returns the SASL rc.
- **Threads and lifetime.** These are the digest path's. In mt the event and the async results go to the dispatch thread, the sync and auth results run on the IO thread at their barriers, and the IO thread then exits, while the dispatch thread stays until close (03 §5.4, §5.5, §10.10). In st everything runs inside the `zookeeper_process` or `zookeeper_interest` call that drove the failure (03 §6.4). Afterwards every request call, `zookeeper_interest` and `zookeeper_process` returns ZINVALIDSTATE, as for any unrecoverable state; `zoo_set_servers`, local watch removal, accessors and `zookeeper_close` behave as in C, except that `zoo_set_servers` finds no open transport, so it commits its list and leaves the state at -113 (ST-18).
- **Mechanism session.** T1 yields no `Dispose`. The session stays until `destroy` yields `Dispose` after the socket close, the point at which C disposes it (§7.4).
- **NATIVE.** Every SASL failure is terminal, transient mechanism errors included: the core does not retry the negotiation, the session ends, and the application decides whether to create a new client (04).

`mark_sasl_failed()` (the faithful `zoo_sasl_mark_failed`; 07 ABI-12, RE) only sets state -113 and ends the negotiation, as the undeclared C function does (zk_sasl.c:135-141). It has no log line, no rc and no teardown.

### 7.5 finalize (2986-3008)

1. State becomes 5 if `read_only`, otherwise 3. `reconfig = false`. Phase becomes Established.
2. INFO "session establishment complete on server %s, sessionId=%#llx, negotiated timeout=%d %s".
3. SetWatches is inserted as a priority frame (§10.5).
4. `AuthLockpoint` (§5.4). After resume, auth entries are inserted as priority frames in list order, so the wire order is auth_n..auth_1, SetWatches, queued requests (AUT-01). Under `auth_resend = Forward` (NATIVE) the entries are inserted last to first, so the wire order is auth_1..auth_n, SetWatches, queued requests. If the list is non-empty, DEBUG "Sending all auth info request to %s".
5. DEBUG "Calling a watcher for a ZOO_SESSION_EVENT and the state=ZOO_CONNECTED_STATE", then `Session{state, snapshot, barrier: Inline, delivery_logs}` (§5.1).
6. After a SASL negotiation, the frames held back during SASL become sendable (the C flush at 3004-3007).

## 8. Auth list

```rust
struct AuthEntry<A> { scheme: JString, cred: SecretBytes, done: Option<A> }
pub struct AddAuthError<T: Tokens> { pub code: i32, pub done: Option<T::Auth> }   // token handed back
```

**`add_auth`** (zookeeper.c:5301-5350; C holds `auth_lock` around the call):
- `state < 0` → ZINVALIDSTATE. Under `LegacyBroadcast`, `state == 0` → ZINVALIDSTATE (RC-08). Under `PerRequest`, state 0 records the entry. NULL scheme and NULL `zh` are rejected by the shim before the call (ZBADARGUMENTS). A negative `certLen` gives ZSYSTEMERROR only after the two state checks, at the stage of 05 §12.1 step 3 (RC-08).
- Otherwise the entry is appended (append-only, never deduplicated).
- **Send rules:**
  - Connected, or Associating without SASL: one `AuthPacket{0, scheme, cred}` frame (xid -4, op 100) for the entry just added. Under `LegacyBroadcast` it goes to the priority boundary; under `PerRequest` it goes to the tail (hook A10).
  - In Associating the packet is sent again by finalize, so it goes out twice, exactly as in C (5340-5346), while `Compat::auth_dup_while_associating` is true (LEGACY_C). NATIVE sets it false.
  - Any other state: record only.
- **The token is retained if and only if `Ok`.** Encoding cannot fail except through allocator abort (07 P7), so C's "ZMARSHALLINGERROR with the completion still registered" path cannot happen. Every non-OK status of `zkrs_add_auth` means "not retained" (CC-10, 00 §4).

**AUTH reply** (`LegacyBroadcast`, 2151-2189, 3585-3598):
1. `AuthLockpoint` (barrier).
2. After resume: if a forced close fired during this lockpoint, the reply belongs to the closed connection and the rest of this list does not run (§12.3). Otherwise, if `err != 0`, state becomes -113.
3. Collect every pending token in list order.
4. `Log`: ERROR "Authentication scheme %s failed. Connection closed." or INFO "Authentication scheme %s succeeded", with the first entry's scheme (AUT-05).
5. `Auth{tokens, rc: err, barrier: state < 0}` if any token was collected.
6. Continuation: if state < 0, teardown AuthFailed (ZAUTHFAILED) and stop processing the buffer.

An AUTH reply with an empty list is processed without completions and logs the scheme as `(null)` (AUT-07 FU; C dereferences NULL).

`PerRequest` (native) matches each AUTH reply FIFO-wise to the oldest in-flight auth packet and completes only that token.

### 9.2 AddrVec and selection

```rust
pub struct AddrVec { data: Vec<Endpoint>, next: usize }  // has_next, at_end, next, peek, contains(eq)
// peek: what next() would return, without moving the cursor (addrvec.c:239-253).
impl AddrVec {
    /// addrvec_eq (addrvec.c:256-271): same count, and every old address is in new.
    /// It is one-way, not a multiset compare: {A,A} equals {A,B}. Argument order matters.
    pub fn legacy_eq(old: &[Endpoint], new: &[Endpoint], eq: AddrEq) -> bool {
        old.len() == new.len() && old.iter().all(|a| new.iter().any(|b| eq.same(&a.addr, &b.addr)))
    }
}
fn shuffle(v: &mut [Endpoint], rng: &mut dyn Rng) {      // addrvec.c:192-203, exact
    let mut i = v.len().saturating_sub(1);
    while i > 0 {
        let modulus = i64::try_from(i).map_or(i64::MAX, |x| x.saturating_add(1));
        let j = usize::try_from(rng.random().rem_euclid(modulus)).unwrap_or(0);
        if i != j { v.swap(i, j); }                       // swap() is bounds-checked
        i = i.saturating_sub(1);
    }
}
```

Endpoints compare by `addr` only, using `Compat::addr_eq`; the host token travels with its address and never changes order or equality.

`select_next_server()` is `zoo_cycle_next_server` (1610-1677):
1. Set `cur = None`.
2. If `reconfig`:
   - `take_new = rng.drand48() <= p_new`. This is drawn on every call, as C does (1612).
   - If `new.has_next() && (take_new || !old.has_next())`, take `new.next()`.
   - Otherwise, if `old.has_next()`, take `old.next()`.
   - Otherwise set `reconfig = false`.
3. If nothing was selected, take `addrs.next()`.

`cycle_next_server()` is the public API and calls the same function.

**Cursor (`Compat::server_cursor = SingleAdvance`, both profiles; DV-FIX-1, SRV-01).** After a failure, T5 sets `delay = at_end(addrs) || addrs.is_empty()` (§12.1) and `cur = addrs.peek()` without moving the cursor, and the next connect advances once. C's `handle_error` runs `addrvec_next` at that point (2124-2132) and, once reconfig is off, its next connect advances again. A new handle has reconfig on from init (zookeeper.c:1450, 1155-1201) and so does this core (§9.3): its first pass tries each server once through `new`. After that pass, C advances twice per failure, and with two servers it retries one server for ever, after at most one move to the other. The T/60 delay and its WARN line follow each full pass over the list except a first pass through `new` and `old`, which leaves `addrs` unmoved. C's delay depends on the cursor parity, so an even-sized list can delay at every end of the list or never.

**The reported server.** `cur` is what `current_server()` and `zoo_get_current_server` return and what the `found_current` test of §9.3 reads. The header describes the report as the server the client is connecting to or connected to (zookeeper.h:866-875). Its value around a failure:

- **From selection through T4.** `cur` is the server of the attempt or connection, and the T0 and T4 log lines name it. C's `cleanup` runs before `handle_error` advances (2101-2132), and T5 runs after T4's `DrainPoint`, so a callback that a teardown runs during T2-T4 reads the server of the closed connection. This holds for every st callback, which C runs inline inside `cleanup` (2119-2121, 3264-3266; the auth completions at 2070-2076), and for an mt auth completion, which runs on the IO thread (2070-2076). An mt completion-thread callback and a sync caller woken at T3 run independently of the IO thread, so each reads that server or the next one, as C's completion thread does against `handle_error`.
- **From T5 to the next selection.** `cur` is the address at the `addrs` cursor: the address after the failed one when `addrs` chose the failed server, or the first address at the end of the list; after a selection from `new` or `old`, including a session established in a new handle's first pass, the unmoved cursor address, which can be the failed server. Once a session has cleared `reconfig`, the next connect then retries it. An empty list leaves `cur` empty (`":0"`), as `addrvec_next` zeroes `addr_cur` (addrvec.c:215-237). The delay iteration does not change it. C's report after a failure follows the same rule, because `handle_error` takes it with `addrvec_next`; the values differ from C's only as far as C's cursor differs, through its double advance and through the `handle_error` moves of a first pass.
- **At the next selection.** With no reconfig pending, step 3 takes the address T5 peeked, so the report names the server chosen. C's connect advances `addrs` again, so its report names an address that the connect skips. With a reconfig pending, selection takes from `new` or `old` and `addrs` does not move, so the report can differ from the server chosen, as in C, where `handle_error` reads only `addrs` (2131, 1624-1636). The report repeats across the failures of that pass, where C's `handle_error` moves `addrs` on each one.
- **Teardowns with no T5.** A forced close (§12.3) and `RwServerFound` (§12.2) leave `cur` alone. After a forced close the report stays on the closed connection's server, through its T2-T4 and until the next selection; C's two sites only close the socket and set state 999 (1222-1226, 4153-4161). After `RwServerFound` it stays there until the next connect takes `rw_target`; C runs `cleanup` alone and then sets `addr_cur` from the probed address (2797, 2674-2677).

### 9.3 Rebalancing (update_addrs, 1145-1229)

`apply_resolution(resolved, shuffle)`:
1. If `shuffle`: `rng.on_resolution()`, then `shuffle()`. This runs on every successful resolution (1028-1038; SRV-04 RE). In the drop-in the reseed itself already ran in the driver's unlocked resolve step (§3.3).
2. If `AddrVec::legacy_eq(&addrs, &resolved, addr_eq)` (old list first, as `update_addrs` calls `addrvec_eq(&zh->addrs, &resolved)`, zookeeper.c:1146), nothing changes: no `reconfig`, no `drand48()` draw, no forced close. Duplicate addresses are legal (INIT-04 keeps duplicate A/AAAA records, and two host tokens can resolve to one IP), so old `{A, A}` and new `{A, B}` compare equal, as in C.
3. Otherwise apply C's branch table with `rng.drand48()`, using identical f64 arithmetic, NaN for 0/0 included (1145-1212, SRV-03). Its `found_current` input is whether `resolved` contains `cur` under `addr_eq` (1152), and it keeps C's meaning: the server of the open transport; with no transport, the address T5 peeked (§9.2), or the closed connection's server after a forced close. An empty `cur` is never found.
4. `addrs = resolved`, `next = 0`.
5. If `reconfig && has_transport`, apply the forced-close policy (§12.3).

`addr_eq` is `IpAndPort` in both profiles (DV-FIX-2, SRV-02), so a port-only change counts as a change. C compares the IP only (addrvec.c:119-152). Everything else about `addrvec_eq`, its one-way comparison included, is kept.

### 9.4 DNS

- **Cadence:**
  - always at init and in `set_servers`;
  - with no transport, by `Compat::resolve_cadence`:
    - `EveryIterationWhileDisconnected` (`LEGACY_C`): on every interest iteration;
    - `EachPass` (`NATIVE`, the `dns_refresh` default; hook A14): once per full host-list pass, at the first connect decision after the pass ended (§7.2 step 1; under `Deadline`, when the pause ends), before the next endpoint is selected;
    - `Throttled { ms }` (native `Interval(d)`): when more than `ms` have elapsed since `last_resolve`, the same test that `resolve_delay_ms = d` applies with a transport;
    - `Never` (native; hook A14): never, apart from init and `set_servers`;
  - with a transport: by `resolve_delay_ms` (-1 never, 0 always, d > 0 when more than d ms have elapsed since `last_resolve`; elapsed < 0 also resolves, 1106-1121). zk-client sets it from `dns_refresh` (§3.3), so `EachPass` and `Never` do not resolve while connected.

  `last_resolve` is set only on success (SRV-05).
- **Driver duties.** Resolution is the Blocking vtable leaf `resolve` in the drop-in (CC-5, 00 §4): `getaddrinfo` with the legacy hints (`AI_ADDRCONFIG`, `AF_UNSPEC`, `SOCK_STREAM`, `IPPROTO_TCP`), one retry without flags on `EAI_BADFLAGS`/`EAI_ADDRFAMILY`, AF_INET/AF_INET6 kept in order with duplicates, each skipped family reported as data, and the `getaddrinfo_errno` mapping (INIT-04; 950-1013). It runs with no Rust lock held, returns errors as data, and does not log. The driver passes each `HostResolution` (one per host token) with `handle_host_resolved` as soon as its `resolve` leaf returns, then runs `rng_reseed` if due (§3.3; after the log-flush barrier), then calls `handle_resolved`. Results carry `gen`, the resolver generation (`u64`, a counter separate from the SASL generation); a stale `gen` is ignored.
- **Logs before blocking work (drop-in).** Pending LOG items are delivered before every Blocking vtable leaf call (`resolve`, `rng_reseed`) and before the TLS file reads of the IO step (§4.3). When LOG items are pending at that point, the zk-ffi step (init, `zoo_set_servers`, the mt IO step, or st `zookeeper_interest`/`zookeeper_process`) stops at a step barrier (`ZKRS_MORE`). C drains them, which invokes the log callback from a C frame, and `zkrs_resume` then continues into the blocking call (05). This costs one extra round trip, only on those paths and only when logs are pending. It is a zk-ffi step boundary, not a core barrier (§5.3): the core's output order is unchanged.
- **Logging and rc (core).** `handle_host_resolved` emits, at once, for a failed host, one line with `GaiStr{gai_rc, errno}` at the platform's legacy site: ERROR `getaddrinfo: %s`, or `Win32 message: %s` on Windows (zookeeper.c:982-988). It also emits the "skipping unknown address family %x for %s" WARN for each skipped family. Each host's lines are therefore pending before the next host's `resolve` call and before `rng_reseed`, so the log flush delivers them in C's order (zookeeper.c:939-941, 982-988, 1016-1017, 1036). A failed host does not fail the list (C continues with the next token). `handle_resolved` then commits the collected list and the rc. If no address resolved, the rc is ZSYSTEMERROR, and the errno hint is the last failure's errno (INIT-01).
- **Whole-list failure (`dns_failure = LegacyRcPreserved`):**
  - **No transport:** no connect this iteration; outputs not written (§4.1).
  - **Transport open (proto P10, SRV-06 FU):** the failure counts as "no change". Timers, pings and interest run and the outputs are written. The rc is the resolver rc unless a teardown occurs in the call (CC-22, 00 §4).
  - `UseLastGood` (native): the failure is ignored and the last good list stays.
- **`set_servers`** (zookeeper.c:1551-1572; CC-23, 00 §4; 05 D9):
  - zk-ffi parses first with `legacy::parse_servers`. A parse error returns its rc (RC-09) and **is not committed** (FU: in C the bad string stays installed and the handle can never reconnect).
  - With a good parse, `set_servers(hosts, now)` commits the host list, bumps `gen` and returns it (an in-flight resolution of the old list is then ignored).
  - The driver then resolves the new list with the same per-host sequence: `handle_host_resolved` per host, `rng_reseed` if due, then `handle_resolved(gen, shuffle, now)`, whose rc zk-ffi returns from `zoo_set_servers`. `handle_resolved` applies the results. On success: `apply_resolution`, rc ZOK. On whole-list failure: the old `addrs` stay, the new host list **stays committed**, and the rc is ZSYSTEMERROR. The next due resolution uses the new list. That is legacy's commit-then-retry behavior, which applications may rely on.
  - `""` gives an empty list.

### 9.5 Read-only probe

The driver performs the probe with these bounds (SRV-11 FU):
- non-blocking connect, at most 1 s;
- with TLS, a non-blocking handshake with a fresh `RustlsConn` and the `tls_verify` policy, at most 1 s;
- send `"isro"`;
- one read of at most 10 bytes into a zero-filled 10-byte buffer, within 1 s;
- success iff `buf[0] == b'r' && buf[1] == b'w' && buf[2] == 0`. This is exactly C's `strcmp(buf, "rw") == 0` rule on a zero-filled `char buf[10]` after one recv (zookeeper.c:2463, 2509-2516; SRV-11): the comparison stops at the NUL of `"rw"`, so a reply such as `"rw\0x"` succeeds and the rule never reads past byte 3;
- the probe socket is always closed.

The driver reports the result with `handle_rw_probe(ep, outcome, now)`: `ReadWrite` on success, `NotReadWrite` when the read completed but the rule failed, `Failed(..)` otherwise (§4.3 for the TLS lines).

Results:
- **Success:**
  1. `rw_target = Some(endpoint)` (per handle; proto P13);
  2. `rw_timeout = 200`;
  3. INFO "r/w server found at %s";
  4. teardown RwServerFound (§12.2).
- **`NotReadWrite` or `Failed`** (any TLS failure included): `addrs.next()` without setting `cur` (2799-2801).

## 10. Watcher registry

### 10.1 Table implementation per `Compat::watch_table`

**`LegacyHashtable` (LEGACY_C) is a safe-Rust port of hashtable.c plus zk_hashtable.c.** Iteration order is bit-identical to C (WAT-05). The port reproduces:

- **Key hash.** djb2 over `unsigned int` with C `char` semantics, stopping at the key's end (zk_hashtable.c:68-77):

  ```rust
  let mut h: u32 = 5381;
  for &b in key {
      // C adds an int read from a char. Signed char sign-extends bytes >= 0x80.
      let c: i32 = if cfg.c_char_signed { i32::from(i8::from_ne_bytes([b])) } else { i32::from(b) };
      h = h.wrapping_shl(5).wrapping_add(h).wrapping_add(u32::from_ne_bytes(c.to_ne_bytes()));
  }
  ```

  There is no `as` cast: the reinterpretations use `from_ne_bytes`.
- **Mixer.** hashtable.c:57-68, with wrapping ops:

  ```
  i += !(i << 9); i ^= (i >> 14) | (i << 18); i += i << 4; i ^= (i >> 10) | (i << 22)
  ```
- **Index.** `indexFor = h % len` (hashtable_private.h:33-35).
- **Sizing.** Primes table from hashtable.c:15-23. `create_hashtable(32)` gives 53 buckets. `loadlimit = ceil(size * 0.65f32)`, with the product computed in f32 as C does.
- **Insert.** `++entrycount > loadlimit` triggers an expand **before** the insert. The new entry is **prepended** to its bucket chain.
- **Expand.** Walk old buckets 0..len. Pop each chain from the head and prepend to the new bucket. This reverses relative order, as C does (hashtable.c:71-125). The `primeindex` cap is reproduced.
- **Remove.** Unlink from the chain; `entrycount -= 1`.
- **Iteration.** Iteration walks buckets 0..len, and each chain from head to tail.
- **Per-key lists.** Newest first: insertion prepends after a (fn, ctx) dedup check (zk_hashtable.c:162-179). Removal unlinks.

**`Ordered` (NATIVE)** uses path-keyed tables (`BTreeMap<JString, Vec<W>>`) whose per-path lists keep registration order (insertion appends), plus the native persistent and recursive tables with the same per-path order. Delivery to several watchers of one kind on one path therefore follows registration order, oldest first; the kinds follow §10.3 (04). Native watchers are never deduplicated against each other, because each has its own `WatchId` (04).

### 10.3 Collection and delivery order

`fan_out(seq)` takes watchers in C collection sequence. Each table is visited in iteration order, and each key list head to tail. The function keeps only the first occurrence of each watcher. It returns the kept watchers **reversed**. This is C's prepend-with-dedup into the delivery list (zk_hashtable.c:162-179, 296-327).

| Event | Collection sequence (removes keys for node events) | Delivery (`fan_out`) |
|---|---|---|
| CREATED, CHANGED | data[path], exist[path] | exist (oldest first), data (oldest first) |
| CHILD | child[path] | child |
| DELETED | data, exist, child | child, exist, data |
| other types | none | empty list: under LEGACY_C a `Watch` with no watchers, for its `delivery_logs` only (WAT-07; the lines are specified in §5.1 `delivery_logs`); NATIVE: no output |
| Session (legacy, `session_fanout_to_path_watchers`) | default, then every key of data, exist, child in **table iteration order** (copied, not removed) | child keys (reverse iteration), exist, data, **default last** |

- Under `Ordered` (NATIVE), `fan_out` does not reverse: the watchers of each table come in registration order, oldest first, the one-shot tables come in the delivery-column order above, and the persistent and then the recursive table follow them. Native has no session fan-out to path watchers.
- Under `Ordered`, after the one-shot tables: `persistent[event path]` for every node event type, and then, for NodeCreated, NodeDataChanged and NodeDeleted only, `recursive[p]` for p = the event path and each ancestor up to "/", nearest first (Java's `PathParentIterator` order); registration order within each path; persistent and recursive entries are copied, never removed, on delivery. NodeChildrenChanged never matches the recursive table: the server sends it for a path below a recursive watch only when the session also holds a standard child watch on that path, and the Java client drops it from recursive matching in the same way (ZKWatchManager.java:445-457).
- Collection happens at receipt, so the window in which `has_watcher` is false while delivery is pending is reproduced (WAT-06).
- A session event reads the default `(fn, ctx)` through `DefaultWatcher::snapshot()` when the event is queued (WAT-05). In zk-ffi that is the Pure leaf `snapshot_default_watcher`, which reads the shim's pair cell under its spinlock. Because the default is collected first, a path watcher equal to it is dropped by the dedup.
- Node events carry the server's state, session events the client state (WAT-08).

### 10.4 Removal and has_watcher

- `has_watcher` follows zk_hashtable.c:460-493:
  - wtype 1 checks child; 2 checks data and exist; 3 checks all; anything else is false under legacy. Native also accepts 4 (persistent) and 5 (persistent recursive) (hook A3).
  - A `None` watcher always matches.
  - Only active tables count.
- **Non-local remove** is a request: op 17 (CheckWatches) when a watcher is given, op 18 (RemoveWatches) when it is NULL. Local tables change only on a ZOK reply. There is never a NOTWATCHING event (WAT-09, WAT-11).
- **Native (`detach_watcher`, hook A3):** a reference count per (path, watch class) that includes registrations on unanswered requests. It returns a `RemoveHint{path, wtype}` (op 18) when the last local user is gone, and also when a failed registration drops the last count while a server watch is set.
- **`WatchTerminated` (hook A4)** is emitted only when `session_fanout_to_path_watchers == false` (native): on a successful remove, local or non-local (`Removed`), on `clear_watches_on_expiry` (`SessionExpired`), on close or `abandon` (`Closed`), on SASL or digest auth failure teardown (`AuthFailed`), and on disconnect with `restore_watches == false` (`ConnectionLost`).

### 10.5 SetWatches and expiry

- **Both profiles (`set_watches_batch = Some(128 KiB)`; DV-FIX-4, WAT-10):** frames with xid -8 and `relativeZxid = last_zxid`, holding the keys of the tables in table iteration order, split into packets of at most `set_watches_batch` bytes. Java uses the same 128 KiB limit (ClientCnxn.java:118) but can exceed it by the last key of a batch (ClientCnxn.java:1040-1042). Nothing is sent if all tables are empty. Replies are ignored. The core inserts the packets at the priority boundary (§6.3) last to first, so they reach the wire first to last, after the auth frames and before queued requests (§7.5). A watch set that fits in one packet gives the single frame C sends (zookeeper.c:2258-2296). C has no size limit, so a larger set exceeds the server's `jute.maxbuffer` and the client reconnects forever.
- **Legacy:** op 101 only.
- **Native:** op 105 when persistent watches exist. Nothing is restored when `restore_watches == false`.
- **Expiry:** tables are kept under legacy (ST-11) and cleared under native.

## 11. Pure legacy functions (`zk_proto::legacy`)

These functions are the single home for the legacy rules. zk-ffi calls them through `Connection` or directly, for example `check_ttl` and `parse_*` at init and in `zoo_set_servers`.

```rust
pub mod legacy {
    pub fn is_sequence(mode: i32) -> bool { matches!(mode, 2 | 3 | 6) }   // equality (118-121)
    pub fn is_ttl(mode: i32) -> bool { matches!(mode, 5 | 6) }
    pub fn create_opcode(mode: i32, create2: bool) -> OpCode;             // 4 -> 19; 5|6 -> 21; else 1|15
    pub fn check_ttl(mode: i32, ttl: i64) -> Result<(), i32>;              // RC-04

    /// isValidPath (zookeeper.c:4064-4106). `p` is the bytes before the first NUL.
    pub fn is_valid_legacy(p: &[u8], mode: i32) -> bool {
        let seq = is_sequence(mode);
        let len = p.len();
        let at = |i: Option<usize>| i.and_then(|i| p.get(i)).copied().unwrap_or(0);  // C reads the NUL as 0
        if p.first() != Some(&b'/') { return false; }
        if len == 1 { return true; }
        if p.last() == Some(&b'/') && !seq { return false; }
        let mut last = b'/';
        for (i, &c) in p.iter().enumerate().skip(1) {
            let at_end = i.checked_add(1) == Some(len);
            let next_slash = at(i.checked_add(1)) == b'/';
            if c == 0 { return false; }
            if c == b'/' && last == b'/' { return false; }
            if c == b'.' && last == b'.' {
                if at(i.checked_sub(2)) == b'/' && ((at_end && !seq) || next_slash) { return false; }
            } else if c == b'.' {
                if at(i.checked_sub(1)) == b'/' && ((at_end && !seq) || next_slash) { return false; }
            } else if (0x01..0x1f).contains(&c) { return false; }   // 0x1F, 0x7F, >= 0x80 accepted
            last = c;
        }
        true
    }
    /// prepend_string (1710-1721): no chroot -> path; any 1-byte path -> chroot; else concatenation.
    pub fn prepend<'a>(chroot: Option<&[u8]>, path: &'a [u8]) -> Cow<'a, [u8]>;
    /// sub_string (1727-1744): byte prefix with no '/' boundary; equal -> "/".
    /// A mismatch gives the raw path and the ERROR record for delivery_logs (§5.1).
    pub fn strip<'a>(chroot: Option<&[u8]>, server: &'a [u8]) -> Stripped<'a>;
    pub fn parse_init(s: &[u8]) -> Result<ConnectString, HostParseError>;  // chroot at the first '/', last ':' port,
                                                                             // strtol(.., 0) check, raw service text (INIT-02..06);
                                                                             // a port error reports the first bad entry's index
    pub fn parse_servers(s: &[u8]) -> Result<Vec<HostSpec>, HostParseError>;
}
pub mod native { pub fn validate_path(p: &str, sequential: bool) -> Result<(), PathError>; pub struct Chroot;
                 pub fn parse_connect_string(..); }
```

`AddrVec::legacy_eq` (§9.2) is the port of `addrvec_eq`.

`HostParseError` carries its errno (EINVAL), its rc (ZBADARGUMENTS or ZSYSTEMERROR), the legacy log site ("no port in %s", "invalid port in %s"), and for a port error `entry: Some(k)`, the index of the first bad host entry, with the parsed entries before it (`prefix: Vec<HostSpec>`); a chroot error has `entry: None`. `parse_init` checks the chroot first, as legacy does before `update_addrs` (zookeeper.c:1443-1450). Legacy parses each port inside the `resolve_hosts` loop, after `getaddrinfo` has run for the earlier entries (870-889, 962, 1023-1024), so the init path resolves `prefix` through the per-host loop (with its lines and log-flush barriers, 03 §4.1) and only then fails with the port error, with no reseed. `","` and `",,"` produce EINVAL (INIT-06).

`ChrootPolicy::LegacyConcatNoEscape` (the `LEGACY_C` value; DV-FIX-7, chroot escape rejected) is C's concatenation with two checks after `prepend` when a chroot is set: a 1-byte path other than `"/"` is ZBADARGUMENTS, and a sequential create on `"/"` is ZBADARGUMENTS (PTH-04). Inside `zoo_amulti` such a sub-op fails the call as any invalid sub-path does, with ZMARSHALLINGERROR.

## 12. Staged teardown

### 12.1 Stages

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
#[non_exhaustive]
pub enum Cause { ConnectFailed, Io, Eof, SocketCreate, Tls, TlsHandshakeTimeout, RecvTimeout, XidMismatch,
                 ProtocolError, SessionExpired, AuthFailed, RwServerFound, SaslTeardown, ForcedClose }
impl Cause {
    /// SessionExpired, AuthFailed and SaslTeardown end the session; every other cause is recoverable.
    pub const fn is_terminal(self) -> bool;
}
```

`Cause` is public. Drivers read the cause of the most recent teardown with `last_teardown_cause()`. zk-client maps it to its public `DisconnectCause` for `SessionInfo::last_error` (04 §8.2). The drop-in does not use it.

A teardown is a continuation that runs these stages in order. It suspends after any barrier output (§5.3).

| Stage | Action | C |
|---|---|---|
| T0 | the trigger's ERROR `Log` in `handle_socket_error_msg` form (`"Socket %s zk retcode=%d, errno=%d(%s): %s"`, with the current server, the rc, the errno from the input and the site text). For `TlsResource{at: ContextNew}` the plain LOG_ERROR "error creating ssl context" (2867) comes first. RwServerFound logs its INFO line instead. AuthFailed emits no T0 line: C calls `handle_error`, not `handle_socket_error_msg` (zookeeper.c:3594-3597), and the "Authentication scheme %s failed. Connection closed." line was already emitted in §8 step 4. SaslTeardown (§7.4) and ForcedClose (§12.3) emit no T0 line | 2134-2147 |
| T1 | yield `CloseTransport`; advance the SASL `gen`, so a late result for this connection is stale; keep the mechanism session for the next `Start` or `destroy` (§7.4; no `Dispose`, as `cleanup` disposes nothing); reset rx and pins; drop the SASL negotiation. A forced close runs this stage at its trigger, and takes its T3 snapshot there (§12.3) | `close_zsock` (2103) |
| T2 | if `state < 0`: `Session{state}`; else if connected (3/5; for a forced close, connected at the trigger): `Session{Connecting}`. Each is preceded by its DEBUG Log. Barrier iff Inline | 2104-2111; st drains here (3264-3266) |
| T3 | Take `tx` and the FIFO **as they stand when this stage runs** (one snapshot, as C swaps `sent_requests` under its lock); a forced close uses the snapshot its trigger took (§12.3). Fail each snapshot entry in order with `rc_for(cause, entry)`: Direct → `Completion{Direct}` (a barrier; consecutive Direct results share one, §5.3), Queued → `Completion{Queued}`. Registrations are dropped. Then `AuthLockpoint` (§5.4), then `Auth{all pending, rc, barrier: legacy}` if any. A request submitted while T3 is suspended is not in the snapshot and survives, as a submit that C blocks until `cleanup_bufs` ends | `cleanup_bufs` / `free_completions` (2015-2091) |
| T4 | DEBUG "Previous connection=%s delay=%d" Log; if `state >= 0`, `state = 0` (a forced close keeps 999, §12.3); `DrainPoint` | 2114-2121 |
| T5 | `handle_error` causes only: `delay = at_end(addrs) \|\| addrs.is_empty()` (proto P12); `cur = addrs.peek()`, and the cursor does not move (§9.2) | 2124-2132 |
| T6 | cause continuation (RwServerFound: nothing further; expiry: nothing) | — |

There is no closing short-circuit. C's `cleanup` does not check `close_requested`, so a teardown that runs after `begin_close` behaves as in C. In that case the FIFO is already empty, and in st an AUTH_FAILED session event queued after a close from a callback is still delivered by the same drain. The serialized foreign-thread close order in mt is one of C's possible orders, not a deviation.

| Cause | rc for pending | handle_error (T5) | C ref |
|---|---|---|---|
| ConnectFailed, Io, Eof, ProtocolError | ZCONNECTIONLOSS | yes | 2706-2711, 3079-3110; proto P6 |
| SocketCreate | ZSYSTEMERROR | yes | 2681-2689 |
| Tls (TlsResource at ContextNew or ConnectionNew, TlsHandshake) | ZSSLCONNECTIONERROR | yes | 2866-2869, 2924-2928, 2957-2963 |
| RecvTimeout, TlsHandshakeTimeout | ZOPERATIONTIMEOUT | yes | 2749-2764 |
| XidMismatch | ZRUNTIMEINCONSISTENCY | yes | 3613-3626 |
| SessionExpired | ZSESSIONEXPIRED | yes | 3166-3173 |
| AuthFailed | ZAUTHFAILED | yes | 3594-3597 |
| SaslTeardown | ZAUTHFAILED | yes | 3594-3597, the digest path it follows (DV-FIX-3, §7.4) |
| RwServerFound | ZCONNECTIONLOSS (§12.2) | **no** (`cleanup`, 2797) | 2790-2797 |

The table is `disconnect_rc = PerCause` (LEGACY_C, ST-06). Under `disconnect_rc = ConnectionLoss` (NATIVE), only the recoverable causes collapse to ZCONNECTIONLOSS. The terminal outcomes keep their codes: SessionExpired gives ZSESSIONEXPIRED, AuthFailed and SaslTeardown give ZAUTHFAILED, and close (`begin_close`, `destroy`, `abandon`; not a `Cause`) gives ZCLOSING.

`TlsConfig` is not a teardown (ST-17). A forced close is a teardown whose stages after T1 run later than its trigger, over work taken at the trigger (§12.3).

### 12.2 RO→RW switch (`Compat::rw_switch_rc = ConnectionLoss`)

Both profiles (DV-FIX-9, ST-08). C's `cleanup(zh, ZOK)` fakes an `err = 0` reply for every pending entry (zookeeper.c:2790-2797, 2032-2058). That gives a false ZOK for writes that never ran, uninitialized structs for the data-bearing kinds, a crash in `sub_string` with a chroot, and an assert for multi. `RwServerFound` has one rc instead:

- every pending result, of every kind, is `Origin::Teardown` with `rc = ZCONNECTIONLOSS` and `reply: None`, after the CONNECTING event;
- a sync waiter gets ZCONNECTIONLOSS with its outputs untouched;
- auth tokens get ZCONNECTIONLOSS;
- a multi gets ZCONNECTIONLOSS with `cleanup_failed_multi` semantics.

### 12.3 Forced close (`Compat::forced_close = Teardown`)

Both profiles (DV-FIX-8, ST-13). Triggers: rebalance in `apply_resolution` with an open transport (1222-1226), and the st submit-flush failure (`handle_forced_close`; `nonblocking_send`, 4153-4161). The mt waker cannot fail (DSP-10), so mt has no submit-path trigger. C closes the socket, sets state 999 and does nothing else, so its queues survive onto the next connection: unsent frames are replayed, a partly sent frame resumes mid-frame, stale in-flight entries cause a later ZRUNTIMEINCONSISTENCY or ZOPERATIONTIMEOUT, and in mt the close races the IO thread. Here the trigger keeps what the caller of the API sees in C and takes the work pending on the closed connection as one snapshot, and the rest of a normal teardown follows on the IO owner for that snapshot. The deviation covers only that work: a request submitted after the trigger stays queued whole for the next connection, as in legacy and as after a normal teardown. The result does not depend on IO-thread timing, because the driver lock orders every submit against the trigger's core call.

**At the trigger.** In the same core call, and therefore synchronously inside the API call:
1. record whether the state is connected (3/5), for T2;
2. `state = 999`;
3. phase Idle;
4. T1: flag `CloseTransport` and advance the SASL `gen`; no `Sasl(Dispose)` is yielded, so the call's outbox gets no SASL item and the mechanism session stays until the next `Start` or `destroy` (§7.4). Only the IO owner closes the fd. In st the API caller is the IO owner. In mt the IO thread is woken;
5. rx reset, pins cleared, and the SASL negotiation dropped;
6. take the snapshot, which also marks the remaining stages pending: `tx` and the FIFO move out whole, and every pending auth token moves out of the auth list in list order. The auth entries keep their scheme and credential, so the next connection resends them (§7.5), as `get_auth_completions` clears only the completion (559-572).

```rust
struct ForcedSnapshot<T: Tokens> {
    connected: bool,             // state was 3 or 5 at the trigger (T2)
    tx: VecDeque<OutFrame>,      // not sent again, partly sent head included; dropped by T3 or by a close (sensitive frames zeroed)
    fifo: VecDeque<Pending<T>>,  // failed by T3 or by a close
    auth: Vec<T::Auth>,          // tokens in list order; the entries stay in the auth list
}
forced: Option<ForcedSnapshot<T>>;   // Some: remaining stages pending
```

The trigger emits no `Session`, `Completion`, `Auth` or `AuthLockpoint`, so no callback runs inside an API call, and an API call's outbox holds LOG items only. The API call returns its own rc (03 §6.5, 05 §17). A trigger with no open transport does nothing.

**The remaining stages.** `run_pending_teardown(now)` runs them as a `Cause::ForcedClose` teardown, on the IO owner, in the next driving call: the driver calls it at the start of every `interest_step` and `process_step`, and after `handle_resolved` in `interest_step`, so a rebalance found in the IO owner's own interest step runs them in that call. If a continuation is suspended, they start when it ends.
- There is no T0 line, because C logs nothing at either site.
- T2: `Session{Connecting}` with its DEBUG line if the state was connected at the trigger, otherwise no event.
- T3 emits only the snapshot: its FIFO entries fail in order with ZCONNECTIONLOSS (Direct entries as barrier runs, §5.3), its frames are dropped, then `AuthLockpoint` and `Auth{snapshot tokens, ZCONNECTIONLOSS}` if any. The stage does not read `tx`, the FIFO or the auth list, so later work stays where it is. None of the snapshot is replayed, and its registrations are dropped as in any teardown.
- T4: the state stays 999, which it keeps until the next attempt changes it, as in C (ST-01).
- There is no T5: no delay is set, the cursor does not move and `cur` stays, so `zoo_get_current_server` reports the closed connection's server until the next connect, as in C (§9.2). The next connect selects its server through §9.2 with `reconfig` as `apply_resolution` left it.

In mt the event and the async results therefore go to the dispatch thread, and the sync and auth results run on the IO thread, as in every other teardown. In st they all run inside the next `zookeeper_interest` or `zookeeper_process` call (03 §6.5, §10.11).

**A request submitted after the trigger.** Its frame goes to the back of the emptied `tx` and its entry to the back of the emptied FIFO. No partly sent frame can survive, because nothing is sent while no transport exists (§6.3) and a late `handle_transmitted` is ignored (§4.2).
- **st.** The `zoo_a*` call submits, its flush pass finds nothing it may send and cannot fail, and it returns its own rc with no second trigger. C's flush sends nothing in state 999 and cannot trigger a second close: its loop needs a connected state or a SASL negotiation in progress (5160), and with sock -1 `nonblocking_send` has nothing to close (4156). This holds for a call from a callback that the remaining stages run, unlike a normal teardown, whose T3 takes what stands when it runs (§5.3).
- **mt.** A submit from any thread takes the same path, before or after the IO thread has run the stages. A sync waiter on such a request stays blocked until its reply, or until a later teardown or close completes it.
- **Auth.** `add_auth` in state 999 only records the entry (§8; C: 5340-5346). Its token stays on the entry and is completed by an AUTH reply on the next connection.
- **Order on the next connection.** The wire order is Connect, the SASL frames if a negotiation runs, the auth frames, SetWatches, and then the queued requests in submission order. Priority inserts go ahead of these unstarted frames (§6.3), and the phase gate holds the requests back until Established (§7.5; C: 2997-2999, 5160-5173). A watch carried by such a request is armed by its reply and is not in that SetWatches.
- **A failed next attempt.** That attempt's teardown fails the request like any queued request (ST-07), as `cleanup_bufs` does in C.

**A sync waiter whose request is in the snapshot.** The waiter stays blocked from the trigger until T3 emits its `Completion{Direct}` with ZCONNECTIONLOSS and `reply: None`. The IO thread signals it at the barrier, and its outputs stay untouched. A close before T3 starts gives it ZCLOSING instead. Snapshot tokens count as never emitted in `into_leftovers`, so a waiter cannot hang on one. st has no sync waiters (2041).

**A close before T3 starts.** `begin_close`, `destroy` and `abandon` take the snapshot. If the stages have not started, they never run and no CONNECTING event is emitted, because a close emits no session event. If the close comes from the callback of T2, T3 finds an empty snapshot when the teardown resumes. The close's own stages fail both the snapshot and the later work with ZCLOSING: the snapshot's FIFO entries first, then the later entries, which is submission order (§13); `AuthLockpoint`; then `Auth{ZCLOSING}` with the snapshot tokens first and the tokens of later entries behind them, which is list order. The snapshot's frames are dropped. Later frames stay in `tx` as CLS-02 keeps them, with nothing to carry them, because `queue_close_op` queues nothing in state 999, and `destroy` drops them. Under `close_mode = Drain`, `begin_close` refuses new submits and keeps the snapshot for `destroy`, `run_pending_teardown` does nothing after `begin_close`, `close_step` reports completion at once, and `destroy` fails both with ZCLOSING. Once T3 has started, it finishes its snapshot with ZCONNECTIONLOSS and the close fails only the later work, as for any teardown.

**A second trigger before the first has run.** The first trigger left no open transport, so the second does nothing: the snapshot and its `connected` value stay as they are, and requests submitted between the two triggers stay queued. A second rebalance still commits its list and `reconfig` (§9.3). A new transport cannot appear before the stages have run, because `run_pending_teardown` comes before `poll_action` in every driving call. At most one snapshot therefore exists.

**A forced close while another teardown is pending.** Every teardown runs T1 before its first barrier, so a suspended teardown has no open transport and a trigger during it does nothing. That teardown finishes with its own cause and its own T3 snapshot, and `reconfig` applies to the next connect. This includes the remaining stages of an earlier forced close. The only suspended continuation that can still start a teardown with the transport open is a failed AUTH reply (§8):
- A trigger during its `Auth` barrier (step 5) replaces -113 with 999, so step 6 starts no teardown, as C's `is_unrecoverable` test finds nothing to do (3594-3598). The handle stays recoverable.
- A trigger during its `AuthLockpoint` (step 1, mt only) condemns the connection that the reply came from, so steps 2-6 do not run, as for the frames that the rx reset dropped. The auth entry is resent on the next connection, and the server answers it there.

After the trigger no other input can start a teardown, because each needs a transport. A suspended continuation of any other kind ends normally, and the stages then run.

## 13. Close

**`close_mode = LegacyFailPending` (LEGACY_C):**
- **`begin_close(now)`** (C refs > 1 path, 4007-4017):
  - set `closing`;
  - fail every FIFO entry with **ZCLOSING** in order (Direct entries as barrier runs, §5.3; Queued entries to the FIFO), the entries of a forced-close snapshot whose T3 has not started first (§12.3);
  - `AuthLockpoint`, then `Auth{ZCLOSING, barrier: false}` if any;
  - `DrainPoint`;
  - no session event;
  - `tx` kept (CLS-02): unsent requests already failed with ZCLOSING are still flushed.

  Afterwards, replies yield ZINVALIDSTATE and are dropped. Watch events are still emitted. Teardowns behave as in §12.
- **`queue_close_op()`:** if connected, append a `Close` frame (normal xid, op -11, no completion) and return true. The driver flushes `tx` for at most `CLOSE_FLUSH_MS = 3000`, then polls for readability for `CLOSE_WAIT_MS = 1500` without reading (4044-4047). Flush rcs are the driver's: ZOK, ZOPERATIONTIMEOUT, ZCONNECTIONLOSS, ZSYSTEMERROR (CLS-06).
- **`destroy(now)`** (`destroy` → `cleanup_bufs(ZCLOSING)`, 676-713):
  - set `closing`;
  - fail anything left with ZCLOSING;
  - `AuthLockpoint`, then `Auth{ZCLOSING}`;
  - `DrainPoint`;
  - then `poll_action` yields `CloseTransport` if a transport exists, and after it `Sasl(Dispose)` if a mechanism session exists (`mech_gen` is set, whether or not a transport is open). This is legacy destroy's order: `close_zsock` (zookeeper.c:719-723), then `zoo_sasl_client_destroy` (744-749).

  This covers st `refs == 1`, where `begin_close` never ran: the output order is fakes queued, auth invoked, then drain, as in CLS-06. In mt the driver discards FIFO items instead of invoking them (CLS-04/12).

**`close_mode = Drain` (NATIVE, hook A6):**
- `begin_close(now)` refuses new submits (ZCLOSING) but keeps the FIFO. It records the close deadline `close_deadline = now + close_timeout_ms` (hook A15, §3.3). A second `begin_close` keeps the first deadline.
- `queue_close_op` appends CLOSE_OP behind the queued frames (04 §13 `Client::close`) and records the CLOSE_OP xid. Under `Drain`, a reply with that xid completes the close and returns ZOK; it does not take the ZINVALIDSTATE row of §7.1.
- `close_step(now)` reports progress as `CloseProgress`. The close completes on the CLOSE_OP reply or when `now >= close_deadline`, whichever comes first. `close_step` also reports completion at once when `queue_close_op` returned false, and when a teardown ends the transport during the drain. The driver derives the `CloseFuture` result of 04 §13 from these cases: the teardown's error after a teardown, ZOPERATIONTIMEOUT when the close completes at the deadline, otherwise ZOK. While the close runs, `finish_interest` caps `timeout_ms` at `close_deadline - now`, so the driver wakes at the deadline. The remaining close budget (for the TLS close_notify below) is `close_deadline - now`. When `close_step` reports completion, the driver calls `destroy(now)`, which fails leftovers with ZCLOSING, emits `WatchTerminated{Closed}`, and yields `CloseTransport` and then `Sasl(Dispose)`.

**`abandon(now)` (native, hook A7):** close the transport without CLOSE_OP, fail pending work with ZCLOSING, and terminate watchers with `Closed`.

**TLS close_notify on a graceful close (both profiles).** On a graceful close (a close frame was queued and the close flush put every queued byte on the wire), a driver with a TLS transport calls `send_close_notify()` at the end of the close flush and wait, before `destroy` (03 §5.10 step 4, §4.3.5). For a `Drain` close, the end of the flush and wait is the CLOSE_OP reply or the deadline. The driver flushes the alert without blocking within the remaining close budget, and never waits for the peer's close_notify (03; 06). The later `CloseTransport` from `destroy` then closes the socket. A `CloseTransport` from a teardown, a forced close or `abandon` sends no close_notify, and the RW probe never sends one. The fatal alert after a TLS error that rustls detects is a driver rule too, the same in both profiles: one non-blocking send of the alert that rustls queued, dropped when earlier ciphertext is still waiting in the driver's `ct_out`, as OpenSSL writes it inside `SSL_connect` or `SSL_read` in legacy (03 §4.3.5). The core has no TLS state for this: the driver owns the close flush and knows whether it put every queued byte on the wire. C never sends close_notify, because `close_zsock` frees the `SSL` object without `SSL_shutdown` (zookeeper.c:648-670). The extra alert record is a wire-only difference that applications cannot observe (07 P6); the ledger records it in a TLS row.

**`into_leftovers()`** returns every token that was never emitted, those of a forced-close snapshot included. After `destroy` it is empty, apart from un-popped outputs.

## 16. Deviations owned by this document

Every item below applies in every profile, `LEGACY_C` included, and is FIX-UB-ONLY: it removes UB, a crash, memory or stream corruption, or a deadlock-class liveness failure that no correct application can depend on. P12's T/60 and P19's stall are the `LEGACY_C` values; NATIVE uses `Backoff::Deadline` and `negative_frame_len = Disconnect` (§14.1). The P-numbers are this section's aliases, cited as "proto P3"..."proto P23" outside this table; the numbers are stable labels and are not consecutive; they are distinct from the ledger classification principles, which this document cites as "07 P1"..."07 P8" (07 §1). The ledger IDs are canonical (07; registers in 00 §5). Items marked **00 §5.2** are on the 00 §5.2 list, "Acknowledged behavior differences (FIX-UB-ONLY)": FIX-UB-ONLY items that a careful application could notice, which the release notes list.

DV-FIX-9 removes C's uninitialized structs, crash and assert on RO→RW. The libc PRNG reseed and draws are reproduced (SRV-04), because an unseeded application that happens to rely on the reseed would otherwise silently get a fixed libc sequence. Session events after a close keep C's order.

## Decisions

| Decision | Rationale | Alternatives |
|---|---|---|
| Pull/outbox model. The core emits one ordered Output stream that also carries Log records. The caller of each core call pumps that call's outputs. Application code runs only from C frames after the Rust call returns, on every thread; the mt IO and dispatch loops are C loops over Rust step functions. | C++ exceptions and longjmp from any callback pass through C frames only, as in legacy. Log lines keep their thread and their order relative to callbacks. No lock is held across application code, which removes C's lock-held-callback deadlocks. | Push model with Rust calling vtable trampolines, or a run_items entry with Rust frames below callbacks on library threads. Rejected: foreign unwind into Rust, aborts where C propagates exceptions, and an extra deviation. |
| Paths are stripped where they are decoded (CC-21, 00 §4), but the log lines that C prints at delivery (the sub_string mismatch ERROR, "Calling a watcher for node", "Calling COMPLETION_*", "Processing sync_completion") travel with the Watch, Session or Completion output as delivery_logs and are emitted on the delivering thread just before the callbacks. Under LEGACY_C every node event yields a Watch output, empty watcher lists included. | C runs sub_string and that DEBUG line on the mt dispatch thread (or inline in st), also for empty lists (zk_hashtable.c:286-293; zookeeper.c:3476). Emitting them at decode would change the thread id in the mt log prefix and drop the lines for empty lists, which 07 P8 forbids. | Strip and log at decode (unlisted visible log changes). Strip at delivery in the shim (a second strip implementation outside the core). |
| Teardown is a staged continuation with barrier/resume. Barriers: Direct completions, Auth with a continuation, AuthLockpoint, and Session outputs under Inline delivery (st). Pending-request rcs are computed when the stage runs; T3 fails a snapshot of the FIFO. | C runs these callbacks inline and then continues. A callback that closes or submits changes what follows: ZCLOSING instead of ZCONNECTIONLOSS, new requests failed by cleanup_bufs, the AUTH_FAILED event after a close from an auth callback. A Direct barrier signals each sync waiter before later frames are processed, as legacy does. | Eager teardown with only a DrainPoint marker. Rejected: wrong rc when a session callback closes the handle in st. A sync slot filled under the core lock. Rejected: a library thread would write another thread's result state under a Rust lock. |
| zoo_lock_auth parity through AuthLockpoint barriers at the four legacy sites, executed by C as lock; unlock with no Rust frame or lock. | Reproduces the legacy stall when an application holds the auth lock (LA-01) while keeping the lock order auth → core and never holding the auth lock across application code. | A shim-only lock that the IO side never takes (visible change). A vtable lock called by Rust around collection (lock-order inversion). |
| One Compat struct, defined here, with consts LEGACY_C and NATIVE. The ledger owns the values. Per-driver settings are DriverMode{interest, session_delivery} only. | LEGACY_C differs from C only through the registered behavior fixes and for UB, crashes, corruption and deadlocks. One table makes the shipped behavior auditable, keeps the ledger consistent with the code, and gives a test matrix of the two profiles. | Per-document Compat variants, or per-flavor Compat. |
| LEGACY_C values for the fixes: server cursor SingleAdvance; endpoints IpAndPort; SASL failure Teardown; SetWatches Some(128 KiB); chroot LegacyConcatNoEscape; forced close Teardown; RO->RW ConnectionLoss. Close stays LegacyFailPending. | Each fix corrects behavior that harms correct applications: a two-server client that settles on one server, ignored port changes, watchers that never learn of a SASL failure, watch sets that exceed jute.maxbuffer, a chroot escape, a delayed ZRUNTIMEINCONSISTENCY or timeout after migration, and a false ZOK for writes that never ran. Each is a registered deviation with a release note, and the legacy core stays available as the oracle and as a supported build. | Reproducing C's outcome for any of these in the Rust core (keeps the defect in the shipped drop-in). |
| T5 sets `cur` to a peek of the next address without moving the cursor, and the connect advances once. | The cursor advances once per failure, and `cur` takes the address that C's `handle_error` takes from its cursor, so the report after a failure keeps C's meaning (the address at the cursor) and `found_current` keeps C's input. The values differ from C's only as far as the cursor sequence of DV-FIX-1 differs. | Leaving `cur` on the failed server (a visible accessor change and a different rebalance input). |
| A forced close sets state 999, closes the transport and takes tx, the FIFO and the auth tokens as one snapshot at the trigger, and the rest of the teardown runs on the IO owner in its next driving call over that snapshot alone. The API call's outbox holds LOG items only. A request submitted after the trigger stays queued for the next connection. | C runs no callback inside zoo_a* or zoo_set_servers, so an application may hold a lock around those calls that its callbacks also take. Running the stages on the IO owner gives every result the thread of any other teardown, and zoo_state still reads 999 when the call returns. The snapshot keeps the deviation to work pending when the connection closed and makes the outcome of a later request independent of IO-thread timing, and that request behaves as in legacy. No partly sent frame survives, because nothing is sent while no transport exists. | Running the stages in the API call's own drain (callbacks inside zoo_a* on the application thread, and auth completions on the wrong thread in mt). Keeping C's forced close without cleanup (delayed errors, replay onto a new connection). Failing what stands when T3 runs (the fate of a later request would depend on when the IO thread runs, and a request legacy would send would fail). |
| After a SASL failure the driving call returns the SASL rc, and all pending work gets ZAUTHFAILED. | The return value of the call stays what C returns and keeps the cause of the failure; the pending work and the event follow the digest path. | ZAUTHFAILED from the driving call too (hides a mechanism error's ZSYSTEMERROR, and changes one more visible value). |
| Session-event fan-out uses a safe-Rust port of hashtable.c and zk_hashtable.c under legacy, with the platform's C char signedness in Config and the default watcher read through DefaultWatcher at queue time. | Callback order is app-observable and deterministic in C for a given registration history. The port is small, safe and differential-testable against the compiled C. The default watcher's source of truth is the shim's pair cell. | BTreeMap order documented as unspecified. Rejected as a visible non-UB change. A core copy of the default watcher. Rejected: it can diverge from the C pair cell. |
| Rebalance change detection is a port of addrvec_eq (same length, every old address contained in new), called old first. | It is one-way, so lists with duplicate addresses can compare equal where a multiset compare would not; a multiset compare would then set reconfig, draw drand48 and possibly force-close where C does none of these (zookeeper.c:1146; addrvec.c:256-271). | A multiset compare (visible difference with duplicate addresses). |
| The Rng trait exposes on_resolution/random/drand48. The drop-in's libc reseed is the Blocking rng_reseed leaf, run by the driver in its unlocked resolve step; ShimRng's on_resolution is empty. The libc call order on that thread is unchanged. | Reseed inside the core under the lock (violates 00 §3 K4). A private per-handle PRNG for the drop-in, or skipping only the reseed (an unseeded application that happens to rely on the reseed would silently get a fixed libc sequence). |
| TLS: rustls in zk-driver for both profiles; the core owns the TLS phases, deadlines, rcs and log lines, and passes Compat::tls_verify (LegacyChainOnly under LEGACY_C, WebPki under NATIVE) in Connect and ProbeRw. Keeping C's tv in the TCP phase changes only the spin case. Calling new_conn before handle_tcp_connected follows C, which builds the context, loads the trust and identity files and creates the connection before the handshake starts (zookeeper.c:2865-2928). Keeping phases, sites and rcs in the core leaves the TLS engine with no protocol logic. C returns this rc at zookeeper.c:2717-2720 and 3093-3094, and the SSL_CTX_new site is at 2865-2871. | OpenSSL in shim C over memory BIOs (keeps the OpenSSL closure and C TLS code; 00 §3 K9). A TLS policy in DriverMode (flavor must not change Compat semantics). tv = T/3 for the whole TCP phase (unlisted change in the (T/3, 2T/3) window). Deadline from attempt start (changes failover timing). ZBADARGUMENTS for config errors (not what C returns to the caller). |

Tokens are SecretBytes. Lines that need live Cyrus results are logged by the glue in the drop-in and by the core only for native mechanisms. | One home for the ZooKeeper-level quirks, shared by both profiles. Cyrus and getpass callbacks are application code and must run in C frames. The generation crosses the C ABI as uint32_t. The generation and the ordering remove the stale-result and cross-thread dispose races without a lock in C (06 §4.7.3-4.7.4). Legacy dispose timing keeps any Cyrus callback that dispose triggers at the legacy point, so SAS-13 is RE (07). One owner per log line avoids duplicate or empty lines. | Quirks in the shim next to Cyrus (duplicated for native). Rust calling Cyrus through a vtable (Rust frames below application callbacks). A u64 generation (does not match the ABI). |
