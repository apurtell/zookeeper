# Overview: Rust ZooKeeper client and C drop-in shim

## 1. Executive summary

The design replaces the internals of `libzookeeper_mt` and `libzookeeper_st` with a sans-IO Rust protocol core. A C shim in front of the core keeps every application-visible contract, apart from the registered deviations of §5.1. The shim keeps only the C work that cannot move into Rust. Each part is in C for one of four reasons: it owns memory that the application sees (the `zhandle_t`, the sync record, the per-thread endpoint buffer, the SASL callback block, the log buffers); it calls application code, which the callback-frame rule (idea 2 below) allows only from a C frame; it is a variadic or ABI-fixed exported entry, or data whose layout the ABI fixes; or it uses Cyrus SASL types. 05 §1 inventories the shim per file with its role, reason and estimated size. The hand-written shim is about 5,050 lines of C (05 §1), of which about 1,120 are the Cyrus glue. The legacy C it replaces is about 9,060 lines (`zookeeper.c`, `zk_sasl.c`, `mt_adaptor.c`, `zk_hashtable.c`, `hashtable/hashtable.c`, `hashtable/hashtable_itr.c`, `addrvec.c`, `zk_log.c`, `st_adaptor.c`, `winport.c` at 60da6eb50; 05 §1). The protocol, session, watcher, server-list, TLS and I/O logic moves to Rust. Result materialization (the legacy `String_vector`, `ACL_vector`, `Stat`, string, data and multi result layouts, and the `Id`/`ACL` contents) and the sync copy-out into caller buffers are pure data shaping, so they are in zk-ffi's audited raw module (K11, K12). C keeps their delivery: the callback invocation and the legacy post-callback deallocation order. The verbatim `recordio.c`, the generated jute C and the generated headers are not counted. The shim is therefore smaller than the code it replaces, but it is not tiny: the largest parts are the exported entry points, the sync wrappers and the SASL glue. The application-visible contracts stay exactly as in legacy, apart from the registered deviations (§5.1):

- installed headers (byte-identical);
- the 211/188 exported symbols (TLS and SASL builds; 01 §5), including the 36 data objects;
- SONAME `.so.2`, struct layouts, return codes and errno;
- callback threads and ordering, memory ownership, the logging format and the pinned `func@line` sites;
- close semantics.

Native Rust applications get a separate typed, futures-based API, the package `apache-zookeeper`, with a recipes crate `apache-zookeeper-recipes` on top of it (K26). It runs on the same core with a different policy profile. The native crates ship in the ASF source release only and are not published to crates.io (K25).

The design rests on four ideas.

1. **Sans-IO core with one policy object.** `zk-proto` holds every protocol decision: xids, FIFO, timers, teardown, host-list rebalancing, the watcher tables (including a bit-exact port of `hashtable.c`), auth and SASL sequencing, and legacy validation order. It has no sockets, threads or clocks. One `Compat` struct selects the legacy C profile, which reproduces C apart from the registered behavior fixes (§5.1), or the native one, including the TLS verifier policy (`tls_verify`). Per-driver settings are kept separate in `DriverMode`.
2. **Callback-frame rule.** No application code ever runs with a Rust frame on the stack, on any thread. Application code means completions, watchers, auth completions, log callbacks and Cyrus callbacks. Every `zkrs_*` call that can produce application-reaching work returns an ordered outbox, and C drains it after Rust returns. The mt IO and dispatch loops are themselves C loops over Rust step functions. Where legacy continues work that a callback could affect, Rust stops at a barrier and resumes afterwards. As a result, C++ exceptions, `longjmp` and re-entrancy behave exactly as in legacy, and no foreign unwind can reach Rust.
3. **Unsafe confined by construction.**
   - Every shipped Rust crate except `zk-ffi` is `#![forbid(unsafe_code)]` (the test-only `zk-xcheck`, `zk-ffi-layout` and fuzz targets are never shipped, 01 §3.2).
   - `zk-ffi` holds C pointers only as integers and reads and writes C memory only in one audited module, `abi::raw`.
   - All application-visible memory is allocated with libc `malloc`/`calloc` and freed with libc `free`, from the one CRT of the library. The shim allocates the objects it owns. `abi::raw` allocates the legacy result layouts with the same `malloc`-or-`calloc` choice and the same sizes per object as legacy, so the application's `free()`, `deallocate_*` and the generated jute deallocators work unchanged (K11).
   - TLS is rustls inside `zk-driver` for both profiles. OpenSSL is not used anywhere.
   - Cyrus SASL stays in C, because its public API is bound to Cyrus types. It is confined to two isolated, hardened shim files behind a bounded byte-view interface (§2.6).
   - The drop-in dependency closure is pinned: `rustix` (libc backend) and its closure, `zeroize`, and the rustls/crypto closure (K14). The audited third-party crates contain `unsafe` (and, for the crypto provider, C and assembly). Our crates contain no unsafe operation outside `zk-ffi`'s audited `abi::raw`. This is the meaning of "core crates forbid unsafe" (K22).
4. **One pre-linked object per flavor.** The shim, `recordio.c`, generated jute C and the Rust staticlib are joined with `ld -r` and localized to the golden symbol set. No Rust, `zkrs_*` or crypto-provider symbol leaks from the `.so` or the `.a` (except on MSVC).

**Deviations.** No ZooKeeper protocol or API semantics change except the DV-ABI-2 stubs of undeclared SASL internals and the nine behavior fixes of the Rust core, DV-FIX-1..9: the single cursor advance, endpoint equality by IP and port, SASL failure as a full teardown, batched SetWatches, the absolute config node for sync getconfig, the `zerror(-15)` text, chroot escape rejection, forced close as a full teardown, and uniform ZCONNECTIONLOSS on the RO→RW switch. Every other runtime difference removes undefined behavior, a crash, corruption or a deadlock. Six DV-TLS deviations follow from using rustls where legacy uses OpenSSL: DV-TLS-1/2/3/5 (protocol floor, policy source, algorithm acceptance, key formats) apply to `zookeeper_init_ssl` handles, DV-TLS-4 (linkage) applies to every TLS-enabled build, and DV-TLS-6 (key formats) applies to the FIPS build only. These, and a short list of link, ABI, build and failure-path differences, are registered deviations with release-note text (§5.1). The nine fixes are always on in the Rust-core drop-in, and no build option selects them (§5.4). The differential [diff] tier runs the one shipped drop-in against the pinned legacy oracle: every case that a fix touches is a DEV test under its DV-FIX row, and all other cases stay EXACT.

**Rollout.** Milestones M0–M5 deliver the Rust core, and the recipes crate follows M5 as milestone M5R (08 §15). The legacy core stays buildable and maintained, and its pinned reference build (08 §4.1) is the differential oracle that CI compares the Rust core against. configure and CMake build what the host can build and honor what the user requires: the Rust core is opt-in before M5, and from M5 the default `auto` builds it wherever rustc and cargo ≥ 1.85 and its crates are available and builds the legacy core elsewhere, with a notice; an explicit request fails clearly when it cannot be met (§2.7). Under Maven the Rust module stays opt-in. `--with-rust-client=no` / `-DWITH_RUST_CLIENT=OFF` is a supported configuration with no deprecation warning, and `-Pfull-build` alone never needs cargo (01 §6.5). If the M4 Windows spike fails, Windows ships on the legacy core for that release (DV-BLD-7), and the Rust core follows on Windows in the first release whose Windows build passes the M4 exit criteria of 08 §15.3 (CC-33).

**Structure and build.**
- The drivers live in their own `zk-driver` crate, separate from `zk-client`. Native-only code therefore cannot be linked into the C libraries.
- The mt library-thread loops are C loops over Rust step functions. No Rust thread runs in the drop-in.
- TLS is rustls in `zk-driver` for the drop-in and for the native API. The shim has no TLS code and the host vtable has no TLS entries.
- SASL is Cyrus in C. Isolation, lifetime, serialization and coding rules minimize unsafe memory operations. A per-session secret trampoline removes the shared-secret data race (DAT-13 FU).
- The Rust workspace lives in `zookeeper-client/zookeeper-client-rust/`. Maven drives its build as it drives the C client (§2.7; 01 §13). Rust jute code is generated by a Java `RustGenerator` in `zookeeper-jute` into `crates/zk-jute/src/generated/zookeeper_jute.rs` (01 §8).
- The third-party crates `rustix`, `zeroize`, `rustls`, `ring` (or `aws-lc-rs`) and the RustCrypto key-decoding crates contain `unsafe`. They form an audited, pinned closure (K14).
- Three TLS provider builds exist: `ring` (the default), `aws-lc-rs` and `aws-lc-rs-fips` (K24).
- A CI advisory watch reports advisories against the crates of every shipped closure, and distributions can build against their own crate packages in the system-crates mode (K23, §2.8).
- Builds, release builds included, fetch crates or read a vendor directory and check them against `Cargo.lock`. Nothing is vendored into git or into the source release (§2.8).

### 2.2 Thread model, libzookeeper_mt

| Thread | Created by | Loop | What runs there (all from C frames) |
|---|---|---|---|
| App threads | application | — | `zoo_a*` (submit, plus the outbox of app-thread log lines). `zoo_add_auth` (holds `auth_lock` around submit). Sync wrappers (calloc a record, call the exported `zoo_aX`, wait, then copy out into the caller's buffers through zk-ffi's raw writers). `zookeeper_init_ssl`: C copies the cert string, splits it with `strtok_r`, passes four borrowed strings in `zkrs_init_args`, then zeroes and frees the copy before init returns; no TLS work runs here. `zookeeper_close` from a foreign thread: ZCLOSING sync and auth completions drained here, then THREAD JOIN items (each a barrier, CC-3), then the final close (CLOSE_OP flush, destroy callbacks, transport close, then the SASL DISPOSE item if a Cyrus session exists, in the legacy destroy order of zookeeper.c:719-749), then RELEASE. |
| IO thread | `pthread_create(&t, NULL, …)` in `zks_threads.c` | `zkrs_io_step` → `zks_drain` → `zkrs_resume` while MORE | One `do_io` iteration in Rust: interest; then `poll([waker, sock])` with no lock and no app code; then process. Getaddrinfo goes through a Blocking leaf with no Rust lock held. Pending LOG items are drained in C before every Blocking call, before the TLS file reads and before any wait in poll, the close flush or close wait, or the RW probe (CC-36). TLS runs in Rust on this thread: the per-attempt TLS context build (CA file, default verify paths, client cert and key file reads, key decryption) runs with no core lock held, like resolution; the handshake and record processing run in `RustlsConn`, and the driver sends the ciphertext with its own `send`. Drained in C on this thread: sync results (barrier: zk-ffi's raw writers build the result in the heap record, then C signals the waiter), auth completions (after an AUTH_LOCKPOINT barrier), Cyrus SASL items (START, STEP, DISPOSE through `zks_sasl_*`), IO-thread log lines. |
| Dispatch thread | `pthread_create(&t, NULL, …)` | `zkrs_wait_dispatch` (blocks on the FIFO) → `zks_drain` | Async completions, node watch events and session events, in proto stream order. "Calling COMPLETION_*" DEBUG lines are emitted here, from the `delivery_logs` of each RESULT (02 §5.1). |

- **Start.** Start uses a three-party latch (IO, dispatch and init thread). `zh->core` is stored before the first `pthread_create`. Callbacks may run before init returns, as in legacy.
- **Close.** Close is keyed on the calling thread's role, which C passes from its TLS:
  - from a foreign thread: join both library threads;
  - from the dispatch thread: join IO, detach self;
  - from the IO thread: detach self, join dispatch.

  The final close runs on whichever thread drops the last reference. A close while another close is in progress is a ZOK no-op.
- **Use after close (debug builds, both flavors).** `--enable-debug` or a CMake `Debug` build defines `ZKS_HANDLE_REGISTRY`. The shim then keeps a mutex-protected registry of live handles, and every API entry checks it and aborts with a clear stderr message on use after close or on a double close. Release builds do not define it: there use after close is undefined, as in legacy, and costs nothing (CLS-10, 07).
- **SASL owner.** SASL items are drained only on the IO owner: the IO thread while it runs, and after the IO thread has been joined or has exited, the thread that runs the final close. At most one SASL START or STEP item is in flight per handle (§2.6 rule 4).

### 2.3 Thread model, libzookeeper_st

- There are no library threads and no waker.
- All work runs on the caller inside `zookeeper_interest`, `zookeeper_process`, `zookeeper_close` and the `zoo_a*` calls. The `zoo_a*` calls do an inline non-blocking flush. On failure they do a forced close: state 999 and the socket closed in the call, with no callback, and the next `zookeeper_interest` or `zookeeper_process` call runs the rest of the teardown (DV-FIX-8).
- Callbacks run inline in the shim's drain. That happens at session-event barriers (`DriverMode::session_delivery = Inline`), at `DrainPoint`s, and at the end of the call.
- A close from inside a callback is deferred to the enclosing call's epilog. The enclosing call then returns its own rc with `zh` already released.
- Interest bits follow `LegacyExact`. Plaintext reads take at most one frame per process call. Under TLS, one process call dispatches every frame that is already complete in plaintext (TLS-04).
- TLS context build, handshake and records run in Rust on the caller, inside the `zookeeper_interest` / `zookeeper_process` call that reaches that phase (the same calls as legacy `init_ssl_for_handler`, zookeeper.c:2718, 3093).
- SASL items run inline in the drain on the caller, which is the IO owner in st.

### 2.4 Drop-in data path for one async op (mt)

1. **App thread.** `zoo_awget` fills a `zkrs_request` and calls `zkrs_submit`. Under the core lock this validates in legacy order, assigns the xid, encodes, and appends to tx and the FIFO. The call returns `zkrs_status` and an outbox that is usually empty; the waker is set.
2. **IO thread.** `zkrs_io_step` polls, flushes, reads the reply and arms the watch. Proto emits `Completion{Queued}`; the IO step pumps it into its outbox as a publish entry, and `zkrs_outbox_next` appends it to the dispatch FIFO (FIFO lock only) after C has emitted any preceding LOG item on the IO thread (03 §3.4).
3. **Dispatch thread.** `zkrs_wait_dispatch` returns the batch. For each result, zk-ffi's raw writers build the legacy reply objects: the data buffer from libc `malloc`, with the allocation choice and size of the generated jute deserializer, and the `Stat`. `zks_deliver_result` then calls `dc(rc, value, len, &stat, data)` and frees the objects after the callback, as legacy `deserialize_response` does with `deallocate_GetDataResponse` (zookeeper.c:3348-3352; 05 §10).

### 2.5 TLS: rustls in zk-driver, both profiles

#### 2.5.1 Placement and backend

- **Backend.** `rustls` 0.23.x (`default-features = false`, features `std`, `tls12`, and one provider). The crypto provider is `ring` by default. Three provider builds are supported (K24): configure `--with-rust-tls-provider=ring|aws-lc-rs|aws-lc-rs-fips`, CMake `-DZK_RUST_TLS_PROVIDER=ring|aws-lc-rs|aws-lc-rs-fips`, Maven `-Drust-tls-provider`. When the C build enables TLS, the drop-in staticlib build passes `--features tls,tls-${provider}`; otherwise it passes no TLS feature (§2.7; 01 §13).
- **FIPS build.** The provider `aws-lc-rs-fips` uses aws-lc-rs with its `fips` feature (sys crate `aws-lc-fips-sys`, which needs CMake and Go on the build host), rustls with its `fips` feature, and `require_ems`. It offers only FIPS-approved cipher suites, key-exchange groups and signature algorithms. zk-ffi asserts `provider.fips()` at handle creation and the connector checks `ClientConfig::fips()` on every per-attempt config (06 §3.15.2). Every signature check, the v1-leaf path of `LegacyChainOnly` included (§2.5.2), uses only the FIPS module. Key loading accepts only the FIPS subset of §2.5.4 (DV-TLS-6). The validation scope is Linux x86_64 and aarch64.
- **Cargo features (zk-ffi and zk-driver use the same names).** `tls` holds the TLS code and selects no provider. `tls-ring`, `tls-aws-lc-rs` and `tls-aws-lc-rs-fips` each select one provider and each imply `tls`. Exactly one provider is required: with `tls` and no provider, or with more than one provider, the crate fails to build with a `compile_error!` that names the provider features. Lint and test jobs therefore use explicit feature sets, never `--all-features`. zk-client mirrors the provider features: `tls-rustls` with `tls-ring` (the default provider), `tls-aws-lc-rs` or `tls-aws-lc-rs-fips` (CC-34; 04 §18).
- **Provider use.** The provider is passed explicitly with `ClientConfig::builder_with_provider`. The library never calls `CryptoProvider::install_default` or `get_default`, because the process default is global state that other Rust code in the process may own.
- **Placement.** TLS code lives in `zk-driver/src/net/tls/` (`#![forbid(unsafe_code)]`), with the module names of 06 §3.1. `RustlsConn` drives a `rustls::ClientConnection` over in-memory buffers (`read_tls`/`write_tls` into `Vec<u8>`). The `TlsConn`/`TlsConnector` traits are the driver contract. 03 §8.2.1 owns their signatures, and 06 §3.1-§3.2 use the same names. `RustlsConn` is the one implementation, for the drop-in and the native drivers alike. The driver-side `TlsTransport` (03 §4.3) also lives in `net/tls/mod.rs`.
- **Connect order.** On TCP-connect completion the driver calls `TlsConnector::new_conn` first and then `handle_tcp_connected` (03 §4.3).
- **Socket ownership.** The driver owns the socket and does every `send` (MSG_NOSIGNAL, or SO_NOSIGPIPE on Apple), so no TLS path can raise SIGPIPE. Legacy `SSL_write` on the fd could (zookeeper.c:407; GLB-01).
- **Not in the shim.** The shim has no TLS source file and the host vtable has no TLS entry. The library never reads or writes `zsock_t.ssl_sock`/`ssl_ctx`.

```rust
// zk-driver/src/net/tls/mod.rs   #![forbid(unsafe_code)], feature "tls"
pub use zk_proto::{Endpoint, TlsConfigStep, TlsResourceAt};
// TlsConfigStep { CaFile, DefaultVerifyPaths, ClientCertChain, ClientKey, CheckPrivateKey }
// TlsResourceAt { ContextNew, ConnectionNew }

/// Sans-IO TLS session for one connection attempt or one RW probe.
/// RustlsConn is the one implementation.
pub trait TlsConn: Send {
    fn is_handshaking(&self) -> bool;
    fn wants_read(&self) -> bool;
    fn has_ciphertext(&self) -> bool;
    fn handshake(&mut self) -> Result<(), TlsFailure>;          // Ok while more bytes are needed
    fn feed(&mut self, ciphertext: &[u8]) -> Result<(), TlsFailure>;
    fn feed_eof(&mut self) -> Result<(), TlsFailure>;
    /// Drains all plaintext. Plaintext already decrypted is returned first;
    /// a latched failure is returned on the next call (03 §8.2.1).
    fn read_plaintext(&mut self, out: &mut Vec<u8>) -> Result<usize, TlsFailure>;
    fn write_frame(&mut self, plaintext: &[u8]) -> Result<(), TlsFailure>;        // one call per chunk
    fn take_ciphertext(&mut self, out: &mut Vec<u8>) -> usize;
    /// Queues the close_notify alert for take_ciphertext. Graceful close only (03 §4.3.5).
    fn send_close_notify(&mut self);
}
pub enum TlsFailure { Handshake, Data, Closed }
/// Config: errno is EINVAL. The step selects the pinned log site.
pub enum TlsSetupError { Config { step: TlsConfigStep }, Resource { at: TlsResourceAt } }
pub enum TlsPurpose { Main, Probe }
pub trait TlsConnector: Send + Sync {
    /// Make a new session. The drop-in reads all files again on each call; natively ReloadPolicy decides (03 §4.3.1).
    /// Call only with no driver lock held (the Unlocked proof).
    /// No time argument: the verifier uses the rustls time provider.
    fn new_conn(&self, u: &Unlocked, purpose: TlsPurpose, peer: &Endpoint)
        -> Result<Box<dyn TlsConn>, TlsSetupError>;
    /// The cert-string field that the step's log line prints. None for a NULL field (printed as "(null)") and for steps that print no path (03 §8.2.1).
    /// TlsSetupError::Config carries no file name; the driver takes it from here.
    fn path_for(&self, step: TlsConfigStep) -> Option<&[u8]>;
}
/// Driver-side transport state for one TLS connection (03 §4.3).
pub struct TlsTransport { /* socket, Box<dyn TlsConn>, unsent ciphertext, latched failure */ }
/// A rustls ClientConnection over Vec<u8> buffers.
pub struct RustlsConn { /* ClientConnection, rx and tx buffers */ }
/// Makes RustlsConn. The verifier comes from Compat::tls_verify.
pub struct RustlsConnector { /* src: ConfigSource {Legacy{.., verify: TlsVerify}, Native}, provider: Arc<CryptoProvider> (03 §8.2.3) */ }
```

`zk_proto::Endpoint { addr: SocketAddr, host: HostToken }` carries the resolved address and the connect-string host token. The token is needed only by `WebPki`. The verifiers check validity against `now`, the `UnixTime` that rustls passes to `verify_server_cert`. It comes from the rustls time provider: in production that is the system clock (`SystemTime::now`), which is the time OpenSSL uses for validity checks; tests inject their own provider. `new_conn` therefore takes no time argument.

The shared TLS types are owned by zk-proto and re-exported by zk-driver (CC-17): `TlsConfigStep`, `TlsResourceAt`, `Endpoint`, and the transport failures `TransportFailure::TlsConfig { step, file }`, `TransportFailure::TlsResource { at, errno }` and `TransportFailure::TlsHandshake { errno }`. `file` exists only for the log line, and the driver fills it from `TlsConnector::path_for(step)`; the zk-proto config keeps no file names. A probe config failure is `ProbeTlsFailure::Config { step, file }`, and the probe result enters zk-proto through `handle_rw_probe(ep: Endpoint, outcome: ProbeOutcome, now)` (02 §9.5).

#### 2.5.2 Verifier policies (`Compat::tls_verify`)

`Compat` has the field `tls_verify: TlsVerify { LegacyChainOnly, WebPki }`. `LEGACY_C` uses `LegacyChainOnly`; `NATIVE` uses `WebPki`.

**`LegacyChainOnly`** reproduces the OpenSSL trust decision of the legacy client (zookeeper.c:2876-2890: `SSL_VERIFY_PEER | SSL_VERIFY_FAIL_IF_NO_PEER_CERT`, CA file plus default verify paths, purpose `sslserver`, no `X509_V_FLAG_PARTIAL_CHAIN`, no CRL check, no name check, no SNI). It is a custom `rustls::client::danger::ServerCertVerifier`. Its rules (a)–(d) are those of 06 §3.5. The reference OpenSSL lines are 3.0 and 3.5 LTS. OpenSSL 1.1.1 is out of support and is not a reference. The rules use OpenSSL's definition of "self-signed":

- **OpenSSL-self-signed** means OpenSSL 3.x `EXFLAG_SS`: the canonical subject equals the canonical issuer; the AKID is consistent with the certificate itself (`X509_check_akid`: a key identifier that differs from the SKID, a different serial, or a different directory name is a mismatch; an absent AKID or SKID is not); and the key type of the signature algorithm matches the SPKI key type. **The self-signature is never verified**, as in OpenSSL without `X509_V_FLAG_CHECK_SS_SIGNATURE` (06 §3.4, `openssl_self_signed()`).

The verifier:

- (a) **Chain path.** When the leaf is not OpenSSL-self-signed, it builds and checks the chain. An X.509 v3 leaf goes through `rustls::client::verify_server_cert_signed_by_trust_anchor`, with the anchors valid at `now` (OpenSSL checks anchor time too) and with the presented intermediates and the trusted non-self-signed inputs offered as intermediates only when `now < notAfter`. After webpki returns, the keyCertSign post-check runs: webpki does not enforce keyCertSign on CA certificates, so the chain is rejected (error 32, `X509_V_ERR_KEYUSAGE_NO_CERTSIGN`) when any presented intermediate or trusted bridge that can lie on the path from the leaf by `check_issued` has keyUsage without keyCertSign. Where OpenSSL's path does not use that certificate (for example because its issuer choice takes another certificate of the same name) and OpenSSL accepts, the stricter verdict is part of DV-TLS-3 (06 §3.5); the check's code comments state that it exists only for OpenSSL parity and how to remove it. Then comes the rejected-issuer post-check: the path is rejected when a rejected trust input (rule (d)), valid at `now` or not, passes `check_issued` for the leaf or for any presented intermediate or trusted bridge offered to path building (the time-filtered candidates of 06 §3.5), because webpki does not return the path it built and OpenSSL's trusted-first chain building takes such an input as the issuer and fails (error 28). Where OpenSSL's path does not use that input, the stricter verdict is part of DV-TLS-3 (06 §3.5). Then the leaf is checked again with `notBefore <= now < notAfter`. OpenSSL treats `now == notAfter` as expired, and every validity check that decides uses that rule, so webpki's inclusive `notAfter` check never makes the verifier accept where OpenSSL rejects (06 §3.5). The leaf is also checked against OpenSSL's keyUsage and Netscape cert type rules for an SSL server leaf. Last comes the OpenSSL path post-check (06 §3.5). webpki builds paths differently from OpenSSL: it ignores keyUsage on CA certificates, the anchor's pathLenConstraint, the AKID and the subject CN, and it retries every same-name issuer after a signature failure, so it accepts some chains that OpenSSL rejects. The post-check therefore runs the issuer selection and finish rules of the v1-leaf verifier (06 §3.14.3) over the leaf, the presented intermediates and the trust set: trusted-first selection, the `find_issuer` order, no sent certificate above a trusted bridge or a self-signed sent certificate, the ambiguity rule, keyCertSign on the chosen issuer, `check_ca`, every pathLenConstraint including the anchor's, and name constraints including `NAME_CONSTRAINTS_check_CN`, with the leaf's own EKU, keyUsage and Netscape cert type purpose and its subjectAltName. The leaf is accepted only when webpki and all three post-checks accept. It **never** calls `verify_server_name`. An X.509 v1 leaf, which webpki does not parse, goes through the in-tree v1-leaf verifier (`forbid(unsafe_code)`, 06 §3.14), with full OpenSSL parity. It checks the leaf signature against its issuer with the provider's `SignatureVerificationAlgorithm`, then verifies the issuer chain to an anchor with OpenSSL's rules: basicConstraints and pathlen, keyUsage keyCertSign, the `notAfter` rule above, the SSL-server purpose, and no sent certificate above a trusted bridge or a self-signed sent certificate. A v1 leaf is therefore accepted at any depth below a valid v3 chain. A v1 intermediate is rejected, as OpenSSL rejects it (`check_ca` returns 0 for a v1 certificate that is not self-signed, error 79 `X509_V_ERR_INVALID_CA`). v3 leaves never take this path to acceptance; for them its rules run only as the post-check above. The v1-leaf verifier is differentially tested against OpenSSL 3.0 and 3.5 (08 §5.2).
- (b) **Self-signed leaf path.** When the presented leaf is OpenSSL-self-signed, OpenSSL builds no chain past it. The leaf is accepted only if it is byte-identical to a trust-set certificate that is not a rejected input (rule (d)) and that passes OpenSSL's `check_issued` for it (OpenSSL 3.x `ossl_x509_likely_issued`: issuer name, AKID and signature-algorithm key type; 06 §3.5), and that certificate is the only such trust input valid at `now`, or the only one at all (the "mimic" rule; it fails closed where OpenSSL's choice among same-subject trust inputs would depend on store order). A time-valid rejected input among those same-subject inputs rejects the leaf (error 28). The leaf must also be valid at `now` (`notBefore <= now < notAfter`, read from the DER) and pass the SSL-server purpose check (EKU, keyUsage, Netscape cert type), which an aux trust list naming serverAuth or anyExtendedKeyUsage satisfies, as in 06 §3.14.3 Purpose: OpenSSL replaces the leaf with the trusted store certificate, and its `check_purpose` consults `X509_check_trust` first for a trusted certificate. The leaf must also have no critical extension outside the processed set of 06 §3.14.3 (`X509_V_ERR_UNHANDLED_CRITICAL_EXTENSION`, error 34); aux trust does not override it. A `CA:TRUE` leaf is accepted on this path. A self-signed leaf not in the trust set is rejected.
- (c) **No name, no SNI.** It sends no SNI (`enable_sni = false`). The `ServerName` passed to rustls is `ServerName::IpAddress` of the peer address, and no host name is checked.
- (d) **Anchors.** A trust input becomes a rustls trust anchor only if it is OpenSSL-self-signed, CA-capable (`X509_check_ca != 0`) and purpose-compatible (no EKU, or an EKU that allows serverAuth or SGC), or if its `TRUSTED CERTIFICATE` aux trust list names serverAuth or anyExtendedKeyUsage. A reject list naming either, or a non-empty trust list that names neither, makes the input a rejected issuer: it stays in the trust set, as OpenSSL keeps it in the store, but it is never an anchor, a bridge or a path-(b) match, and the chain fails (OpenSSL error 28, `X509_V_ERR_CERT_REJECTED`) when chain building selects it as an issuer (06 §3.4). A v1 self-signed certificate is CA-capable (`check_ca` returns 3 for it), so v1 anchors are accepted. A trust input that is neither self-signed nor explicitly trusted, and not rejected, is offered only as an intermediate ("bridge"). Legacy OpenSSL runs without `X509_V_FLAG_PARTIAL_CHAIN`, so a chain must end at a self-signed trusted certificate or at an explicitly trusted `TRUSTED CERTIFICATE` input; webpki would otherwise accept a chain that ends at any listed intermediate.
- **Handshake signatures** are verified from the leaf's SPKI with the provider's `signature_verification_algorithms` (TLS 1.2 through `WebPkiSupportedAlgorithms::mapping`, TLS 1.3 through `verify_tls13_signature_with_raw_key`), so a v1 leaf accepted by (a) or (b) works. Before any path runs, the verifier rejects a leaf whose own key type, curve, size or point form no provider algorithm verifies (`leaf_key_usable`, 06 §3.5; DV-TLS-3), because the chain checks read only issuer keys and path (b) verifies no signature.
- It disables session resumption (a fresh `SSL_CTX` per attempt in legacy).

**In-tree fixtures.** The in-tree tests (`testSSL`, `testSSLServerOnly`, TestClient.cc:975-987) put the server's own certificate, `server.crt`, in the CA file. `server.crt` is a leaf signed by `root.crt`, not a self-signed certificate. OpenSSL accepts it only because `ssl/gencerts.sh` gives root, server and client one identical DN: a v1 `server.crt` made by `openssl x509 -req` (gencerts.sh:113) on OpenSSL ≤ 3.1 or LibreSSL has subject equal to issuer and no AKID, so it is `EXFLAG_SS`, and rule (b) accepts it by byte identity. A cryptographic self-signature check would reject it and break `testSSL`. The output of OpenSSL ≥ 3.2 (v3 with an AKID that names the root key) is not self-signed by this rule and is rejected by legacy too. When the CA file holds `root.crt` instead, this `server.crt` is still OpenSSL-self-signed and not byte-identical to a trust-set certificate, so OpenSSL rejects it (error 18) and rule (b) rejects it too. Operators who follow `gencerts.sh` with their own DNs get a v1 leaf that is not self-signed; such a leaf is accepted by the v1-leaf path of rule (a) when its CA is trusted, as OpenSSL accepts it (06 §3.14).

The trust-decision corpus (§7 row 6; 08 §5.2) checks rules (a)–(d), the v1-leaf path included, against OpenSSL 3.0 and 3.5 LTS before M3 exit. A Rust ACCEPT against an oracle REJECT is a blocking defect and can never become a DV row (under the reference OpenSSL's default configuration; DV-TLS-2 covers stricter host policy).

**`WebPki`** (native) checks the hostname against the connect-string host token and sends SNI for DNS names only. IP-literal tokens verify against IP SANs. Only configured roots are trusted unless the application asks for system roots. System roots come from the same trust loader (`trust.rs`) as the drop-in default paths, with no extra trust crates. The native `TlsOptionsBuilder::build` with `DefaultRoots` fails when the loader reports zero usable roots. That check is native-only; the drop-in `DefaultVerifyPaths` step never fails for that reason (§2.5.3). `add_system_roots()` uses this OpenSSL-location loader. The opt-in native feature `tls-platform-verifier` adds `TlsOptionsBuilder::with_platform_verifier()`, which verifies through `rustls-platform-verifier` with the OS trust store and the OS verification policy. The drop-in never uses it: cargo-deny bans `rustls-platform-verifier` from the zk-ffi closure, and the feature has its own native closure golden. The API names belong to 04 §16.1 (`TlsOptions`).

#### 2.5.3 Trust inputs (drop-in)

The trust inputs are found the way OpenSSL finds them, so trust is never wider than legacy (08 P6). The drop-in and the native `tls-rustls` feature share one loader, `trust.rs`.

- **CA file** (`SSL_CTX_load_verify_locations(ctx, ca, NULL)`):
  - parsed as PEM by our own RFC 1421 reader over `base64ct` (no `rustls-pemfile`, K14);
  - `CERTIFICATE`, `X509 CERTIFICATE` and `TRUSTED CERTIFICATE` blocks are trust inputs; `TRUSTED CERTIFICATE` aux trust and reject settings are honored by the OpenSSL rules, as `X509_check_trust` applies them for `X509_TRUST_SSL_SERVER` (06 §3.4);
  - `X509 CRL` blocks are counted but not used (legacy enables no CRL check); well-formed private-key blocks, well-formed blocks with other labels and text outside blocks are ignored, as `PEM_X509_INFO_read_bio` does;
  - the load succeeds when the file yields at least one certificate or at least one CRL, as `X509_load_cert_crl_file` does. A CRL-only file therefore loads and contributes no anchor. The load fails, all or nothing, when the file cannot be opened or read, when any PEM block of any label has invalid base64, when a certificate, CRL or unencrypted private-key block has invalid DER, or when the file yields neither a certificate nor a CRL. The `CaFile` step then fails and logs "Failed to load CA file %s". Invalid DER means what OpenSSL's `d2i_X509` refuses: a certificate block that OpenSSL decodes and the verifier's parser does not parse adds no trust input and does not fail the load (06 §3.4, DV-TLS-3). `ca == NULL` (cert string `""`) fails, as OpenSSL does when both arguments are NULL. Its log line prints `(null)` for the path on every platform. Legacy passes the NULL pointer to `%s` (zookeeper.c:2881), which glibc prints as `(null)` and which crashes on some other libcs; there the fixed output is FU.
- **Default verify paths** (`SSL_CTX_set_default_verify_paths`):
  - **Environment.** `trust.rs` reads `SSL_CERT_FILE` and `SSL_CERT_DIR` itself, per attempt, only when `zkrs_init_args.tls_env_allowed` is set. The shim computes that flag once at init from `getauxval(AT_SECURE) == 0` (Linux) or `!issetugid()` (BSD, Apple), and sets it on Windows, so set-uid and set-gid processes ignore the variables as OpenSSL's `ossl_safe_getenv` does. The native `tls-rustls` builder computes the same flag in safe Rust with rustix: `getuid() == geteuid() && getgid() == getegid()` on Unix, and true on Windows (04 §16.1). When a variable is set, its value is used alone, even if the path does not exist; there is no fallback. `SSL_CERT_DIR` is a `:`-separated list (`;` on Windows).
  - **Without the variable.** The loader uses the compile-time defaults `ZK_TLS_DEFAULT_CERT_FILE` and `ZK_TLS_DEFAULT_CERT_DIR`. configure passes them to cargo from `--with-rust-tls-default-paths=FILE:DIR` (CMake `-DZK_RUST_TLS_DEFAULT_PATHS`). The option defaults to the OPENSSLDIR recorded at configure time: the file `OPENSSLDIR/cert.pem` and the directory `OPENSSLDIR/certs`, from `openssl version -d`. The `openssl` binary is the one of the OpenSSL installation that the legacy probe selected: `$with_openssl/bin/openssl` for `--with-openssl=DIR`, `OPENSSL_ROOT_DIR/bin/openssl` in CMake, and otherwise the first `openssl` on PATH. This keeps the defaults those of the library that legacy would link, so trust is never wider than legacy. When no such binary exists, configure and CMake apply the platform list of 01 §6.1 (`/usr/lib/ssl /etc/pki/tls /etc/ssl /usr/local/ssl /usr/local/etc/openssl@3 /opt/homebrew/etc/openssl@3`) on the build host and take `<dir>/cert.pem` and `<dir>/certs` from the first entry that exists (06 §3.4). For a native cargo build with `ZK_TLS_DEFAULT_CERT_FILE`/`ZK_TLS_DEFAULT_CERT_DIR` unset, zk-driver's `build.rs` applies the same list on the build host. Cross builds set the variables explicitly. There is exactly **one** default file and **one** default directory, because OpenSSL has one compiled-in default file and one default directory. Nothing is probed at run time. TI-02 (08) checks the recorded pair against the OPENSSLDIR of the OpenSSL that the legacy probe selected, on a test image that has the `openssl` CLI.
  - **Not used.** `openssl-probe` is not in the closure, and `openssl_probe::probe()` is never called. That function reads the variables itself (ignoring AT_SECURE), drops missing paths, falls back to system bundles and returns every existing candidate directory, so it could trust more than legacy. Its functions that set environment variables would also change process state (08 G9).
  - **Windows.** There is no compile-time default unless `--with-rust-tls-default-paths` sets one, so only the environment variables are used (legacy OpenSSL's compiled-in OPENSSLDIR (for example C:\Program Files\Common Files\SSL) normally does not exist or holds no certificates there; a populated one is covered by DV-TLS-2). The Windows certificate store and the macOS keychain are never consulted.
  - **Windows path encoding.** The cert-string paths (CA file, certificate, key) are opened as UTF-8 first, through the wide API. When the bytes are not valid UTF-8, or the open fails with not-found, the open is retried with the bytes converted from the ANSI code page (`MultiByteToWideChar(CP_ACP, …)` in zk-ffi), as OpenSSL's `openssl_fopen` does. `SSL_CERT_FILE` and `SSL_CERT_DIR` are read as wide strings with `std::env::var_os` and used without conversion; OpenSSL 3 reads them with `getenv` in the ANSI code page (unless `OPENSSL_WIN32_UTF8` is set) and opens them by the same UTF-8-then-ANSI rule, so both open the same file whenever the value is representable in the ANSI code page. Hash-directory entries are formed from the directory path in the same encoding (06 §3.4). TI-06 (08) tests both encodings.
  - **Directories** (`SSL_CERT_DIR` and the default directory) are read only through OpenSSL subject-hash file names `HHHHHHHH.N`, with suffixes from `.0` upward until the first suffix whose file is missing or does not load (no certificate, or a corrupt block), as `by_dir` does. A certificate in such a file counts only when the OpenSSL subject hash (`X509_NAME_hash_ex` canonical form) of its subject equals the name. The hash uses the selected provider's SHA-1 (`ring::digest::SHA1_FOR_LEGACY_USE_ONLY` or the aws-lc-rs equivalent, 06 §3.4); the `sha1` crate is in the closure only for PBKDF2-HMAC-SHA1, and only in the `ring` and `aws-lc-rs` builds. Other files, including CRL files (`HHHHHHHH.rN`), are ignored. OpenSSL 3.0 also consults a default `X509_LOOKUP_store` over the same directory value when it is a single path and the `by_dir` pass finds no certificate with the wanted subject; that lookup reads `<hash>.<digits>` names with the hex part compared case-insensitively and no stop at a suffix gap. OpenSSL 3.5 adds no default store location. The loader applies the `by_dir` rule alone; where OpenSSL 3.0 accepts through the store lookup, or where OpenSSL 3.0 or 3.5 keeps a certificate that comes before a corrupt block in a hash-named file, or a certificate in a hash-named file of another subject, the stricter verdict is DV-TLS-3 (06 §3.4).
  - **Failure.** A missing, empty or malformed default location contributes no anchors (all or nothing per file) and never fails the attempt, as `X509_STORE_set_default_paths` ignores the results of its loads. The `DefaultVerifyPaths` step fails only on a resource error. In Rust that is allocation failure, which aborts (07 P7), so the line at zookeeper.c:2888 is effectively unreachable, as in legacy.
  - The difference between the configure-recorded location and the OPENSSLDIR compiled into a system OpenSSL is part of DV-TLS-2.
- Files are re-read on every connection attempt and every probe (TLS-02 parity).

#### 2.5.4 Client identity (drop-in)

- It is loaded only when cert, key and passwd are all non-NULL, as in legacy (zookeeper.c:2892).
- **Chain.** The first `CERTIFICATE`, `X509 CERTIFICATE` or `TRUSTED CERTIFICATE` block is the leaf (aux data dropped); later `CERTIFICATE` or `X509 CERTIFICATE` blocks form the chain in file order. The chain is sent as DER exactly as read, so v1 client certificates work. It is not checked against the OpenSSL security level (DV-TLS-2).
- **Key.** The first private-key block of the file is used, so a key file may also hold certificates. The passphrase is the first `min(strlen(passwd), 1024)` bytes of passwd, which is what OpenSSL's `PEM_def_callback` copies. Accepted:
  - unencrypted PKCS#1, SEC1 (named curve) and PKCS#8;
  - encrypted PKCS#8: PBES2 with PBKDF2 (PRF HMAC-SHA1, -SHA224, -SHA256, -SHA384 or -SHA512, the accepted subset of the PRFs OpenSSL loads; other PRFs that OpenSSL loads are DV-TLS-5) or scrypt, and AES-128/192/256-CBC or DES-EDE3-CBC, using `pkcs8` 0.10 (`encryption`) and `pkcs5` 0.7 (`pbes2`, `3des`, `sha1-insecure`). The set includes the PBKDF2-HMAC-SHA1 PRF and DES-EDE3-CBC that OpenSSL 1.0/1.1 produced. Before decryption the `EncryptedPrivateKeyInfo` is parsed. If the scrypt memory (128·r·(N + 2) + 128·r·p, OpenSSL's Vlen + Blen) is above 32 MiB (OpenSSL's default `EVP_PBE_scrypt` `maxmem`), or the key length is unexpected, the `ClientKey` step fails with "Failed to load client private key from %s" before any allocation for the derivation. A hostile key file therefore cannot make the process abort on allocation, and OpenSSL fails in the same cases;
  - traditional OpenSSL PEM encryption (`Proc-Type: 4,ENCRYPTED` + `DEK-Info` with AES-128/192/256-CBC, DES-EDE3-CBC or DES-CBC). The DEK-Info cipher name must be one of AES-128-CBC, AES-192-CBC, AES-256-CBC, DES-EDE3-CBC or DES-CBC; any other name fails the ClientKey step (06 §3.6, DV-TLS-5). OpenSSL 3 decrypts DES-CBC only with its legacy provider, so the reference legacy core fails the ClientKey step for such a key, and the Rust core loads it (DV-TLS-2). The key comes from `EVP_BytesToKey(cipher, MD5, salt = IV[0..8], count = 1)` (D1, or D1‖D2), followed by strict PKCS#7 padding removal. It is implemented in a small `zk-driver::net::tls::legacy_pem` module over RustCrypto `aes`, `des`, `cbc`, `md-5`.
  - PKCS#12 PBE schemes, PBES2 PRFs and ciphers outside the sets above, and other PEM encryptions are rejected (DV-TLS-5, §5.1). Key types and sizes that the provider's key loader does not load are rejected with the same line (DV-TLS-5): DSA, Ed448, RSA-PSS (PKCS#8 `id-RSASSA-PSS`, which OpenSSL loads into its RSA_PSS slot), RSA keys under 2048 bits, EC keys on unsupported curves (for example P-521 in the `ring` build), and keys outside the provider's own limits (in the `ring` build, RSA keys above its maximum modulus size or with a public exponent below 65537, and SEC1 keys without the public key). PBES1, which uses single DES or RC2, fails in both cores under the reference default providers. The release notes give the conversion command, `openssl pkcs8 -topk8 -v2 aes-256-cbc`.
  - **FIPS build.** The `aws-lc-rs-fips` build accepts unencrypted keys and encrypted PKCS#8 with PBES2, PBKDF2-HMAC-SHA256, -SHA384 or -SHA512 and AES-128/192/256-CBC only, decrypted in the FIPS module (06 §3.15.3). Traditional PEM encryption (MD5-based key derivation, any cipher), DES-EDE3-CBC and DES-CBC, PBKDF2 with HMAC-SHA1 or HMAC-SHA224, and scrypt are rejected with the same "Failed to load client private key from %s" line (DV-TLS-6).
- An unencrypted key with a passwd given ignores the passwd, as OpenSSL does.
- **Key/cert match** reproduces which OpenSSL step fails. When the key and the leaf are of the same key type (same OpenSSL key slot), a different public key fails the `ClientKey` step ("Failed to load client private key from %s"). When they are of different types, the `CheckPrivateKey` step fails ("SSL_CTX_check_private_key failed"); the SPKI comparison there covers any remaining case (06 §3.6).
- **Ownership.** The shim `strdup`s the cert string, splits the copy with `strtok_r`, and passes four borrowed strings to `zkrs_handle_new`. zk-ffi copies passwd into the connector's `Zeroizing<Vec<u8>>` (03 §8.2.3) and keeps the three paths as owned bytes. The shim then zeroes the whole copy with `zks_secure_zero` and frees it before `zookeeper_init_ssl` returns. The handle does not keep the cert string; zk-ffi keeps only its own copies of the four fields (06 §3.10). This is hardening beyond legacy, which keeps `certstr` until destroy and only frees it, without zeroing (zookeeper.c:730-735). Decrypted key bytes are held in `Zeroizing<Vec<u8>>`.

#### 2.5.5 Phases, return codes and log lines

- TLS phases are zk-proto phases. State 7 is visible on the EINPROGRESS path. The immediate-connect path shows the pre-connect value (0 or 999) until the handshake completes.
- The TCP-connect phase stays exempt from the receive timeout; only its `tv=0` spin is fixed. In state 7, `tv = T/3` when `recv_to <= 0`, otherwise `tv = min(recv_to, T/3)` (ST-16(a), 07 §4.3).
- The handshake is non-blocking, with a deadline of 2/3·T from TCP-connect completion. Expiry tears down with ZOPERATIONTIMEOUT, errno ETIMEDOUT. A fatal handshake (verify failure, alert, protocol error) tears down with ZSSLCONNECTIONERROR.
- After the handshake, an alert, a record or protocol error, a received close_notify or TCP EOF is a ZCONNECTIONLOSS teardown (TLS-05, RE).
- **Graceful close sends close_notify (both profiles).** After the CloseSession exchange, or when it ends within the close budget, the driver calls `send_close_notify()`, flushes the alert without blocking within the remaining close budget, and closes the socket. It never waits for the peer's close_notify. Forced and error teardowns send no close_notify, and neither does the RW probe. Applications cannot observe the extra record (07 P6); the ledger records it in a TLS row as a wire-only difference, and the wire-trace comparisons of 08 allow it. After a fatal TLS error that rustls detects (a verify failure, a bad record, a protocol violation), the driver in both profiles makes one non-blocking send of the fatal alert that rustls queued, and drops the alert when earlier ciphertext is still waiting in `ct_out`. This is what OpenSSL does on the non-blocking legacy socket: it writes the fatal alert inside `SSL_connect` or `SSL_read`, before the C code sees the error, when no record write is pending, and `SSL_free` discards it otherwise (03 §4.3.5). 08 §5.1 confirms this OpenSSL 3.0 and 3.5 behavior before M3 work begins, against the releases frozen for M3.
- **Socket errno in TLS teardown log lines.** The errno printed by a TLS teardown line is the errno of the last failed socket call, or 0. This is log text only, not observable (07 P6), and the ledger records it.
- A config failure follows CC-14 (§4): ZSSLCONNECTIONERROR, errno EINVAL, no teardown, no WRITE interest, no spin.
- A `Resource` setup failure (the rustls config or connection cannot be made) tears down with ZSSLCONNECTIONERROR, as legacy does for `SSL_CTX_new`/`SSL_new` failure.
- Exact legacy log lines per failing step, emitted by Rust through the pinned Site table with `func` = `init_ssl_for_socket`. "Main" is the session connection (`fail_on_error = 1`); "Probe" is the RW probe (`fail_on_error = 0`). A Main-column `handle_socket_error_msg` site prints, at ERROR, `"Socket %s zk retcode=%d, errno=%d(%s): %s"` with the current server, the rc, errno and the step text (zookeeper.c:2134-2147).

- Other rules: the cert-string `strtok_r` parsing (as legacy); the RO-probe rules (own session, `TlsPurpose::Probe`, any TLS failure is a probe failure); drain-all reads (TLS-04 FU). Each poll_transmit chunk goes into rustls with one `write_frame` call (03 §4.3.4); record boundaries are not observable (TLS-03, 07 P6).

#### 2.5.6 Build flags and headers

- **TLS presence follows the legacy autodetect exactly.** The configure `--with-openssl[=DIR]` and CMake `WITH_OPENSSL` switches keep their names, their defaults and their probe:
  - autotools: `--with-openssl` defaults to `yes`, which means autodetect. TLS is built only when `openssl/ssl.h` and `-lssl SSL_CTX_new` are found (`=DIR` adds `DIR/include` and `DIR/lib` to the probe). Otherwise configure warns "cannot build SSL support -- openssl not found" and builds without TLS (configure.ac:42-67). `--with-openssl=no` disables TLS;
  - CMake: `WITH_OPENSSL` defaults to `ON` (or a path), gated on `find_package(OpenSSL)` and `OPENSSL_FOUND`, with a warning when OpenSSL is not found (CMakeLists.txt:205-219). `OFF` disables TLS.
- The probe only decides the feature. OpenSSL is never linked, and libssl/libcrypto are not DT_NEEDED (DV-TLS-4). Without the opt-in below, `zookeeper_init_ssl` and `HAVE_OPENSSL_H` are therefore present in exactly the configurations where legacy has them, and the golden export subsets with and without SSL are those of legacy.
- **Opt-in without OpenSSL headers.** `--with-rust-tls=yes` (CMake `WITH_RUST_TLS`) enables TLS when the probe finds no OpenSSL. It is additive and off by default.
- When TLS is enabled, the drop-in staticlib build passes the zk-ffi features `tls,tls-${provider}`. OpenSSL is never linked into the library; the build host needs the OpenSSL headers and libssl only for the autodetect probe, unless `--with-rust-tls=yes` is given (06 §3.11).
- `--with-rust-tls-default-paths=FILE:DIR` (CMake `-DZK_RUST_TLS_DEFAULT_PATHS`) sets the compile-time default trust locations. It defaults to the OPENSSLDIR recorded at configure time (§2.5.3).
- **Feature defines follow legacy exactly.** "TLS is built" means that the legacy autodetect found OpenSSL, or that `--with-rust-tls=yes` / `WITH_RUST_TLS=ON` is given.
  - Autotools: `-DHAVE_OPENSSL_H` is in the library CPPFLAGS when TLS is built (Makefile.am `OPENSSL_CPPFLAGS`), and `-DHAVE_CYRUS_SASL_H` when SASL is built (Makefile.am `SASL_CPPFLAGS`).
  - CMake: `target_compile_definitions(zookeeper PUBLIC HAVE_OPENSSL_H)` when TLS is built and `target_compile_definitions(zookeeper PUBLIC HAVE_CYRUS_SASL_H)` when SASL is built (CMakeLists.txt:213, 227).
  - 01 §6.2 and §6.3 give the build-file text.
- **The shim and `HAVE_OPENSSL_H`.** The shim's own translation units do not depend on `HAVE_OPENSSL_H`. The shim defines `zookeeper_init_ssl` under its private macro `ZKS_WITH_TLS`, with its own prototype check, and that prototype uses no OpenSSL type. The shim never reads or writes `zsock_t.ssl_sock`/`ssl_ctx`. `OpenSSL::SSL`/`OpenSSL::Crypto` are not in any link interface (DV-TLS-4).
- The installed headers are unchanged. `zookeeper.h` still includes `<openssl/ossl_typ.h>` and declares `zookeeper_init_ssl` (zookeeper.h:539-574) when the *application* defines `HAVE_OPENSSL_H`. The layouts are unchanged (ABI-07): `zsock_t` is 16 or 32 bytes on LP64, by the application's `HAVE_OPENSSL_H`; `zcert_t` is 5 pointers, 40 bytes on LP64 (zookeeper.h:302-324).

The full drop-in closure is K14. The TLS additions are pinned, `cargo-vet safe-to-deploy`, and recorded in one closure golden per provider (01 §3.3): `supply-chain/closure/zk-ffi-<target>.txt` for `ring`, `supply-chain/closure/zk-ffi-<target>-aws-lc-rs.txt` for `aws-lc-rs` and `supply-chain/closure/zk-ffi-<target>-aws-lc-rs-fips.txt` for `aws-lc-rs-fips`. ### 2.6 SASL: Cyrus in hardened C (drop-in)

The SASL engine is Cyrus libsasl2. It is called only from shim C, from SASL outbox items drained on the IO owner with no Rust frame on the stack (K2). The ZooKeeper-level quirks (op 102 framing, gating, deferred CONNECTED, DIGEST-MD5 empty initial response, GSSAPI final packet, per-connection reset) live in zk-proto's `SaslNegotiation`. These rules minimize unsafe memory operations on the C side.

1. **Isolation.**
   - Exactly two shim translation units include `<sasl/sasl.h>`: `shim/zks_sasl_cyrus.c` (the engine glue, the secret trampoline and `zks_sasl_set_gen`) and `shim/zks_sasl_cb.c` (`zoo_sasl_make_basic_callbacks` / `zoo_sasl_make_password_callbacks` and their callback functions). Among the shim TUs, only these two have `HAVE_CYRUS_SASL_H` in effect when `zookeeper.h` is included: they define `ZKS_SASL_GLUE`, and in every other TU `zks_internal.h` undefines the macro first (05 §2, 06 §4.7.1). The library and its consumers get the define as in legacy (§2.5.6). The other shim TUs select SASL code with the private macro `ZKS_WITH_SASL` (01 §4.9).
   - `shim/zks_sasl.h` is the glue interface. It has no Cyrus types and is included by the drain. `shim/zks_sasl_cb.h` carries Cyrus types between the two SASL files and is included only by them.
   - No other shim file sees Cyrus types. The engine glue functions (`zks_sasl_start/step/dispose` and the session accessors) call no `zkrs_*` function; `zks_drain.c` moves data between the glue and Rust. The only `zkrs_*` call in `zks_sasl_cyrus.c` is `zkrs_sasl_mark_failed`, from the leaked `zoo_sasl_mark_failed` (05 §19.10).
   - Both files are left out of the build when SASL is disabled; the golden subsets keep the symbol differences.
   - Cyrus headers are included as system headers (`-isystem`), so the strict warning set of rule 7 applies to our code only.
2. **Narrow, bounded interface.**
   - The glue exposes three `void` functions to the drain, with the status in `out` (sketch below; 06 §4.7.2 owns the details). Every call carries the generation.
   - Every byte argument is a `zks_bytes`, which is `typedef zkrs_bytes zks_bytes`, so no field copy or cast is needed. Arguments that carry wire data are built by Rust from data it has already bounds-checked: frame decoding is exact-length, and a -1 token becomes `is_null=1, p=NULL, len=0` (SAS-10). The `local` and `peer` views carry the platform `sockaddr_in`/`sockaddr_in6` image that zk-ffi writes from the addresses that Rust reads with rustix `getsockname`/`getpeername` on the IO-owned socket (CC-31). The glue validates family and length, calls `getnameinfo(NI_NUMERICHOST|NI_NUMERICSERV)` and formats `"%s;%s"` with `snprintf` into bounded buffers, so the strings are byte-identical to legacy, IPv6 scope suffixes included. On a `getnameinfo` error it logs "getnameinfo: %s\n" at the legacy site (zk_sasl.c:185). The mechlist reaches `sasl_client_start` from `p->mechlist`, the session's NUL-terminated copy of `zoo_sasl_params_t.mechlist` in `zks_sasl_params`; there is no separate mechlist accessor. The glue checks every view on entry (`len <= 0x7fffffff`; `is_null` implies `len == 0` and `p == NULL`; `len > 0` implies `p != NULL`).
   - Cyrus output (`clientout`, `clientoutlen`) and the chosen mechanism are returned as views and copied into Rust at once by `zkrs_sasl_result(core, gen, view)`. C never keeps a pointer into a Cyrus output buffer past the next Cyrus call; each glue call clears `out` first.
   - Lengths are `uint32_t`, matching Cyrus `unsigned`, and are checked against a cap of 0x7fffffff before use. The mechanism name is checked with `strnlen(mech, SASL_MECHNAMEMAX + 1)`.
3. **Ownership and lifetime.**
   - `sasl_conn_t*` lives in a shim-owned per-handle `zks_sasl_sess` with a generation counter that matches the Rust `SaslCall.gen` (`u32`, never 0, wraps and skips 0).
   - Dispose timing is the legacy timing. Legacy disposes the old connection at the top of the next `zoo_sasl_connect` (zk_sasl.c:215-217: `if (sc->conn) sasl_dispose(&sc->conn);`) and at destroy (zookeeper.c:744-749). On a reconnect, zk-proto emits `Sasl(Dispose)` for the old connection immediately before `Sasl(Start)` in the same outbox. At close it emits `Sasl(Dispose)` after `CloseTransport` (rule 4). Teardown alone emits no DISPOSE. After dispose the glue sets the pointer to NULL. Any Cyrus callback that a plugin makes during dispose therefore runs at the same point as in legacy, on the IO owner (SAS-13, RE). The generation counter still advances at teardown, so a late result for the old session is rejected as stale.
   - START with a live `sasl_conn_t` disposes it first, as `zoo_sasl_connect` does. **The glue itself rejects a stale generation before any Cyrus call**: START rejects 0 or the live session's gen; STEP and DISPOSE reject any gen other than the live one. A rejected START or STEP sets the status `ZKRS_SASL_STALE` in `out`, and the drain then does not call `zkrs_sasl_result` for that item. The check sits in the glue so that `fuzz/sasl_glue` exercises it. After START the drain records the item's gen with `zks_sasl_set_gen`, which `zks_sasl_cyrus.c` defines (a no-op when START left no connection). Rust also ignores a `zkrs_sasl_result` with a stale generation (CC-17).
   - When `sasl_client_new` fails, the glue disposes `*pconn` if it is non-NULL before it frees the per-session callback array and the secret copies. Cyrus can return an error with the connection still allocated, and that connection points at the shim's own array (05 §19.2).
   - Strings copied from `zoo_sasl_params_t` (service, host, mechlist) are owned by the session. The application's `sasl_callback_t*` array stays borrowed, as in legacy.
4. **Serialization.**
   - Rust guarantees that at most one SASL START or STEP item is in flight per handle. START and STEP are barriers; DISPOSE is ordered by the outbox but is not a barrier. Items are drained only on the IO owner (§2.2, §2.3), so `zks_sasl_dispose` from close is never concurrent with START or STEP.
   - A DISPOSE (and the START behind it) that is due while a START or STEP result is outstanding waits for that result (02 §7.4). If an application Cyrus callback throws during an st START or STEP item, C never answers it. zk-ffi records the item's generation, the receive timeout tears the connection down and advances the generation, and zk-ffi then hands the core a ZSYSTEMERROR result for the old generation. The core ignores that result as stale, and it ends the wait. At the next prime response the core emits DISPOSE for the old session and then START, as legacy `zoo_sasl_connect` does after the stalled negotiation (zk_sasl.c:215-217; zookeeper.c:3188-3189). The glue's stale-generation reject of rule 3 ends the same way (05 §5, §19.2).
   - In an mt close, DISPOSE is emitted after the IO thread is joined (or by the IO thread itself when it runs the final close). The final close closes the transport first and then emits DISPOSE, which is the legacy `destroy` order (zookeeper.c:719-749).
   - This removes the cross-thread dispose race without a lock in C.
5. **Secret trampoline (DAT-13 is FU, with no layout change).**
   - The application-visible calloc block from `zoo_sasl_make_*_callbacks` keeps its exact layout (zk_sasl.c:440-666) and the single-`free()` contract.
   - When the glue calls `sasl_client_new`, it passes a *shim-built per-session callback array*. It is a copy of the application's array in which only the first `SASL_CB_PASS` entry is replaced by `zks_sasl_pass_trampoline`, with a per-session context that records the original `proc`/`context`. Other callback ids pass through unchanged, with their original contexts.
   - **Application callback.** The trampoline calls the original callback with no lock held, then copies the returned `sasl_secret_t` into a per-session buffer (`zks_pass_store`), bounded by its `len` and by the 0x7fffffff cap. Cyrus uses the copy for the life of that `sasl_conn_t`.
   - **Library callback.** When the original callback is the library's own `_zsasl_getsecret` (`zks_is_library_pass_cb`), the trampoline calls `zks_getsecret_unlocked`. It runs the legacy password rules (file re-read, 1023-byte cap `ZSASL_MAX_PASSWORD_LEN`, zk_sasl.c:447; first line; transform callback; `getpass`) with no lock held, so application code (`zoo_sasl_password_t.callback`, `getpass`) never runs under a library lock. It passes the bytes to the same per-session sink. The shared in-block buffer is **not written** for ZooKeeper sessions.
   - **Direct Cyrus users of the block.** The process-wide `zks_sasl_pass_mutex` guards only the in-block `memcpy`/`memset`/`len` write in `_zsasl_getsecret`. That path runs only when the application passes a library-made block to its own Cyrus connections outside ZooKeeper. The password is computed before the lock is taken, so the mutex never spans application code or a Cyrus call. Writes to the shared buffer are therefore serialized. For ZooKeeper sessions the data race of DAT-13 does not occur. The application's own Cyrus connections read the shared `sasl_secret_t` with no lock while another thread can write it under the mutex; that use keeps the legacy header contract (zookeeper.h:695-697) and its residual race, unchanged from legacy.
   - Cyrus may keep the secret pointer across steps (zk_sasl.c:462-465), so each copy stays valid until dispose. A later call makes a new copy and keeps the old ones. Dispose zeroes and frees all copies.
   - **Hardening limits.** More than 16 secret requests on one connection fail with SASL_NOMEM, and so does an application callback array of 4096 or more entries at START. Legacy has neither limit. The shipped mechanisms never reach them; they bound hostile or corrupted input (SAS-14, FU; §5.2).
   - Cyrus never reads a buffer that another session can rewrite.
   - No internal lock is ever held across application code. The library password callback (`zoo_sasl_password_t.callback`, `getpass`) runs with no ZooKeeper lock held and writes into the per-session sink that the trampoline owns. The process-wide mutex guards only the short, non-callback in-block copy for the direct Cyrus path. Because no lock spans application code, unwinding through the callback needs no cleanup handler (06 §4.7.6-4.7.7).
   - This is FIX-UB-ONLY: no correct application can depend on the old behavior (§5.2 lists it as an acknowledged behavior difference).
6. **C coding rules for both files.** These are enforced in CI (06 §4.7.9; 08 §6.1):
   - no `strcpy`/`strcat`/`sprintf`/`vsprintf`/`gets`/`strtok`;
   - `snprintf` with truncation checks for the `"ip;port"` strings;
   - checked arithmetic for every size computation (callback-block layout, per-session array, secret copies) and scoped cleanup through the portable macros of `shim/zks_sasl_cb.h`: `ZKS_ADD_OVF`/`ZKS_MUL_OVF` use `__builtin_add_overflow`/`__builtin_mul_overflow` on GCC and Clang and explicit range checks on MSVC; `ZKS_CLEANUP` uses `__attribute__((cleanup))` on GCC and Clang and an explicit `goto out` cleanup path on MSVC. The code is written so that both forms are correct;
   - `strnlen` with explicit caps;
   - `zks_secure_zero` (`explicit_bzero` / `memset_s` / `SecureZeroMemory`) on every secret copy before free;
   - every Cyrus return code checked; Cyrus errors are logged by C at the pinned legacy sites. "SASL authentication failed. rc=%d", the getsockname/getpeername failures and "SASL intermediate server_data_len:%d" are core (Rust) sites in `log-sites.tsv`, and the glue does not log them;
   - no global mutable state except the documented password mutex (statically initialized).
7. **Build hardening (both files; the rest of the shim without the conversion warnings).**
   - `-D_FORTIFY_SOURCE=3 -fstack-protector-strong -fstack-clash-protection -ftrivial-auto-var-init=zero -fno-strict-overflow -Wformat=2 -Wformat-security -Wconversion -Wsign-conversion -Werror` for these TUs;
   - `-fcf-protection` / `-mbranch-protection=standard` where supported. The shipped library carries no IBT/SHSTK/BTI property note, because the Rust objects in the prelinked member are unmarked and the link drops the note (DV-BLD-8). The design adopts the rustc flags for these markers when they are stable.
   - **Probe and drop.** Configure and CMake probe each flag in every build, releases included, drop a flag that the compiler does not support, and print a notice for each dropped flag. No release gate requires the full set. A host that cannot use `_FORTIFY_SOURCE=3`, such as the AlmaLinux 8 floor image with glibc 2.28, falls back to `_FORTIFY_SOURCE=2`. One CI job uses a toolchain that supports all of them.
   - **`-Werror`.** `-Werror` is on by default and in CI. Packagers turn it off with configure `--disable-werror` or CMake `ZK_WERROR=OFF`.
8. **Verification.**
   - A libFuzzer harness (`fuzz/sasl_glue`) drives `zks_sasl_start`/`zks_sasl_step`/`zks_sasl_dispose` with fuzzed server tokens, address views, mechlists and generations against Cyrus's in-process PLAIN and DIGEST-MD5 plugins and a fake password callback. The mechlist is fuzzed through the params: `zks_sasl_test_new` takes a mechlist argument. It runs under ASan+UBSan.
   - The SASL conformance tests (TestSASLAuth ports, DIGEST-MD5 reconnect, password-file cases) run under ASan, UBSan and Valgrind memcheck, and MSan where Cyrus can be instrumented.
   - `conf.sasl.shared_block_concurrency[dev]` runs two handles on one library-made block under TSan.
   - Clang static analyzer, `gcc -fanalyzer` and CodeQL run on `shim/` in CI.
   - A unit test checks the calloc-block layout with `offsetof` and the single-`free()` release under LSan.
9. **Native API.** The native API implements DIGEST-MD5 in safe Rust, and GSSAPI through the `sasl-gssapi` feature (libgssapi). Cyrus is never linked into native-only builds. Every native SASL failure is terminal: it ends the session with `Cause::SaslTeardown`, and the application decides whether to create a new client (04 §16.2).
10. **Windows.** SASL is optional on Windows, as in legacy: it is built only when CMake finds Cyrus. The glue supports an SRWLOCK password mutex. Windows SASL is tested in CI on a best-effort basis and is not an M4 gate.

```c
/* shim/zks_drain.c: runs on the IO owner, no Rust frame below.
   The glue functions exist only in zks_sasl_cyrus.c, which SASL builds compile.
   This function and its drain case are therefore under ZKS_WITH_SASL. */
#ifdef ZKS_WITH_SASL
static void zks_sasl_item(zhandle_t *zh, const zkrs_sasl_call *c)
{
    struct zks_sasl_sess *s = zh->sasl;      /* Rust emits SASL items only when init_args.sasl = 1 */
    zkrs_sasl_out out = ZKS_SASL_OUT_FAIL;
    if (s == NULL) {                         /* cannot occur; fail cleanly, no Cyrus call */
        if (c->kind != ZKRS_SASL_DISPOSE) ZKS_CALL(zkrs_sasl_result(zh->core, c->gen, &out));
        return;
    }
    switch (c->kind) {
    case ZKRS_SASL_START:                    /* start disposes any old connection first */
        zks_sasl_start(s, c->gen, zks_sasl_sess_params(s), c->local, c->peer, &out);
        if (out.status != ZKRS_SASL_STALE)
            zks_sasl_set_gen(s, c->gen);     /* no-op when START left no connection */
        break;
    case ZKRS_SASL_STEP:
        zks_sasl_step(s, c->gen, c->token, &out);
        break;
    case ZKRS_SASL_DISPOSE:
        zks_sasl_dispose(s, c->gen);         /* a stale gen is a no-op in the glue */
        return;                              /* DISPOSE has no result */
    default:
        return;
    }
    if (out.status == ZKRS_SASL_STALE) return;            /* the glue made no Cyrus call; no result */
    ZKS_CALL(zkrs_sasl_result(zh->core, c->gen, &out));   /* Rust copies before it returns */
}
#endif
```

```c
/* zks_sasl_cyrus.c: Cyrus calls this in place of the SASL_CB_PASS entry. */
static int zks_sasl_pass_trampoline(sasl_conn_t *c, void *ctx, int id, sasl_secret_t **out)
{
    struct zks_pass_ctx *pc = ctx;                   /* one per session */
    sasl_secret_t *got = NULL;
    int rc;
    if (pc == NULL || out == NULL || id != SASL_CB_PASS) return SASL_BADPARAM;
    *out = NULL;
    if (pc->is_library)                              /* zks_is_library_pass_cb(): no lock, no shared write */
        return zks_getsecret_unlocked(c, pc->orig_ctx, zks_pass_store, pc, out);
    rc = ((zks_pass_fn)pc->orig_proc)(c, pc->orig_ctx, id, &got);   /* application code; no lock held */
    if (rc != SASL_OK) return rc;
    if (got == NULL) return SASL_FAIL;
    if (got->len > ZKS_SASL_LEN_CAP) return SASL_BUFOVER;
    return zks_pass_store(pc, (const unsigned char *)got + offsetof(sasl_secret_t, data),
                          (size_t)got->len, out);    /* bounded copy */
}
```

### 2.7 Build and Maven integration

Maven drives the Rust build the same way it drives the C client. 01 §13 is the full specification; 01 §8 owns jute generation and 08 §14 owns the CI topology.

- **Module.** The module is `zookeeper-client/zookeeper-client-rust/pom.xml` (artifactId `zookeeper-client-rust`, packaging `pom`, parent `zookeeper-client`). It inherits the deploy skip, so nothing goes to Maven Central. The module is opt-in: it is listed only in its own profile `rust`, which is activated by `-Prust` or automatically when the `rust-client` property is defined, because a Rust-core C build needs the staticlib. `-Pfull-build` alone builds the legacy C client and needs no cargo. `zookeeper-client-c/pom.xml` holds the `rust-client-dropin` profile, which activates when the `rust-client` property is defined; its only effect is a pom-type reactor-order dependency. That `provided` `pom` dependency on `zookeeper-client-rust` makes the reactor build the staticlib before the C module links it.
- **Core selection (configure and CMake).** The build systems detect what the host can build and honor what the user requires (01 §6.1, §6.3). `--with-rust-client` takes `no`, `yes`, `side-by-side` or `auto`, and CMake `WITH_RUST_CLIENT` takes `ON`, `OFF` or `AUTO`. The default is `no` (unset `WITH_RUST_CLIENT`: `OFF`) before M5 and `auto` (`AUTO`) from M5. `auto` builds the Rust core when rustc and cargo ≥ 1.85 are present, the default provider `ring` supports the target (or a provider other than `ring` is named), and the crates are available (a vendor directory, the system-crates mode, or a successful `cargo fetch`), and otherwise builds the legacy core and prints a notice that gives the reason. An explicit request is mandatory and fails with a clear message when the host cannot build it: `--with-rust-client=yes|side-by-side`, `-DWITH_RUST_CLIENT=ON`, `--with-rust-tls=yes` / `WITH_RUST_TLS=ON`, `-DZOOKEEPER_BUILD_SHARED=ON`, a named TLS provider, `--with-rust-tls-default-paths` / `ZK_RUST_TLS_DEFAULT_PATHS`, `--with-rust-workspace` / `ZKRS_WORKSPACE`, an explicit crate source, `--with-rust-staticlib` / `ZKRS_STATICLIB`, and `--with-rust-target` / `Rust_TARGET`. When `--with-rust-client` / `WITH_RUST_CLIENT` is not given and the default is `no` / `OFF` (before M5), an explicit Rust-only option stops configure or CMake with a message that names the option and `--with-rust-client=yes` / `-DWITH_RUST_CLIENT=ON`; an explicit `--with-rust-client=no` / `-DWITH_RUST_CLIENT=OFF` ignores these options. `--with-openssl` / `WITH_OPENSSL` and `--with-sasl` / `WITH_CYRUS_SASL` keep their legacy detection: an absent library gives a warning and a build without the feature. Under Maven the Rust module stays opt-in.
- **Root-pom properties.** `rust-client` (default `no`; `yes` and `side-by-side` map 1:1 to `--with-rust-client=`; there is no `auto` under Maven), `rust-tls` (default `no`; maps to `--with-rust-tls` and to the zk-ffi feature set), `rust-tls-provider` (default `ring`; `aws-lc-rs`, `aws-lc-rs-fips`), `rust-system-crates` (empty by default, which means off; the system-crates mode of §2.8), `rust-cargo-vendor` (empty by default, which means off; a `cargo vendor` directory used as an offline source replacement for an offline or release build, §2.8, which excludes `rust-system-crates`; 01 §13.1) and `cargo.executable` (default `cargo`). `c-client-openssl` and `c-client-sasl` keep their names and pass through unchanged.
- **TLS decision under Maven.** The Rust module builds before configure runs. It therefore takes the TLS decision with `zookeeper-client-c/abi/tls-probe.sh` (01 §13.7), which reproduces configure.ac:42-67 for the Maven build and emits the default trust paths. TLS is built when the probe finds OpenSSL or when `rust-tls` is `yes`.
- **Phase mapping.**

  | Maven phase | Rust module |
  |---|---|
  | generate-sources | `antrun` mkdir `target/cargo`. `zookeeper-jute` runs the execution `generate-Rust-Jute` (`Rcc -l rust`). |
  | process-sources | A check of the `rust-client` value (no, yes, side-by-side), then `${cargo.executable} --version` (fails early when cargo is absent), then a version check that compiles no workspace code: antrun compares the versions that `${cargo.executable} --version` and `rustc --version` print with 1.85 and fails with "Building the Rust client needs Rust 1.85 or later", then the TLS decision with `abi/tls-probe.sh`. `cargo fetch --locked` unless `-Dcargo.offline`, `rust-cargo-vendor` or the system-crates mode is set (§2.8). |
  | compile | Two separate cargo invocations. The drop-in staticlib: `cargo build --locked --profile capi -p zk-ffi --features <set>`, with no `--workspace`, because a workspace build would unify zk-client features (tokio, std threads) into the staticlib. `<set>` comes from the C build options: `tls,tls-${rust-tls-provider}` when TLS is enabled (§2.5.6; under Maven, by the `tls-probe.sh` decision and `rust-tls`), otherwise empty, and empty in every Maven build before M3 (01 §13.2). The native crates: `cargo build --locked --workspace --release --exclude zk-ffi`. Environment: `CARGO_TARGET_DIR=${project.build.directory}/cargo`, `ZK_VERSION_H`, `base_dir`, `CALLER=ANT`, and `ZK_TLS_DEFAULT_CERT_FILE`/`ZK_TLS_DEFAULT_CERT_DIR` from `abi/tls-probe.sh`. |
  | test | Profile `cargo-test` (active unless `-DskipCargoTest`; honors `skipTests`): `cargo test --locked --workspace --exclude zk-ffi` and `cargo test --locked -p zk-ffi --features <set>`, with `<set>` as in the compile row (the TLS features), starting the server through `zookeeper-client-c/tests/zkServer.sh`; logs in `target/cargo/TEST-*.txt`. |
  | verify | Profile `rust-lint` (active unless `-DskipRustLint`): `cargo fmt --check`, `cargo clippy` with explicit feature sets, `cargo xtask ledger check`. The C module runs `make abi-check` at verify when `rust-client≠no` and cargo is available (01 §13.7). Profile `rust-supply-chain` (opt-in, activated explicitly with `-Prust-supply-chain`): `cargo deny check` (with `deny-fips.toml` for the FIPS set), `cargo vet --locked`, `cargo audit` and the closure golden diff. |
  | package | None, except that with `rust-client=side-by-side` the module runs `dev/gen-license-binary.sh` for the convenience lib package (01 §13.5). The native crates are not packaged as `.crate` files: every `Cargo.toml` has `publish = false`, and the crates ship in the ASF source release only (K25). |

  Profiles `rust-test-coverage` (`cargo llvm-cov`) and `rust-test-asan` (nightly only) mirror `c-test-coverage` and `c-test-asan`.
- **Switches.** `-Drust-client=no|yes|side-by-side` selects the core. Defining `rust-client` (any value) or passing `-Prust` adds the Rust module and needs cargo ≥ 1.85; `side-by-side` also needs `cargo about` at package (01 §13.5). Without either, no Rust code builds, and `-Pfull-build` builds the legacy C client on a host without cargo. CI jobs that test Rust pass `-Prust` or `-Drust-client=…`.
- **C module.** Its `configure` execution passes `--with-rust-client=${rust-client}`, `--with-rust-staticlib=…/zookeeper-client-rust/target/cargo/capi/libzk_ffi.a`, `--with-rust-tls=${rust-tls}` and `--with-rust-tls-provider=${rust-tls-provider}`. The C module links the staticlib that the Rust module built and never builds Rust library code itself (its only cargo use is `cargo xtask` in `make abi-check`, 01 §13.7), so Maven builds the Rust code exactly once. A standalone autotools or CMake build without `--with-rust-staticlib` runs the same `-p zk-ffi` cargo build itself, under its build directory.
- **Jute path.** A Java `RustGenerator` beside `CGenerator` in `zookeeper-jute` (`Rcc -l rust`) writes `crates/zk-jute/src/generated/zookeeper_jute.rs` from the `generate-Rust-Jute` execution. The output is git-ignored, as `zookeeper-client-c/generated/` is, and listed in `zk-jute/Cargo.toml` `include`. When the file is missing, `zk-jute/build.rs` fails with a message that mirrors configure.ac's jute check. There is no generator crate and no committed generated file (01 §8).
- **Release.** The root pom version is the one version source. The antrun execution `replace-rustclient-files-during-release` rewrites `[workspace.package] version` and the `=` pins in `[workspace.dependencies]` in `Cargo.toml` (with `-SNAPSHOT` stripped) and updates `Cargo.lock` and `fuzz/Cargo.lock`. The `maven-release-plugin` preparation and completion goals run it in the modules of the release reactor, and the release `scm:add` includes these files. The release-plugin arguments do not carry `-Prust`, because under Maven the Rust module is opt-in. A release that includes the Rust module needs `-Prust` in its release builds (for example `-Darguments=-Prust`), cargo and rustc ≥ 1.85, network access or a `cargo vendor` directory (`-Drust-cargo-vendor=DIR`), and the `Cargo.toml`/`Cargo.lock` version rewrite; `-DskipRustLint` is optional (01 §13.4). `zk-ffi/build.rs` checks the version against `ZK_VERSION_H`, so a tree in which only the C rewrite ran does not build the Rust core. The native crates have `publish = false` and are not published to crates.io (K25). The source release includes `zookeeper-client-rust` without vendored crates (§2.8).
- **Convenience lib package.** Whether a release builds the C lib package, and whether with the Rust module, is the release manager's choice. With the Rust module it is built from `-Pfull-build -Drust-client=side-by-side -Drust-tls=yes -Drust-tls-provider=ring`, and it carries both cores: from the first opt-in release, the legacy core in `usr/lib/` and the Rust core in `usr/lib/zookeeper-rs/`, which a process opts into through the loader path; from M5, the Rust core in `usr/lib/` and the legacy core in `usr/lib/zookeeper-c/`. It adds the `LICENSE-binary` that `dev/gen-license-binary.sh` generates for the shipped closure and the Rust workspace `NOTICE` (01 §3.10, §13.5).
- **RAT.** Every new file that the excludes below do not cover carries the ASF header, including `.rs`, `build.rs`, `Cargo.toml`, `*.toml` outside `supply-chain/`, `xtask` source, shim C, `UNSAFE.md`, `shim/analyzer-suppressions.txt` and `.zks` scripts; `RustGenerator`, `cargo xtask gen`, the cbindgen configuration and `cargo xtask difftest` emit it. RAT excludes `**/Cargo.lock`, `**/supply-chain/imports.lock`, `**/supply-chain/audits.toml`, `**/supply-chain/config.toml`, `**/supply-chain/closure/*.txt`, `**/abi/*.tsv`, `**/abi/abixml/**`, `**/fuzz/corpus/**`, `**/abi/needed/*.txt`, `**/abi/layout/*.expect`, `**/abi/release-deltas/*.txt`, `**/tests/conformance/ledger.tsv`, `**/tests/conformance/tls/corpus/**`, `**/tests/conformance/sasl/*.pw` and the generated jute directory `**/crates/zk-jute/src/generated/**` (01 §13.6).
- **Toolchain and CI.** The MSRV is 1.85 and the edition is 2024. CI pins MSRV plus stable in every job that tests Rust and adds the jobs `full-build-rust-tests` and `full-build-dropin-cppunit` (08 §14). `full-build-rust-tests` runs `-Pfull-build,rust,rust-supply-chain verify -Dtest=_ -DfailIfNoTests=false -DskipCppUnit`, so it passes `-Prust` and `-Prust-supply-chain` explicitly (08 §14). Further CI jobs build the `aws-lc-rs` and `aws-lc-rs-fips` providers on Linux x86_64 and aarch64, and the system-crates mode against a Debian/Fedora-style crate directory (§2.8). `fuzz/` and the ctest crate `crates/zk-ffi-layout` are their own workspaces with their own lockfiles. The workspace-wide `cargo-test` and `rust-lint` invocations therefore never compile ctest, which needs rustc 1.88, and a 1.85 toolchain builds, tests and lints the workspace. The layout checks run in the stable CI job (01 §3.9). The Jenkins jobs need no Rust switch: they build `-Pfull-build` without `-Prust` on agents without cargo, and add `-Prust` once their agents have cargo ≥ 1.85 (08 §14). s390x enables the Rust module at M2.

### 2.8 Crate sources, security updates and distribution builds

Legacy links the system OpenSSL, so a distribution OpenSSL update patches its TLS without a ZooKeeper release. The Rust core links rustls and its provider statically. Two mechanisms carry TLS security updates (K23).

- **Advisory watch.** The CI job `advisories` runs `cargo audit` against the RustSec database and `cargo deny check advisories` over every closure golden, on every PR and daily on a schedule (08 §10 G10, §14). The closure goldens list the crates of each shipped configuration, so they show which shipped closures an advisory affects. A fix ships as a ZooKeeper release with the bumped crates, and the system-crates mode below is the fast path for distributions.
- **System-crates mode.** configure `--with-system-rust-crates` (CMake `ZK_SYSTEM_RUST_CRATES`, Maven property `rust-system-crates`) builds offline from a crate directory or local registry that the distribution provides, for example `/usr/share/cargo/registry`, through a source-replacement file that the build generates in its build directory (`<builddir>/cargo/system-crates.toml`, under Maven `target/cargo/system-crates.toml`) and passes to every cargo invocation with `--config` (01 §3.11), in place of the pinned set. In this mode:
  - `Cargo.lock` is regenerated against the system crates;
  - the closure-golden check (08 §10 G1) compares crate names and semver-compatible version ranges, not exact versions;
  - `cargo-vet` and `cargo-deny` still run, and the ABI goldens and every symbol and localization check still apply;
  - a CI job builds this mode against a Debian/Fedora-style crate directory.

  Distributions can therefore patch `rustls` or `ring` in place and rebuild, as they do for OpenSSL.
- **Crate fetching.** Nothing is vendored into git or into the source release, and no vendored crate tarball is a release artifact. Every build, a release build included, either fetches the crates (network access) or reads them from a `cargo vendor` directory, and with `--locked` cargo checks every crate against the hashes in `Cargo.lock`. Users who build offline run `cargo vendor` themselves and pass the directory with `--with-cargo-vendor=DIR` (CMake `-DZOOKEEPER_CARGO_VENDOR=DIR`, Maven `-Drust-cargo-vendor=DIR`) or use `-Dcargo.offline` with a populated `CARGO_HOME`; the build documentation shows the commands (01 §3.10). A release build without network access passes a vendor directory the same way, with `-Drust-cargo-vendor=DIR` (01 §13.4). The system-crates mode is the distribution path.

## 3. Key decisions

| # | Decision | Choice | Rationale |
|---|---|---|---|
| K1 | Crate graph | `zk-jute ← zk-proto ← zk-driver ← {zk-client, zk-ffi}`, and `zk-client ← zk-recipes`. zk-ffi never depends on zk-client or zk-recipes. Workspace `zookeeper-client/zookeeper-client-rust/`, crates under `crates/` (01 §2, §13.1). | Native-only code (tokio, tracing, native SASL, persistent watches) cannot reach libzookeeper through the graph, and feature unification cannot leak it in. rustls reaches zk-ffi only through zk-driver's `tls` feature. CI checks this with `cargo tree`. |
| K2 | Who calls application code | Only C. Callbacks for Rust-originated work run from `zks_drain` after the `zkrs_*` call returns; log lines emitted directly by C (05 §16.2) reach the log callback from the C frame that emits them. mt loops are C. Barrier/resume for continuations. | C++ exceptions, `longjmp` and re-entry behave exactly as in legacy (DSP-14 RE). No `C-unwind`. No internal lock is held across callbacks (fixes DSP-13). This includes the SASL password path: the password mutex guards only an in-block copy and never spans application code (§2.6 rule 5). |
| K3 | Private ABI ownership | c-shim (05) owns `shim/zkrs.h` (cbindgen, committed, drift-checked). No public C input struct crosses into Rust. The only public records that Rust touches are the result records that `abi::raw` writes (`struct Stat`, `String_vector`, `ACL_vector`, `ACL`, `Id`, `zoo_op_result_t`), through the hand-written `repr(C)` mirrors in `abi/legacy.rs` that `crates/zk-ffi-layout` checks (05 §1 rule 6, §10.1). The shim marshals `zoo_op_t`/`ACL_vector` into `zkrs_op`/`zkrs_acl`. | The union variant is chosen in C. There are no layout cookies or bindgen mirrors. |
| K4 | Host vtable | Pure or Blocking leaves only (CC-6). No entry can reach app code or `log_message`. Blocking leaves are callable only with the `&Unlocked` proof. No TLS or SASL entries. | Rust can never block or re-enter while it holds a lock. |
| K5 | Policy | One `zk_proto::Compat` (field names in 02 §14, values in 07 §2.1) with `LEGACY_C` and `NATIVE`, plus `DriverMode {interest, session_delivery}`. | Two profiles give a finite test matrix. Flavor never changes `Compat`. |
| K6 | Watch fan-out order | `LegacyWatchTable`, a safe-Rust port of hashtable.c with djb2 C-char signedness, differential-tested against the compiled C. | Bit-identical session fan-out order (WAT-05). |
| K7 | Randomness | `Rng{on_resolution, random, drand48}`. The drop-in uses the libc PRNG through the shim; native uses a per-handle SplitMix64. | Keeps the legacy process-global PRNG side effects (SRV-04 RE) without globals in Rust. TLS randomness comes from the crypto provider and never touches the libc PRNG. |
| K8 | xids | Per handle, wrapping to 1; seeded with `time(0)` by the shim and with 1 in the native API (02 §6.2). | Not app-observable (07 P6). Removes the wrap into reserved xids and st signed-overflow UB. |
| K9 | TLS (both profiles) | rustls 0.23 in `zk-driver::net::tls` (feature `tls`, `forbid(unsafe_code)`), sans-IO `RustlsConn` over in-memory buffers, the one `TlsConn` implementation. Provider `ring` (default, feature `tls-ring`), `aws-lc-rs` (feature `tls-aws-lc-rs`) or `aws-lc-rs-fips` (feature `tls-aws-lc-rs-fips`) (K24). Verifier from `Compat::tls_verify`: `LegacyChainOnly` for the drop-in, with the in-tree v1-leaf verifier for X.509 v1 leaves and its rules as the OpenSSL path post-check for v3 leaves (§2.5.2), and `WebPki` for native. Both profiles send close_notify on a graceful close (§2.5.5). OpenSSL is not used anywhere: no shim TLS file, no `tls_*` vtable leaves, no OpenSSL crate. §2.5. | Takes the TLS engine and its glue out of C and out of our unsafe surface. One TLS implementation serves both profiles. The driver keeps sole socket ownership (no SIGPIPE). `LegacyChainOnly` keeps the legacy trust decision, v1 leaves included, because operators follow the documented `ssl/gencerts.sh` examples, which make v1 leaves on OpenSSL ≤ 3.1. The remaining differences are DV-TLS-1..6. |
| K10 | SASL (drop-in) | Cyrus libsasl2, called only by C from SASL{START, STEP, DISPOSE} items on the IO owner, in two isolated TUs (`zks_sasl_cyrus.c`, `zks_sasl_cb.c`) behind the bounded `zks_bytes` interface, with generation-checked session lifetime, single-item serialization, the per-session `SASL_CB_PASS` trampoline, and the C coding, hardening and fuzzing rules. ZooKeeper-level quirks live in zk-proto's per-connection `SaslNegotiation`. §2.6. | The public SASL API is bound to Cyrus (`sasl_callback_t`, `zoo_sasl_params_t`), so the engine cannot move to Rust. Cyrus and `getpass` callbacks are application code (K2). The rules shrink the remaining C memory-unsafety to two audited, fuzzed files. One home for the quirks. |
| K11 | Results to C | The core decodes typed replies. zk-ffi's audited raw module (`abi::raw`, the only reader and writer of C memory) builds the legacy C result layouts: `String_vector`, `ACL_vector`, `Stat`, the string, data and multi result arrays, and the `Id`/`ACL` contents. It allocates through libc `malloc`/`calloc`, called from `abi::raw`, with the same `malloc`-or-`calloc` choice and the same size per object as legacy, from the same CRT as the shim. C owns delivery: the callback invocation and the legacy post-callback deallocation order, in `zks_drain`. Miri, the `zk-ffi-layout` tests and a fuzz target of the reply-to-C-layout writers under ASan cover the writers. | Pure data shaping is not in the C shim. The application's `free()`, `deallocate_*` and the generated jute deallocators work unchanged. Paths already chroot-stripped, multi parsed by wire type, lengths bounded. No second decoder. The unsafe surface stays inside the one audited module (01 §3.8; 08 G-rows). |
| K12 | Sync API | Shim wrappers call the exported `zoo_aX` with a marker (keeps interposition, ABI-06). Heap `zks_sync` record with refcount 2, filled by zk-ffi's raw writers on the completing thread at a barrier. C keeps the exported entry, the waiting and the record. After the waiting thread wakes, zk-ffi's raw writers copy out into the caller's buffers with the legacy rules (`buffer_len` truncation, the `path_buffer` NUL rules). | Keeps RC-13's checked ZSYSTEMERROR. No library thread writes another thread's stack. Cancellation-safe. The difference from legacy is unobservable. |
| K13 | Threads | C `pthread_create(NULL attrs)` / `_beginthreadex`. Thread role comes from C TLS. No `std::thread`, no `std::thread::current()` in the drop-in. | Default stack, signal mask and naming parity (DSP-01). No TLS destructors pinning the DSO (R7). |
| K14 | Dependency closure (drop-in) | **Base:** `rustix` (std,net,event,pipe,use-libc), `libc`, `errno` (rustix renames it `libc_errno`), `bitflags`, `linux-raw-sys`, `windows-sys`, and `zeroize` (default-features=false, features=["alloc"]). **TLS (feature `tls`):** `rustls` (default-features=false; `std`, `tls12`, provider), `rustls-pki-types`, `rustls-webpki`, `ring` (or `aws-lc-rs`/`aws-lc-sys`, or in the FIPS build `aws-lc-rs`/`aws-lc-fips-sys`), `untrusted`, `zeroize`, `pkcs8` 0.10 (`encryption`), `pkcs5` 0.7 (`pbes2`, `3des`, `sha1-insecure`), `der`, `spki`, `pem-rfc7468`, `base64ct`, `aes`, `des`, `cbc`, `cipher`, `md-5`, `sha1`, `sha2`, `pbkdf2`, `hmac`, `scrypt`, with their transitive closure. The `aws-lc-rs-fips` build leaves out pkcs8 `encryption`, pkcs5 `pbes2`/`3des`/`sha1-insecure` and the crates `pbkdf2`, `scrypt`, `hmac`, `sha1`, `aes`, `cbc`, `cipher`, `des` and `md-5` (01 §3.3 R3). No `rustls-pemfile`, no `rustls-native-certs`, no `openssl-probe` and no pki-types PEM API: the PEM reader is the RFC 1421 reader of 06 §3.1 (`pem.rs`) over `base64ct`, because it must see `Proc-Type`/`DEK-Info` headers. The transitive members (expected: `digest`, `subtle`, `once_cell`, `cfg-if`, `getrandom`, the other RustCrypto support crates, `rand_core` (through pkcs8 `encryption`, in the `ring` and `aws-lc-rs` builds only), and the build dependency `cc`) are whatever the per-target golden records. All pinned per target and provider in `supply-chain/closure/zk-ffi-<target>.txt` (TLS with `ring`), `zk-ffi-<target>-aws-lc-rs.txt` (TLS with `aws-lc-rs`), `zk-ffi-<target>-aws-lc-rs-fips.txt` (TLS with `aws-lc-rs-fips`) and `zk-ffi-<target>-notls.txt` (01 §3.3), all `cargo-vet safe-to-deploy`. In the system-crates mode the golden check compares names and semver-compatible ranges (§2.8). `log` is not in the closure (rustls `logging` off). | Every socket and poll syscall stays interposable through libc. The provider's OS randomness (`getrandom`) may use a raw syscall; legacy OpenSSL also drew randomness internally, so no interposable legacy call is lost. Audited third-party unsafe only; our crates forbid it. |
| K15 | Build | One `zk-ffi` staticlib (`capi` profile, panic=abort, fat LTO), built by `cargo build --locked --profile capi -p zk-ffi --features <set>` with no `--workspace`; the native crates are a separate `cargo build --locked --workspace --release --exclude zk-ffi`. The shim is compiled twice (±THREADED). The flavor reaches Rust at runtime. TLS presence follows the legacy `--with-openssl` / `WITH_OPENSSL` autodetect, or the opt-in `--with-rust-tls=yes` / `WITH_RUST_TLS` / Maven `rust-tls` (§2.5.6, §2.7). When TLS is enabled, `<set>` is `tls,tls-${provider}`, where `--with-rust-tls-provider` / `-DZK_RUST_TLS_PROVIDER` / Maven `rust-tls-provider` selects `ring`, `aws-lc-rs` or `aws-lc-rs-fips`; otherwise `<set>` has no TLS feature. `--with-sasl` selects only the two shim SASL TUs (SASL use reaches Rust per handle as `zkrs_init_args.sasl`, 05 §6). | Tested once, shipped twice. No double cargo build. Building zk-ffi alone keeps zk-client features (tokio, std threads) from unifying into the staticlib. |
| K16 | Link | Per flavor, `ld -r` (or `cc -r` on Mach-O) into one object, localized to golden ∪ `static-symbols.tsv` (161 + 18 `oa_*`/`ia_*`). Version script or exports list on top for the `.so`. | No `zks_*`/`zkrs_*`/Rust std/ring/aws-lc globals in the `.so` or `.a`. Two Rust staticlibs can coexist in one link. Interposition preserved (no `-Bsymbolic`). |
| K17 | Golden ABI data | `abi/symbols.tsv`, `absent.tsv`, `static-symbols.tsv`, `needed/<os>.txt`, `layout/`, `abixml/` (libabigail references: the pinned reference build `ref-pinned` and the releases 3.9.6 and 3.8.7), `release-deltas/`, `log-sites.tsv` (CC-30). ## 6. Release prerequisites

These items are not design decisions. Each must be true before the release or milestone gate that it names.

1. **ASF legal review of the aws-lc builds.** The ASF legal review of `aws-lc-sys` and `aws-lc-fips-sys` (which include OpenSSL-licensed code) must pass before any release ships an `aws-lc-rs` or `aws-lc-rs-fips` build (K24). Until then, releases ship the `ring` provider only; `ring` stays the default in any case.
2. **Infrastructure.** Each requirement of 08 §15.6 must be in place before the first milestone gate that uses it (its 'Needed from' column), among them the dedicated performance runner, the MIT Kerberos KDC container and the CI images with OpenSSL 3.0 and 3.5 LTS (at the latest patch when M3 starts, then frozen) that serve as test-only oracles (08 §4.1, §5.2).
3. **Windows fallback.** If the M4 Windows spike fails, the release ships Windows on the legacy core with DV-BLD-7 in its release notes, and the Rust core ships on Windows only in the first release whose Windows build passes the M4 exit criteria of 08 §15.3 (CC-33).
