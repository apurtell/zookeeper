# Compatibility Ledger: legacy C client quirks, defects and undocumented behavior vs. the Rust drop-in

## 1. Purpose and how to read the ledger

This ledger lists every behavioral quirk, latent defect and undocumented behavior of `zookeeper-client-c` (at 60da6eb50), with the drop-in decision for each. It is authoritative for behavior. Only the overview is above it: the key decisions K-n (00 §3) and the cross-cutting contracts CC-n (00 §4), which include the TLS design of 06 §3 and the SASL design of 06 §4. For behavior, a row here is the reference for every other document.

Three things are built and tested against the ledger: the values of `zk_proto::Compat::LEGACY_C`, the C shim, and the conformance suite. The ledger gate (`xtask ledger check`, §3) enforces the link between the rows, the constant and the tests. Each row states the behavior of the one drop-in, which is `LEGACY_C` plus the shim. That behavior includes the nine behavior fixes of the Rust core (DV-FIX-1..9, §5.1, §5.2). The rows they change (SRV-01, SRV-02, ST-18, WAT-10, PTH-05, RC-16, PTH-01, PTH-04, ST-13, SRV-09, ST-08, and the follow-on effects in ST-03, ST-06, ST-14, INIT-15 and RC-05) name the registered deviation. If a behavior is not listed, the drop-in must match the reference library. A test that finds an unlisted difference is a bug in the drop-in, not in the ledger.

Ref abbreviations: `zk.c` = src/zookeeper.c, `mt` = src/mt_adaptor.c, `st` = src/st_adaptor.c, `ht` = src/zk_hashtable.c, `rio` = src/recordio.c, `sasl.c` = src/zk_sasl.c, `log` = src/zk_log.c, `av` = src/addrvec.c, `ad` = src/zk_adaptor.h, `H` = include/zookeeper.h, `JR` = zookeeper-jute/.../JRecord.java. Line numbers are at 60da6eb50.

**Classification codes** (Class column):

| Code | Meaning |
|---|---|
| **RE** | REPRODUCE-EXACT. The drop-in shows the same behavior through the API. |
| **FU** | FIX-UB-ONLY. In C the behavior is UB, a crash, memory or wire corruption, or a deadlock-class liveness failure (P2). The fix changes nothing a correct application can depend on. |
| **DV** | DEVIATE-VISIBLE. A correct application could observe the change. Each one is a registered deviation with release-note text (§5.1). Every DV row names its register ID (DV-ABI-n, DV-BLD-n, DV-TLS-n, DV-FIX-n). |
| **NO** | NATIVE-ONLY. Only the Rust API differs. The C ABI is unchanged. |
| **P6** | NOT APP-OBSERVABLE. Principle P6 below applies. The row is not reproduced and needs no gated test. |

**Classification principles.** They make the class of borderline rows deterministic.

- **P1 Nondeterminism envelope.** Where C's outcome depends on scheduling or timing, choosing one outcome C can already produce is RE. Examples: a reply racing a concurrent close, when an auth packet goes out, two concurrent `zoo_add_auth` calls.
- **P2 Liveness.** Permanent hangs, CPU spins, unbounded blocking and self-deadlocks count as deadlocks. They may be fixed as FU only if the fixed drop-in then behaves as C does when the trigger is absent, or as C does on a sibling code path.
- **P3 Lifetimes.** A borrowed output may stay valid longer than in C, never shorter. Content read after the documented lifetime is unspecified.
- **P4 Hostile or malformed server input.** C's handling of malformed frames is UB (over-reads, garbage structs, NULL derefs), so bounding it is FU. A well-formed server sees identical behavior.
- **P5 Unspecified values.** Where C leaves a value indeterminate (stale errno), the drop-in may define it. P5 does **not** license writing out-parameters that C leaves untouched: an untouched output is a defined value (the caller's).
- **P6 Not app-observable.** Syscall sequences, allocation order inside the core, xid values and xid scope, TLS record boundaries and the close_notify alert on a graceful close, key order inside SetWatches vectors, internal symbols absent from the `.so`, thread names. Listed in §4.20 and deliberately not reproduced.
- **P7 OOM.** Where C checks an allocation and returns an rc or errno, the shim keeps that check and that rc (ENOMEM at init, ZSYSTEMERROR from the sync record, ZSYSTEMERROR from `zoo_add_auth`). Where C's allocation is unchecked (a NULL dereference follows), the drop-in aborts. Allocation failure inside the Rust core aborts, with two exceptions: request encoding calls `try_reserve_exact` before it encodes and maps a failure to ZMARSHALLINGERROR, as C's serialization stage does; and the `zoo_add_auth` credential copy maps a failure to ZSYSTEMERROR, as C's checked `calloc` does. Auth-frame encoding is infallible and aborts on OOM.
- **P8 Emission point.** A callback or log line produced during one `zkrs_*` call is delivered before the exported function returns (application thread) or before the library thread blocks again, on the same thread, in the same relative order as C. Its position relative to internal state changes inside that one call may differ from C. That is observable only to a callback that re-enters the API in the middle of a library call, which C itself runs under internal locks at most sites (DSP-13). These cases are classified RE.

**Layer column.** `proto:<field>` is a `zk_proto::Compat` field (§2.1). `mode:<field>` is a `zk_proto::DriverMode` field (§2.2). `proto` is zk-proto logic without a knob. `drv` is zk-driver. `tls` is zk-driver `net::tls` (rustls, §2.5). `ffi` is zk-ffi. `ffi:raw` is zk-ffi's audited raw module (`abi::raw`), the only Rust code that reads or writes C memory; it builds the legacy C result layouts and performs the sync copy-out. `shim` is C code in the shim that always implements the legacy behavior, or the fixed behavior of DV-FIX-5 and DV-FIX-6. `shim:sasl` is one of the two Cyrus translation units, `shim/zks_sasl_cyrus.c` and `shim/zks_sasl_cb.c` (§2.5).

**Test column.** Suite names follow 08. `[diff]` means the reference library and the drop-in must produce equal traces under verification mode EXACT, PER-ROLE or SET; the `[diff]` tier runs the one shipped drop-in against the pinned legacy reference (08 §4.1). `[dev]` means verification mode DEV: the drop-in is checked against its new behavior. The legacy behavior that a DV-FIX row changes is asserted on the reference. Other reference behavior (crash, hang, corruption, the OpenSSL TLS decision) is characterized in a forked child and recorded (08 §4.3). Every case that a fix touches is a `[dev]` test registered under its DV-FIX row. All other cases stay EXACT. `proto::`/`golden.`/`abi.`/`shim.`/`fuzz/` tests are unit, golden or fuzz tests.

## 2. Normative cross-document contracts

### 2.1 The single `Compat` policy (type and names owned by zk-proto; values owned here)

There is exactly one `Compat` type. It lives in zk-proto, is fixed when a handle is constructed, and is read by every transition. 02 (zk-proto) owns the type, the field names and the variant names. This ledger owns the values of `LEGACY_C` and `NATIVE`, and the ledger gate checks that the constants equal the table below. Behavior that is purely C-ABI shaping (rc funnel, buffer copies, multi result-array writes, `zerror`) is in the shim and has no knob. Settings that differ per driver rather than per profile are in `DriverMode` (§2.2).

Only `LEGACY_C`, and `NATIVE` with the per-client overrides of 04 §19.2 (`max_frame_len`, `resolve_cadence`, `tls_verify`), exist in shipped code. The C shim never overrides `LEGACY_C`, so the test matrix is the two profiles. `LEGACY_C` is the single drop-in value and includes seven of the nine behavior fixes: `server_cursor = SingleAdvance` (DV-FIX-1), `addr_eq = IpAndPort` (DV-FIX-2), `sasl_failure = Teardown` (DV-FIX-3), `set_watches_batch = Some(128 KiB)` (DV-FIX-4), `chroot = LegacyConcatNoEscape` (DV-FIX-7), `forced_close = Teardown` (DV-FIX-8) and `rw_switch_rc = ConnectionLoss` (DV-FIX-9). DV-FIX-5 and DV-FIX-6 are shim code (§5.2). `rw_switch_rc`, `forced_close`, `server_cursor`, `addr_eq`, `sasl_failure` and `set_watches_batch` have the same value in both profiles; they stay fields because each is the named mechanism of a DV-FIX row and a ledger row (02 §14.1).

These behaviors have a single value and are not knobs:
- Multi sub-results are always parsed by the wire `MultiHeader.type` (MUL-07).
- The TLS handshake deadline is TCP-connect completion + 2/3·T in both profiles (ST-16).
- A TLS configuration failure returns ZSSLCONNECTIONERROR without a teardown in both profiles (ST-17).

`SaslFailure::Teardown` (ST-18, DV-FIX-3; 02 §7.4): the state becomes AUTH_FAILED (-113) in the core call that sees the failure, and a `Cause::SaslTeardown` teardown follows the path of C's digest-auth failure (AUT-04). The socket is closed, the AUTH_FAILED session event goes out, and all pending sync, async and auth work fails with ZAUTHFAILED. The call that drives the failure returns the SASL rc. In mt the event and the async results run on the dispatch thread, the sync and auth results run on the IO thread at their barriers, and the IO thread then exits while the dispatch thread stays until close. In st everything runs inside the driving call. The Cyrus session is disposed at the final close, as C does.

`ForcedClose::Teardown` (ST-13, DV-FIX-8; 02 §12.3): inside the API call the state becomes 999, the transport is flagged for closing, `tx`, the FIFO and the pending auth tokens are taken as one snapshot, and no callback runs, so the call's outbox holds LOG items only. The IO owner's next driving call runs the remaining stages as a `Cause::ForcedClose` teardown: the CONNECTING event if the state was connected at the trigger, then ZCONNECTIONLOSS for the snapshot alone. The state stays 999, no delay is set and the cursor does not move. A request submitted after the trigger stays queued whole and goes out on the next connection. A close before T3 starts gives the snapshot and later work ZCLOSING and no event.

`CloseMode::LegacyFailPending` (CLS-01, CLS-02): `begin_close` fails every pending entry with ZCLOSING at once, keeps the unsent frames in `tx`, and the final close flushes them before CLOSE_OP. `Drain` is native: the FIFO is kept and CLOSE_OP goes behind the queued frames.

**Teardown rc per zk-proto `Cause` (02 §12)** under `disconnect_rc = PerCause` (`LEGACY_C`):

| Cause | rc to pending work | Session event | Post-state |
|---|---|---|---|
| ConnectFailed, Io, Eof, ProtocolError | ZCONNECTIONLOSS | CONNECTING if it was 3 or 5 | 0 |
| SocketCreate (incl. empty list, SRV-08) | ZSYSTEMERROR | — | 0 |
| Tls (handshake failure, TLS resource failure) | ZSSLCONNECTIONERROR | — | 0 |
| RecvTimeout, TlsHandshakeTimeout | ZOPERATIONTIMEOUT | CONNECTING if it was 3 or 5 | 0 |
| XidMismatch (incl. empty FIFO) | ZRUNTIMEINCONSISTENCY | CONNECTING if it was 3 or 5 | 0 |
| SessionExpired | ZSESSIONEXPIRED | EXPIRED | -112 |
| AuthFailed (digest reply) | ZAUTHFAILED | AUTH_FAILED | -113 |
| SaslTeardown (DV-FIX-3, ST-18) | ZAUTHFAILED | AUTH_FAILED | -113 |
| RwServerFound (DV-FIX-9, ST-08) | ZCONNECTIONLOSS | CONNECTING | 0 |
| ForcedClose (DV-FIX-8, ST-13) | ZCONNECTIONLOSS | CONNECTING if it was 3 or 5 | 999 |
| `begin_close` (not a Cause) | ZCLOSING | — | unchanged |

`TransportFailure::TlsConfig` (ST-17) is not a teardown, in both profiles.

### 2.3 Callback-frame rule, outbox protocol and thread model (normative for 01, 03 and 05)

**No application code ever runs with a Rust frame on the stack, on any thread.** Application code means completions, watchers, auth completions, log callbacks and Cyrus SASL callbacks (password, getpass, GSSAPI). Every thread that can run application code enters Rust only through `zkrs_*` calls that return before that code runs.

**Outbox protocol** (shape owned by 05 §5):
- Every `zkrs_*` call that can produce application-reaching work takes a `zkrs_outbox` that lives on the C stack. The call returns `zkrs_step { DONE, MORE, RELEASE, EXIT }` (or `zkrs_status` for submits) and leaves an ordered list of items in the outbox.
- C drains the items with `zkrs_outbox_next`/`zkrs_outbox_finish` in `zks_drain`. Callbacks for Rust-originated work run from `zks_drain` after the `zkrs_*` call returns; log lines emitted directly by C (05 §16.2) reach the log callback from the C frame that emits them. On `MORE`, Rust has stopped at a barrier; C drains, then calls `zkrs_resume`. On `RELEASE`, C drains, then frees `zh` and drops its reference.
- A C++ exception from a callback unwinds through `zks_drain`; its cleanup handler calls `zkrs_outbox_requeue`, and the handle delivers the untaken items at the start of the next driving call.
- Item kinds:

| Item | Content | C action |
|---|---|---|
| LOG | `LogSite`, level, arguments, wall-clock time stamped by zk-ffi | re-check `logLevel`, format, emit |
| RESULT | token plus the result; async, sync and auth results, told apart by the `zks_req` mode. zk-ffi's raw writers (`ffi:raw`) build the legacy C result layouts with libc `malloc`/`calloc` (05) | invoke with the built structures, then free them in the legacy post-callback order; or `zks_sync_complete` has zk-ffi's raw writers (`zkrs_write_result`) build the reply into the heap `zks_sync` record, then signals the waiter (05 §13) |
| WATCH | node or session event view with the watcher list | invoke each watcher; free the path after the batch |
| AUTH_LOCKPOINT | none | call the exported `zoo_lock_auth(zh); zoo_unlock_auth(zh);` (`zks_auth_lockpoint`, 05 §19.9; mt locks and unlocks `zh->auth_lock`, st returns 0) |
| SASL{START, STEP, DISPOSE} | generation, bounded byte views; for START, the local and peer addresses as `zkrs_bytes` that hold the platform `sockaddr_in`/`sockaddr_in6` image (`zkrs_sasl_call`, 05 §19.2) | call the Cyrus glue (§2.5) with the item's gen; after a START that is not STALE, `zks_sasl_set_gen`; then `zkrs_sasl_result(core, gen, view)`, except for DISPOSE and for a START or STEP the glue rejected as STALE |
| THREAD{JOIN \| DETACH, IO \| DISPATCH} | role | `pthread_join` or `pthread_detach` on the C thread handle |

- **Barriers** (Rust returns `MORE` right after the item): auth completion groups and AUTH_LOCKPOINT (all flavors), session events in st (`Session{barrier}` and `DrainPoint`), each run of sync results (Direct completions) in the mt IO step and in close (the waiters are signalled before later frames are processed, as C does; consecutive Direct results with no callback item between them share one barrier, which keeps the order, because nothing observable runs between them), SASL START and STEP items, every THREAD item (JOIN or DETACH, IO or DISPATCH), and pending LOG items before every Blocking vtable call (`resolve`, `rng_reseed`) and before the TLS file reads of the IO step (C drains and emits the lines from a C frame, then `zkrs_resume` continues into the blocking call), and before any wait: a step that would block in `poll`, in the close flush or close wait, or in the RW probe first returns `MORE` when LOG items are pending in its outbox, so each line reaches the log callback before the wait, as in legacy (01 §3.6 CF5, 03 §3.3). SASL DISPOSE is ordered by the outbox, not a barrier. With SASL params, `zkrs_handle_new` also stops at the SASL point after resolution and the reseed and before the mt waker, with no item before it, so C creates the SASL session in the legacy order (05 §5, §15.1).

**Thread model, `libzookeeper_mt`:**
- **Application threads.** `zoo_a*` submit and drain the (usually empty) outbox before return. `zoo_add_auth` holds `auth_lock` around `zkrs_add_auth` (lock order auth → core). Sync wrappers calloc a heap record, call the exported `zoo_aX` with the sync marker, wait, then copy out (K12). `zookeeper_close` from a foreign thread drains ZCLOSING sync and auth completions here, then THREAD JOIN items, then the final close and RELEASE. The final close closes the transport first and then emits SASL DISPOSE if a Cyrus session exists, the order of legacy destroy (zk.c:719-749). A forced close from `zoo_set_servers` only marks the transport; the IO thread closes it and runs the rest of the teardown.
- **IO thread.** A C loop in `shim/zks_threads.c` that calls `zkrs_io_step`, drains and resumes while the step is `ZKRS_MORE`, drains once more, and repeats until `ZKRS_EXIT` (05 §15.2). One step is at most one interest/poll/process iteration and returns early at every barrier. Sync results, auth completions (after an AUTH_LOCKPOINT), SASL items and IO-thread log lines are drained here. `getaddrinfo` and the libc PRNG reseed run in Blocking leaves with no Rust lock held, after the pending log lines are drained.
- **Dispatch thread.** A C loop over `zkrs_wait_dispatch(core, &ob, &rc)`, which blocks in Rust on the FIFO and returns a batch. Async completions, node watch events and session events are drained in proto stream order. "Calling COMPLETION_*" DEBUG lines are emitted here, from the `delivery_logs` of each RESULT (02 §5.1).
- **Thread creation and identity.** C creates both threads with `pthread_create(&t, NULL, …)` (`_beginthreadex` on Windows). The role (foreign, IO, dispatch) comes from C thread-local storage (`zks_current_role`) and is passed to Rust as an argument. The drop-in uses no `std::thread` and no `std::thread::current()`.
- **Start.** Start uses a three-party latch (IO, dispatch and init thread). `zh->core` is stored before the first `pthread_create`. Callbacks may run before init returns, as in C.
- **Close.** Keyed on the caller's role: a foreign thread joins both library threads; the dispatch thread joins IO and detaches itself; the IO thread detaches itself and joins dispatch. ZCLOSING auth completions are drained before the join, as in C. The final close runs on whichever thread drops the last reference. A close while another close is in progress is a ZOK no-op (CLS-05).

**Thread model, `libzookeeper_st`:** no library threads and no waker. All work runs on the caller inside `zookeeper_interest`, `zookeeper_process`, `zookeeper_close` and `zoo_a*`. Callbacks run inline in the shim's drain at session-event barriers, at `DrainPoint`s and at the end of the call. A `zoo_a*` call runs no completion or watcher callback. A forced close inside one sets state 999 and closes the socket, and its outbox holds LOG items only; the next `zookeeper_interest` or `zookeeper_process` call delivers the event and the results (02 §12.3). A close from inside a callback is deferred to the enclosing call's epilog, which then returns its own rc with `zh` already released.

**Host vtable (what Rust may call).** Only leaves that cannot reach application code or `log_message`:
- **Pure** (non-blocking, may be called with Rust locks held): `discard_token`, `snapshot_default_watcher`, `store_client_id`, `log_enabled`, `conn_permute_disabled`, `rng_random`, `rng_drand48`.
- **Blocking** (callable only with the `&Unlocked` proof, no Rust lock held): `rng_reseed`, `resolve`.
- The vtable has no other entries. TLS has no vtable entry (rustls runs in zk-driver, 06 §3.1). SASL, threads, log emission, delivery and the auth mutex are outbox items, not vtable entries.

Consequences:
- DSP-13 (callbacks under internal locks) is fixed, and DSP-14 (C++ exceptions) is RE on every thread. An exception thrown from any callback unwinds through C frames only: to the application on application threads, or to the thread start routine on library threads, where the process terminates as in C.
- No `extern "C"` Rust frame ever sees a foreign unwind, so no `C-unwind` ABI is needed.
- The sync-before-FIFO order (DSP-03) holds because a Direct completion is a RESULT item in the producing thread's outbox, closed by a barrier (one per run of Direct results), while queued completions and events go to the dispatch FIFO. Both are pumped into the producing call's outbox under the core lock in proto stream order; queued items reach the FIFO when `zkrs_outbox_next` reaches them (03 §3.4). No C code runs under the core lock.

### 2.4 Tokens, validation and submit status

- **Completion token:** `CReq(NonZeroUsize)` holding a shim `zks_req *`. Rust never turns it back into a pointer. It reaches C exactly once, as a RESULT item or through the Pure leaf `discard_token`. Dropping a token in Rust calls `discard_token`: an async request is freed uninvoked; a sync record gets ZCLOSING and is signalled. A token still alive after host release aborts with a diagnostic.
- **Watcher token:** `(fn, ctx)` as two `usize`, compared by value.
- **Validation order (RC-01):** zk-proto `submit` runs the legacy order under `LEGACY_C`, using the pure legacy functions in zk-proto (`legacy::is_valid_legacy`, `legacy::prepend`, `legacy::strip`, `legacy::parse_init`, `legacy::parse_servers`), and returns the final legacy code in `SubmitError.code`. zk-ffi only converts raw inputs (in its audited raw module (`abi::raw`)) and passes `InputDefect` flags (bad value buffer, BAD_ACL, shim marshal OOM), which proto reports at the stage legacy would reach. The shim checks only the entry preconditions that legacy checks before any core state, or that replace a crash: NULL `zh`, `scheme`, `hosts`, `cert`, sync out-pointers and the sync remove-watches path, `delay < -1`, and NULL `ops`/`results` with `count > 0` (05 §12-§17).
- **`zkrs_status`** (owned by 05): `OK`, `OK_LOCAL`, `EARLY_BADARGS`, `EARLY_STATE`, `LATE`, `UNIMPLEMENTED`, `NOWATCHER`, `SYSTEM`. zk-ffi maps the proto code to it, and the shim funnel maps it to the rc. **The token is retained iff the status is `OK`.** `LATE` maps to ZMARSHALLINGERROR. There is no second retained state: `zoo_add_auth` encoding is infallible (P7), so its send-queue failure is unreachable.

### 2.5 Injected legacy implementations

- **`Rng`** (SRV-03, SRV-04): `Rng { on_resolution, random, drand48 }`. The drop-in implementation is `ShimRng`, the shim's libc PRNG through the vtable:
  - `random` → Pure leaf `rng_random` (libc `random()`); `drand48` → Pure leaf `rng_drand48`;
  - `on_resolution` is empty. The reseed (C's `setup_random()`: `srandom` and `srand48` from `/dev/urandom`, getpid fallback) is the Blocking leaf `rng_reseed`. The driver calls it in its unlocked resolve step, after the `resolve` leaf returns and before it relocks to call `handle_resolved`, on every path, `zoo_set_servers` included (02 §9.4), and only when `shuffle = !zoo_deterministic_conn_order` (read through `conn_permute_disabled`) is true and at least one address resolved (zk.c:1028-1038). The libc call order on that thread stays: reseed, then the shuffle's `random()` calls, then the rebalance `drand48()` calls;
  - reconfig always draws `drand48`, also in deterministic mode;
  - on Windows `rng_reseed` does nothing, `rng_random` calls `rand()` and `rng_drand48` returns `(double)rand()/RAND_MAX`, as legacy.

  The native implementation is a per-handle SplitMix64 in zk-client.
- **Resolver** (INIT-03/04, SRV-05): the Blocking leaf `resolve` performs `getaddrinfo` with the legacy hints and retry, keeps AF_INET/AF_INET6 in order (duplicates included) and reports each skipped family as data, maps EAI codes to errno, logs nothing, and returns errors as data. Rust emits the platform's legacy site (`Win32 message: %s\n` on Windows, `getaddrinfo: %s\n` elsewhere) with a `GAI_STR` argument that C renders with `gai_strerror` on Windows and Linux/GCC and with `strerror(errno)` elsewhere, as zookeeper.c:982-988.
- **Log sites** (LOG-03/04): the `(func, line, level, fmt)` table `zookeeper-client-c/abi/log-sites.tsv` generates the `LogSite` enum in zk-proto (committed) and `shim/zks_log_sites.h`. It is pinned to the final legacy C-core commit on main before the Rust core becomes the default: `cargo xtask log-sites` extracts it from the C core at that commit and re-extracts it whenever the pin moves. Legacy C-core changes may move or change log sites freely; the table follows the pin. zk-ffi stamps wall-clock time when it pumps each Log output into the outbox, so zk-proto stays clock-free. C re-checks `logLevel` at emit time and renders the line.
- **TLS** (TLS-*, 06 §3): `rustls` 0.23 in `zk-driver/src/net/tls/` (`#![forbid(unsafe_code)]`). The cargo feature `tls` needs exactly one provider feature: `tls-ring` (the default provider), `tls-aws-lc-rs` or `tls-aws-lc-rs-fips` (`--with-rust-tls-provider=ring|aws-lc-rs|aws-lc-rs-fips`, CMake `ZK_RUST_TLS_PROVIDER`, Maven `rust-tls-provider`). zk-driver and zk-ffi use the same feature names. `tls` with no provider or with more than one stops the build with `compile_error!`. The FIPS build uses aws-lc-rs `fips` (`aws-lc-fips-sys`), rustls `fips` with `require_ems`, and only FIPS-approved suites, groups and signature algorithms; it asserts `provider.fips()` at handle creation and checks `ClientConfig::fips()` per attempt (06 §3.15.2); its validation scope is Linux x86_64 and aarch64 (06 §3.15.4). One implementation, `RustlsConn`, drives a `rustls::ClientConnection` over in-memory buffers; the driver owns the socket and all sends. The drop-in verifier is `LegacyChainOnly`, a custom `ServerCertVerifier` whose rules are exactly 06 §3.5. The reference OpenSSL lines are 3.0 and 3.5 LTS; 1.1.1 is out of support and is not a reference.
  - (a) a leaf that is not OpenSSL-self-signed must chain to a trust anchor. A v3 leaf chains through `verify_server_cert_signed_by_trust_anchor`, plus the keyCertSign post-check (06 §3.5: error 32 when a sent certificate or trusted bridge that can lie on the path from the leaf by `check_issued` has keyUsage without keyCertSign, because webpki does not enforce keyCertSign on CA certificates; where OpenSSL's path does not use that certificate, as in the order-dependent same-name case, the stricter verdict is DV-TLS-3), the rejected-issuer post-check (06 §3.5), OpenSSL's keyUsage and Netscape cert-type rules, and the OpenSSL path post-check (06 §3.5): the issuer selection and finish rules of the v1-leaf verifier (06 §3.14.3) run over the leaf, the sent certificates and the trust set (trusted-first selection, `find_issuer` order, no sent certificate above a trusted bridge or a self-signed sent certificate, the ambiguity rule, keyCertSign on the chosen issuer, `check_ca`, every pathLenConstraint including the anchor's, and name constraints including `NAME_CONSTRAINTS_check_CN`), with the leaf's own EKU, keyUsage and nsCertType purpose and its subjectAltName, and the leaf is accepted only when webpki and all three post-checks accept. Intermediate candidates with `now >= notAfter` are dropped before path building, and the leaf is checked after webpki with OpenSSL's rule `notBefore <= now < notAfter`, so webpki's inclusive `notAfter` check never decides and no chain is accepted at `now == notAfter` (06 §3.5). A v1 leaf is accepted at any depth below a valid v3 chain, as OpenSSL accepts it, through the in-tree `#![forbid(unsafe_code)]` v1-leaf verifier (06 §3.14), which is the acceptance path for this case only (for v3 leaves the same module runs only as the OpenSSL path post-check): it checks the leaf signature against its issuer with the provider's `SignatureVerificationAlgorithm`, and then verifies the issuer chain to an anchor with OpenSSL's rules (basicConstraints and pathlen, keyUsage certSign, the `notBefore <= now < notAfter` rule, the `ssl_server` purpose, no sent certificate above a trusted bridge or a self-signed sent certificate). v1 intermediates are rejected as OpenSSL rejects them (`check_ca` returns 0, error 79, `X509_V_ERR_INVALID_CA`). The v1-leaf verifier is differentially tested against OpenSSL 3.0 and 3.5 (§3);
  - (b) a leaf byte-identical to a trust-set certificate is accepted **only when that certificate is OpenSSL-self-signed** (`EXFLAG_SS`, defined in full in 06 §3.4). The certificate must also pass OpenSSL's `check_issued`, the mimic rule must hold (among the trust-set certificates whose canonical subject equals the leaf's and that pass `check_issued` for the leaf, that certificate is the only one valid at `now`, or the only one at all; 06 §3.5), the leaf must be valid (`notBefore <= now < notAfter`), and the `ssl_server` purpose check must pass (a `CA:TRUE` leaf included); an aux trust list naming serverAuth or anyExtendedKeyUsage satisfies that check, as in 06 §3.14.3 Purpose. The leaf must have no critical extension outside the processed set of 06 §3.14.3 (error 34; aux trust does not override it). A self-signed leaf not in the trust set is rejected;
  - (c) no SNI is sent (`enable_sni = false`); the peer name is `ServerName::IpAddress` of the peer; there is no hostname check (`verify_server_name` is never called);
  - (d) anchors are self-signed or explicitly trusted (06 §3.5): only trust inputs that are OpenSSL-self-signed, CA-capable (`X509_check_ca`) and EKU-compatible with SSL server use become anchors, filtered by validity at verify time; trust inputs that are neither self-signed nor explicitly trusted are bridges, offered only as intermediates; a self-signed input that is not an anchor can be accepted only through path (b); in issuer selection (06 §3.14.3) it stays a trusted candidate, and a chain that selects it fails, as in OpenSSL (06 §3.4). A chain must end at an anchor (no `X509_V_FLAG_PARTIAL_CHAIN`); `TRUSTED CERTIFICATE` aux settings override the default rule as OpenSSL's `X509_check_trust` does: a trust list naming serverAuth or anyExtendedKeyUsage makes the input an anchor, and a reject list naming either, or a non-empty trust list naming neither, makes it a rejected issuer, which is never an anchor, a bridge or a rule-(b) match and fails the chain (error 28) when chain building selects it (06 §3.4). v1 self-signed anchors are accepted, as OpenSSL does;
  - handshake signatures are verified with the provider's `signature_verification_algorithms`, from the leaf's SPKI (so v1 leaves accepted by (a) or (b) work); before any path runs, a leaf whose own key type, curve, size or point form no provider algorithm verifies is rejected (`leaf_key_usable`, 06 §3.5; DV-TLS-3), because the chain checks read only issuer keys and path (b) verifies no signature; and resumption is disabled.

  No OpenSSL code or library is used by the library; OpenSSL is probed at configure time only to decide whether TLS is built (INIT-16). The legacy trust inputs and key formats are reproduced as listed in TLS-09 and TLS-10.
- **SASL** (SAS-*, 06 §4): Cyrus libsasl2, called only by shim C from SASL items with no Rust frame on the stack. The items are drained only on the IO owner: the mt IO thread, the st caller, or (for the DISPOSE of the final close) the thread that runs the final close after the IO thread is joined or has exited. The ZooKeeper-level quirks (op 102 framing, send gate, DIGEST-MD5 empty initial response, GSSAPI final packet, deferred CONNECTED) live in zk-proto's per-connection `SaslNegotiation`. The C side is hardened:
  - **Isolation.** Only `shim/zks_sasl_cyrus.c` (engine glue) and `shim/zks_sasl_cb.c` (`zoo_sasl_make_*_callbacks` and their callbacks) include `<sasl/sasl.h>`. Both are excluded when SASL is disabled.
  - **Interface** (06 §4.7.2; 05 mirrors it). The glue exposes `void zks_sasl_start(zks_sasl_sess *s, uint32_t gen, const zks_sasl_params *p, zks_bytes local, zks_bytes peer, zkrs_sasl_out *out)`, `void zks_sasl_step(zks_sasl_sess *s, uint32_t gen, zks_bytes challenge, zkrs_sasl_out *out)` and `void zks_sasl_dispose(zks_sasl_sess *s, uint32_t gen)`. Byte arguments are `zks_bytes` (the zkrs.h `zkrs_bytes { p, len, is_null }`). The output is `zkrs_sasl_out { status: CONTINUE|DONE|FAIL|STALE, mech, token }`. Server tokens are built by Rust from exact-length frames. `local` and `peer` carry the platform `sockaddr_in`/`sockaddr_in6` image that zk-ffi writes from the addresses that the driver reads with rustix `getsockname`/`getpeername`. The glue validates family and length, calls `getnameinfo(NI_NUMERICHOST|NI_NUMERICSERV)` and formats `"%s;%s"` with `snprintf` into bounded buffers, so the strings are byte-identical to legacy, IPv6 scope suffixes included. On a `getnameinfo` error it logs "getnameinfo: %s\n" at the legacy site (sasl.c:185). The params (service, host, mechlist) come from the session's own copies in `zks_sasl_params` (built in C with capped `strnlen`). `sasl_client_start` takes the mechlist from `p->mechlist`, the session's NUL-terminated copy; there is no separate mechlist accessor. The glue checks every view on entry. Lengths are `uint32_t` and checked against 0x7fffffff. Cyrus output is returned as a view and copied into Rust at once by `zkrs_sasl_result(core, gen, view)`. The zkrs.h item is `zkrs_sasl_call { kind, gen, local, peer, token }` (05).
  - **Lifetime.** `sasl_conn_t*` lives in a per-handle `zks_sasl_sess` with a generation counter that matches `SaslCall.gen`. The drain records the generation with `zks_sasl_set_gen`, which `shim/zks_sasl_cyrus.c` defines. The connection is disposed at the times legacy disposes it, then set to NULL: on a reconnect, by a DISPOSE item that zk-proto emits immediately before the next START in the same outbox (legacy disposes at the top of `zoo_sasl_connect`, sasl.c:215-217), and at the final close, by a DISPOSE item after `CloseTransport` (zk.c:719-749). A teardown or forced close alone emits no DISPOSE. The generation still advances at teardown, so a late reply to the old session is rejected as stale. The glue itself rejects a stale generation (status STALE, no Cyrus call), so the libFuzzer harness covers the check. When `sasl_client_new` fails, the glue disposes `*pconn` if it is non-NULL.
  - **Serialization.** At most one SASL START or STEP is in flight per handle, drained only on the IO owner, and dispose is ordered through the same outbox.
  - **Secret trampoline.** See DAT-13 (06 §4.7.6-4.7.7; helpers `zks_is_library_pass_cb` and `zks_getsecret_unlocked`). No internal lock is ever held across application code.
  - **Limits.** A callback array of `ZKS_SASL_MAX_CB` (4096) or more entries fails START, and a PASS request beyond `ZKS_SASL_MAX_SECRETS` (16) on one connection fails, both with SASL_NOMEM (SAS-14).
  - **Coding and build rules.** No `strcpy`/`strcat`/`sprintf`/`gets`/`strtok`; `snprintf` with truncation checks; every size computation through the portable checked-arithmetic macros `ZKS_ADD_OVF`/`ZKS_MUL_OVF` of `shim/zks_sasl_cb.h` (`__builtin_*_overflow` on GCC and Clang, explicit range checks on MSVC), and cleanup through `ZKS_CLEANUP` (`__attribute__((cleanup))` on GCC and Clang, explicit `goto out` cleanup on MSVC), with the glue written so that both forms are correct; `strnlen` with caps; `zks_secure_zero` on every secret copy before free; every Cyrus rc checked; no mutable global except the password mutex. Compiled on GCC and Clang with `-D_FORTIFY_SOURCE=3 -fstack-protector-strong -fstack-clash-protection -ftrivial-auto-var-init=zero -fno-strict-overflow -Wformat=2 -Wformat-security -Wconversion -Wsign-conversion -Werror`, plus `-fcf-protection` or `-mbranch-protection=standard` where supported. configure and CMake probe each hardening flag and drop one that the compiler or C library does not support, with a notice per dropped flag, in every build including releases (`_FORTIFY_SOURCE=3` falls back to 2, for example on glibc 2.28). `-Werror` is on by default and in CI; packagers turn it off with configure `--disable-werror` or CMake `ZK_WERROR=OFF`. The linked library carries no IBT/SHSTK/BTI property note, because the Rust objects carry none (DV-BLD-8).

### 2.6 Dependency closure assumed by the ledger

No ledger row needs a crate outside the pinned drop-in closure (K14). The closure is recorded per target and feature set in the goldens of 01 §3.3: `supply-chain/closure/zk-ffi-<target>.txt` (TLS on, `ring`), `zk-ffi-<target>-aws-lc-rs.txt` (TLS on, `aws-lc-rs`), `zk-ffi-<target>-aws-lc-rs-fips.txt` (TLS on, `aws-lc-rs-fips`) and `zk-ffi-<target>-notls.txt`. Every crate is `cargo-vet safe-to-deploy`, and the `cargo tree` closure diff of 01 §3.3 R4 (08 §10 G1) checks it. In the system-crates build mode (`--with-system-rust-crates`, 01), the diff compares crate names and semver-compatible ranges instead of exact versions; every other check still applies:
- system layer: `rustix` (libc backend; features std, net, event, pipe, use-libc), with `libc`, `errno` and `bitflags` from its closure on every target, plus `linux-raw-sys` on Linux and `windows-sys` (with the `windows-targets`/`windows_*` import-library crates it pulls) on Windows (01 §3.3 R4);
- secrets: `zeroize` (default-features=false, features=["alloc"]);
- TLS (06 §3.11): `rustls`, `rustls-pki-types`, `rustls-webpki`, `ring` (or `aws-lc-rs`, with `aws-lc-sys` or, in the FIPS build, `aws-lc-fips-sys`), `untrusted`, `zeroize`, `pkcs8`, `pkcs5`, `der`, `spki`, `pem-rfc7468`, `base64ct`, `aes`, `des`, `cbc`, `cipher`, `md-5`, `sha1`, `sha2`, `pbkdf2`, `hmac`, `scrypt`, with their transitive closure as `cargo tree` reports it. The closure includes no `rustls-pemfile`, no `rustls-native-certs` and no `openssl-probe`. `sha1` serves PBKDF2-HMAC-SHA1 only; the OpenSSL subject hash for hash-named directory entries uses the selected provider's SHA-1 (06 §3.4). The PEM reader must see RFC 1421 headers, so it is the project's own strict reader.
- The native `tls-rustls` feature uses the same trust loader (`trust.rs`) and adds no trust crates. The native-only, opt-in `tls-platform-verifier` feature adds `rustls-platform-verifier`, which has its own native-feature closure golden; cargo-deny bans it from the zk-ffi closure, and the drop-in never uses it.
- The FIPS build omits the RustCrypto key-decryption crates and `legacy_pem` (06 §3.15.3); its golden is `zk-ffi-<target>-aws-lc-rs-fips.txt`.
- The v1-leaf verifier (§2.5 (a)) is in-tree and adds no crate.

Rows that mention sockets assume rustix, not socket2. The crypto crates contain audited third-party `unsafe` or assembly in a pinned, audited closure; the project's own code has no `unsafe` outside zk-ffi's raw module, and every shipped crate of this project except zk-ffi stays `#![forbid(unsafe_code)]` (the test-only zk-xcheck, `crates/zk-ffi-layout` and fuzz targets are never shipped; `crates/zk-ffi-layout` is its own Cargo workspace on the stable toolchain, so the 1.85 floor of DV-BLD-4 holds for the shipped workspace (01 §3.9); and nothing links zk-ffi, a `staticlib` only, as an rlib). ring's and aws-lc's C/asm symbols are prefixed and localized by the `ld -r` step (ABI-10). The FIPS build (aws-lc-rs feature `fips`, sys crate `aws-lc-fips-sys`, which needs CMake and Go on the build host) has its own closure golden and build-specific cargo-deny exceptions. No aws-lc build ships in a release before the ASF legal review of `aws-lc-sys` and `aws-lc-fips-sys` passes (00 §6); `ring` stays the default. tokio, tracing, native SASL, persistent watches and the `zk-recipes` crate are native-only and never reach zk-ffi (K1).

## 3. Test harness and the ledger gate

08 owns the harness; the ledger uses its names.

- **`conf`.** Programs under `tests/conformance` compiled once against the installed headers, linked by SONAME, run against the reference and the drop-in by loader path. Traces record rcs, errno, `zoo_state`, every callback (kind, rc, argument shapes, payload) and the thread role (`app`, `L1`, `L2`, `st-inline`).
- **Reference build** (08 §4.1). The legacy core is pinned to the same commit as the log-site table (§2.5), in four configure variants: with and without OpenSSL, times with and without Cyrus SASL. The `[diff]` tier runs the one shipped drop-in against it. The TLS oracles are OpenSSL 3.0.x LTS and 3.5.x LTS at the latest patch release when M3 starts, then frozen.
- **Wire traces.** Byte-level comparisons accept one extra TLS alert record (close_notify) at a graceful close of the drop-in (TLS-06, P6).
- **`zk-fakeserver`.** Scripted wire-level server built on zk-testkit's `ServerSim`; captures the exact client bytes, and can terminate TLS with generated chains.
- **Real-ensemble tier.** `zktest-public-{mt,st}` plus the real-server matrix (IS-5/6/7), TLS 1.2-only and TLS 1.3-only servers.
- **`proto`.** Sans-IO tests in zk-proto/zk-testkit under `LEGACY_C` and `NATIVE`.
- **`abi`, `golden`.** Export, layout, header and log-site goldens; exhaustive differentials against the legacy C `isValidPath`, `prepend_string`, `sub_string`, host parsing and cert-string parsing compiled into zk-xcheck.
- **TLS trust corpus** (08 §5.2). A differential corpus of OpenSSL `verify` decisions, from the reference lines OpenSSL 3.0 and 3.5 LTS, against `LegacyChainOnly` over generated chains: the in-tree `ssl/gencerts.sh` set, a self-signed leaf in the CA file, an intermediate-only CA file, expired intermediates, missing intermediates, wrong EKU, name mismatch, `TRUSTED CERTIFICATE` aux settings, two same-name issuers of which one lacks keyCertSign (the keyCertSign post-check), a CRL-only CA file, hash-directory names, the set-uid environment rule, and X.509 v1 cases (v1 leaves below v3 chains at several depths, among them a leaf made as `gencerts.sh` makes it (`openssl x509 -req`, OpenSSL ≤ 3.1) but with its own DN; v1 self-signed anchors; v1 intermediates, which both sides reject). Under the reference OpenSSL's default configuration, a case where the drop-in accepts and OpenSSL rejects is a blocking defect. Every case where OpenSSL accepts and the drop-in rejects must map to DV-TLS-1, DV-TLS-3 or DV-TLS-5 (and, for the FIPS build, DV-TLS-6), or the gate fails.
- **SASL fuzzing and sanitizers.** `fuzz/sasl_glue` (libFuzzer) drives `zks_sasl_start`, `zks_sasl_step` and `zks_sasl_dispose` (08 F12) with fuzzed server tokens, generations (including stale ones) and mechlists (passed through the params: `zks_sasl_test_new` takes a mechlist argument) against Cyrus's in-process PLAIN and DIGEST-MD5 plugins and a fake password callback, under ASan+UBSan. The SASL conformance tests run under ASan, UBSan, Valgrind memcheck, and MSan where Cyrus can be instrumented. Clang static analyzer, `gcc -fanalyzer` and CodeQL run on `shim/`.

**Ledger gate (`xtask ledger check`).** `tests/conformance/ledger.tsv` mirrors this ledger with the columns `id, class, knob, test_ids`. The ledger owns its content. CI fails under the conditions of 08 §4.7: an FU or DV row, or a register ID of 00 §5, has no test; a DEV-mode test names an ID that is missing or of class RE or P6; a `Compat::LEGACY_C` value differs from §2.1 (read through a `zk-proto` `testkit`-feature dump), or a `Compat` field has no row; a DV-FIX row has no DEV test that asserts the legacy behavior of the oracle and the fixed behavior of the Rust core; a C-core and a Rust-core run disagree on a test not in DEV mode.

A behavior difference without a row therefore cannot pass CI.

## 5. Registers and summaries

### 5.1 DEVIATE-VISIBLE: registered deviations

**ZooKeeper protocol and API semantics.** Apart from the DV-ABI-2 stubs of undeclared SASL internals and the nine behavior fixes DV-FIX-1..9 (second table), every protocol, session, callback and memory row is RE, FU or P6. The fixes are the single cursor advance, endpoint equality by IP and port, SASL failure as a full teardown, batched SetWatches, the absolute config node for sync getconfig, the `zerror(-15)` text, chroot escape rejection, forced close as a full teardown, and uniform ZCONNECTIONLOSS on the RO→RW switch. They are always on in the Rust-core drop-in, and no build option selects them. The other visible items are link, ABI, build and failure-path differences (first table; DV-BLD-7 applies only if the M4 Windows spike fails) and TLS policy (DV-TLS-1..6, from the rustls backend, last table; DV-TLS-6 in the FIPS build only). The behavior and export set of the legacy C core (`--with-rust-client=no`) are not changed by this design; only its export list is generated from `abi/symbols.tsv` (01 §6.2, 08 E1). **Testing.** The `[diff]` tier runs the one shipped drop-in against the pinned legacy oracle (08 §4.1). Every case that a fix touches is a DEV test registered under its DV-FIX row, which asserts the legacy behavior of the oracle and the fixed behavior of the Rust core. All other cases stay EXACT.

**Not a fix.** The drop-in keeps the libc `srandom`/`srand48` reseed and the `random`/`drand48` draws (SRV-04, §5.5), because an unseeded application that happens to rely on the reseed would otherwise silently get a fixed libc sequence. The native client keeps its private RNG.

### 5.5 Behaviors reproduced exactly, and settings that have one value

These legacy behaviors are reproduced exactly under `LEGACY_C`. None is a deviation:

- the libc PRNG reseed and draws (SRV-04, `ShimRng`), because an unseeded application that happens to rely on the reseed would otherwise silently get a fixed libc sequence;
- delivery order when a reply races a concurrent close (DSP-09, RE under P1);
- CLOEXEC parity (GLB-05; DRV-9);
- C++ exception propagation on every thread (DSP-14, RE through the callback-frame rule; c-shim D12; 08 TH-* tests);
- the state 0/999 on the immediate-connect TLS path (ST-01, ST-16) and the duplicate AUTH packet while ASSOCIATING (AUT-01);
- the `zoo_lock_auth` mutex: default attributes, taken by the library at every legacy site through AUTH_LOCKPOINT (ABI-05, AUT-09, SEC-12);
- default verify paths that fail only on a resource error, and a CA file that loads when it yields at least one certificate or CRL, so a CRL-only CA file loads (TLS-09);
- the OpenSSL decision for X.509 v1 certificates: v1 leaves at any depth below a valid v3 chain and v1 self-signed anchors accepted, v1 intermediates rejected (TLS-01, TLS-14, §2.5 (a)).

These settings have a single value in both profiles and are not `Compat` knobs: the TLS handshake deadline (ST-16), TLS configuration-error handling (ST-17) and multi parsing by wire type (MUL-07). The flavor reaches zk-ffi through `zkrs_init_args` and is not a proto setting (§2.2). `ChrootPolicy::LegacyConcatNoEscape` (DV-FIX-7) is a core value; its validation lives in zk-proto, not in the shim.

Legacy OpenSSL `SSL_write` framing and `SSL_get_error`/`ERR_clear_error` handling have no counterpart in the drop-in (TLS-03 is P6, TLS-05 is RE). The libc PRNG reseed runs in the driver's unlocked resolve step, and `ShimRng::on_resolution` is empty (§2.5).

## Decisions

| Decision | Rationale | Alternatives |
|---|---|---|
| LEGACY_C is the one drop-in value and includes the behavior fixes DV-FIX-1, 2, 3, 4, 7, 8 and 9; DV-FIX-5 and DV-FIX-6 are unconditional shim code. No build option, environment variable or other input selects a fix. | Each fix removes a hazard for correct applications: a two-server client that settles on one server after at most one move, ignored port changes, a silent SASL failure, a reconnect loop on large watch sets, the wrong config node, a wrong error text, a chroot escape, replay of unsent requests, and a false ZOK for unexecuted writes. One shipped behavior is one behavior to test and support, and each fix is registered with release-note text. The [diff] tier runs the shipped drop-in against the pinned legacy oracle: cases that a fix touches are DEV tests under its DV-FIX row, and all other cases stay EXACT. | Fixes left to applications. |
| Callback-frame rule with C loops on every thread: app threads drain a per-call outbox; the mt IO and dispatch loops are C loops over zkrs_io_step and zkrs_wait_dispatch; threads are created, joined and detached by C from THREAD items; Cyrus runs from SASL items. | Preserves C++ exception propagation and C's terminate-at-thread-start exactly (DSP-14 RE), removes every lock-held-callback deadlock, keeps function pointers out of Rust, and avoids foreign unwinds into extern "C" Rust frames. | Rust-called vtable trampolines (abort on exceptions); a run_items vtable entry on the IO thread, which leaves Rust frames under user code on library threads. |
| One Compat type, owned by zk-proto, with the values in this ledger and the ledger gate checking LEGACY_C and NATIVE against them; per-driver settings in DriverMode {interest, session_delivery} only. | One list keyed to ledger rows gives one test matrix (LEGACY_C and NATIVE) and makes drift a CI failure. | Per-document or per-flavor Compat definitions (unnecessary: flavor differences are in DriverMode). |
| The libc PRNG reseed runs in the Blocking rng_reseed leaf from the driver's unlocked resolve step; ShimRng::on_resolution is empty. | A Blocking leaf must never run under a Rust lock (K4, CC-6 (00 §4)), and on_resolution is called under the driver lock. The libc call order on that thread is unchanged. | Reseeding inside on_resolution (Blocking call under a lock). |
| zoo_lock_auth is reproduced at every C site through an AUTH_LOCKPOINT barrier executed by C (lock; unlock) before the state change and collection, with zoo_add_auth locking and unlocking it around submit as legacy does; the mutex is initialized as in legacy, with default attributes. | Same stall behavior for an application holding the lock (LA-01 parity), no lock-order inversion at the teardown site (within P1), and no Rust frame or lock under the mutex. The mutex is the legacy one, so misuse (a relock on the same thread, `zoo_add_auth` while holding `zoo_lock_auth`) behaves as in legacy. | IO side never taking the lock; a Rust-held AuthGate across calls; unlocked teardown collection with fenced delivery. |
| SASL failure is a full teardown (DV-FIX-3): state AUTH_FAILED, the AUTH_FAILED event, the socket closed, ZAUTHFAILED for all pending work, the SASL rc from the driving call, the mt IO thread exit, and the Cyrus dispose only at the final close. | It takes the path of C's digest-auth failure (AUT-04), so an application sees one auth-failure behavior. C's SASL path leaves watchers uninformed, async work waiting until close, and an mt sync caller blocked until another thread closes the handle. | C's silent state change. |
| Forced close (a rebalance after zoo_set_servers or after a re-resolution inside zookeeper_interest, st submit-flush failure) is a full teardown split at the API-call boundary (DV-FIX-8): state 999 in the call and no callback there; the trigger takes tx, the FIFO and the pending auth tokens as one snapshot; the CONNECTING event and the snapshot's ZCONNECTIONLOSS results come from the IO owner's next driving call, or from that call for a rebalance found in zookeeper_interest; none of the snapshot is replayed; a request submitted after the trigger stays queued whole for the next connection. | C's replay, its later ZRUNTIMEINCONSISTENCY or timeout, and its mid-frame resume harm correct applications. C runs no callback inside these API calls, and the IO owner is where every other teardown delivers, so the threads and the callback-frame rule stay as for any teardown. The snapshot limits the deviation to work pending when the connection closed and makes the result independent of IO-thread timing. | Delivery inside the API call (a callback in a `zoo_a*` frame); keeping the queues and fixing only the mid-frame resume and the fd race; failing whatever stands when T3 runs (timing-dependent, and it fails requests legacy would send). |
| TLS uses rustls in zk-driver for both profiles, with the LegacyChainOnly verifier and legacy trust inputs, key formats, log lines and rcs for the drop-in; the library contains and links no OpenSSL. | Keeps all TLS code in forbid(unsafe) Rust over an audited closure, avoids the process-global state and error-queue hazards of legacy's OpenSSL use, and reproduces the legacy trust decision; the remaining differences are registered as DV-TLS-1..6 and checked by a trust-decision corpus. | OpenSSL driven from shim C over memory BIOs (parity with openssl.cnf and DT_NEEDED, but more unsafe C and an OpenSSL build floor). |
| LegacyChainOnly never trusts more than OpenSSL: a leaf byte-identical to a trust-set certificate is accepted only when that certificate is OpenSSL-self-signed (EXFLAG_SS) and passes check_issued under the mimic rule, and the leaf has no critical extension outside the processed set of 06 §3.14.3 (error 34); only self-signed, CA-capable, purpose-compatible trust inputs and explicitly trusted `TRUSTED CERTIFICATE` inputs (06 §3.4) are anchors; rejected `TRUSTED CERTIFICATE` inputs fail any chain that would select them (error 28); a v3 chain fails when a certificate that can lie on webpki's path has keyUsage without keyCertSign (error 32, the keyCertSign post-check); directories are read only through hash-named entries, by the `by_dir` rule; set-uid processes ignore the environment. | Each rule matches OpenSSL 3.0 and 3.5 LTS, except the directory rule, which matches 3.5 on hash names and suffix gaps, is stricter than the OpenSSL 3.0 default store lookup, and is stricter than both lines for a hash-named file with a corrupt block or a certificate of another subject (DV-TLS-3, 06 §3.4), the mimic and ambiguity rules, which fail closed where OpenSSL's verdict depends on the order of same-subject trust-store certificates (DV-TLS-3, 06 §3.5, §3.14.3), the rejected-issuer post-check, which fails closed where OpenSSL's path does not use the rejected input (DV-TLS-3, 06 §3.5), and the keyCertSign post-check, which is stricter where OpenSSL's path does not use the certificate without keyCertSign (DV-TLS-3, 06 §3.5). Accepting more than OpenSSL would widen trust beyond the legacy decision, which the trust corpus treats as a blocking defect. | — |
| The DefaultVerifyPaths step fails only on a resource error; missing or empty default locations do not fail it. The default locations are the environment variables (when tls_env_allowed) or the compile-time defaults; openssl_probe::probe() is never called. | OpenSSL's SSL_CTX_set_default_verify_paths (X509_STORE_set_default_paths) ignores its file and directory loads and returns 1 except on allocation failure, so the drop-in matches legacy (RE). Compile-time defaults keep the run time free of environment reads other than the two gated variables. | — |
| The CaFile step succeeds when the CA file yields at least one certificate or at least one CRL; CRLs are parsed and counted but not used. It fails when the file cannot be read, when a PEM block is malformed (06 §3.4), when `ca` is NULL, or when it yields neither a certificate nor a CRL. | This is OpenSSL's X509_load_cert_crl_file rule, so a CRL-only CA file loads as in legacy (RE, TLS-09). Legacy sets no CRL-check flags, so the CRLs never affect the trust decision. | — |
| TLS timing and config errors: the TCP-connect phase stays exempt from the receive timeout (only the tv=0 spin once recv_to <= 0 is fixed); the handshake deadline is TCP-connect completion + 2/3 T; a config error returns ZSSLCONNECTIONERROR with errno EINVAL and the step's log line, without teardown or spin, and fails over by the receive rule; immediate-path state and outputs as C. No knobs. | ZSSLCONNECTIONERROR is what both C callers return (zk.c:2715-2722, 3093-3094). The TCP phase is kernel-bounded, so changing it would alter failover timing without removing UB; while recv_to > 0, tv stays C's min(recv_to, T/3). Single values in both profiles keep the matrix small. | Deadline from attempt start; a ZSSLCONNECTIONERROR teardown for config errors; ZBADARGUMENTS (the internal code, which never reaches the API); tv = T/3 throughout state 7. |
| TLS presence in the C build follows the legacy autodetect exactly: --with-openssl / WITH_OPENSSL keep their names, defaults and probe, and the probe only decides the zk-ffi tls feature; OpenSSL is never linked; the feature defines HAVE_OPENSSL_H and HAVE_CYRUS_SASL_H follow legacy exactly (autotools CPPFLAGS, CMake PUBLIC); --with-rust-tls=yes / WITH_RUST_TLS is an additive opt-in, off by default. | zookeeper_init_ssl, HAVE_OPENSSL_H and the export sets are identical to legacy in every configuration that does not set the opt-in `--with-rust-tls=yes` / `WITH_RUST_TLS=ON`, and consumers keep the 32-byte zsock_t (01 §4.8, §6.3). Only the link changes (DV-TLS-4). The opt-in serves hosts without OpenSSL headers without changing any default. | — |
| SASL stays Cyrus in two isolated, hardened C translation units with bounded views, generation-checked session lifetime, one SASL START or STEP in flight on the IO owner, and the secret trampoline; DAT-13 is FU for ZooKeeper sessions (06 §4.7). The password mutex guards only the short, non-callback in-block copy on the direct Cyrus path; no internal lock is ever held across application code. | The SASL API is bound to Cyrus; minimizing the C surface and bounding every byte argument is the most that can be done without an API change. The trampoline removes the shared-buffer race for ZooKeeper sessions with no layout change (direct Cyrus use of a shared block keeps the legacy header contract); keeping every lock off application code keeps the callback-frame rule (DSP-13 fix), and unwinding needs no cleanup handler. | RE under the header contract with no per-connection buffer; a Rust SASL engine in the drop-in (not possible: Cyrus callbacks are API). |
| Reproduce the libc PRNG side effects (SRV-04), hashtable fan-out order, duplicate AUTH in ASSOCIATING, and CLOEXEC parity. | None of these is UB, and each is observable by a correct application. An unseeded application that happens to rely on the reseed would silently get a fixed libc sequence without it. The native client keeps its private RNG. | Private RNG in the drop-in, dropped duplicate AUTH, CLOEXEC everywhere. |
| Per-handle xid seeded from time(0), wrapping to 1. | Xid scope and values are visible only in DEBUG logs and on the wire (P6); per-handle matches the core's no-globals invariant; positive wrap removes misrouted replies. | A process-global counter. |
| OOM: keep C's checked rcs wherever C checks; abort only where C's allocation is unchecked; the core aborts except request encoding (ZMARSHALLINGERROR) and the `zoo_add_auth` credential copy (ZSYSTEMERROR); auth-frame encoding is infallible, so there is no second retained token state. | Closest to C; abort only replaces paths that are already UB in C, and one ownership state is easier to verify. | Abort everywhere in the shim; a LATE_RETAINED status for zoo_add_auth. |
| zookeeper_interest out-parameters stay unwritten on C's early-return paths that this design keeps (unrecoverable; resolve failure without a socket) and are written on the connected-resolve-failure path. | Applications such as cli.c ignore the rc and reuse persistent fd/tv variables. The connected path is itself the FU fix and runs a full iteration. | Always writing fd=-1/interest=0/tv=T/60. |
| zoo_set_servers: deterministic parse errors are not committed (FU); transient resolution failures keep commit-then-retry (RE). | Only the parse error is a permanent liveness failure; applications may rely on a list that resolves later. | Commit only after parse and resolve both succeed. |
| Bad value buffers and NULL acl in set_acl return ZMARSHALLINGERROR at the serialization stage, single ops and multi alike; sync DATA capacity<-1 keeps C's request and the legacy `*buffer_len` formula, with only the crashing copy skipped; zoo_get_current_server(NULL) returns "null"; DAT-15 reproduces the endpoint-buffer overwrite. | Each choice matches the stage or value C reaches without the crash, and exact reproduction of the overwrite is closer to C than the longer lifetime P3 permits. | ZBADARGUMENTS for bad values; up-front ZBADARGUMENTS for capacity<-1; NULL for the endpoint. |
| X.509 v1 certificates are decided as OpenSSL decides them: v1 leaves at any depth below a valid v3 chain and v1 self-signed anchors are accepted, v1 intermediates are rejected (error 79). An in-tree forbid(unsafe) verifier is the acceptance path for the v1-leaf case only; v3 leaves go through webpki, followed by the same verifier's rules as an OpenSSL path post-check that can only reject (06 §3.5). The verifier is differentially tested against OpenSSL 3.0 and 3.5. | ZooKeeper operators follow the documented examples, and the repository's ssl/gencerts.sh makes v1 leaves on OpenSSL <= 3.1, so rejecting them would break working deployments. Limiting the custom code to the v1-leaf signature check plus OpenSSL's issuer-chain rules keeps the audited surface small. | Rejecting v1 leaves issued by a trusted CA as part of DV-TLS-3. |
| TLS-06 is P6: both profiles send close_notify on a graceful close, flushed without blocking within the close budget and never awaited; forced and error teardowns and the RW probe send no close_notify; after a fatal TLS error that rustls detects, the driver in both profiles makes one non-blocking send of its fatal alert and drops it when `ct_out` is not empty, as OpenSSL writes it inside `SSL_connect` and `SSL_read` in legacy. | No application can observe the alert; sending it is the correct TLS close and lets servers log a clean shutdown. Wire-trace comparisons accept the extra record. The fatal-alert rule keeps the legacy wire behavior after an error. | No close_notify, as legacy. Dropping the fatal alert after an error (the server would see EOF where legacy sends the alert). |
| CLS-10: a mutex-protected live-handle registry (ZKS_HANDLE_REGISTRY) exists in debug builds only and aborts on use after close or double close; release builds keep the legacy contract with no overhead. | Debug builds turn a silent UB into a clear diagnostic for developers; release builds pay nothing and behave as legacy. | A registry in every build; no registry. |
| The errno printed in TLS teardown log lines is that of the last failed socket call, or 0, and is P6. | rustls reports errors as values, so there is no OpenSSL errno to reproduce; the value is log text only. | Reproducing OpenSSL's errno side effects. |
