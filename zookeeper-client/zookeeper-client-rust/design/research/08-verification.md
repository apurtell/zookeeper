# Verification, testing, and rollout

## 0. Contracts under test

The tests in this document assume the contracts below. They come from the key decisions K1–K27 (00 §3) and the cross-cutting contracts CC-1..CC-36 (00 §4), from the TLS design (06 §3), the SASL design (06 §4), the jute generation (01 §8) and the Maven integration (01 §13). In the Source column, "CC-n" means the contract of that number in 00 §4. Every expectation in this document follows these contracts. The ledger gate (§4.7) fails CI when `Compat::LEGACY_C` or the code differs from the ledger values.

## 1. Goals and rules

Before anyone runs the Rust build in production, verification must establish three things:

- **(A) Interface identity.** The new `libzookeeper_{mt,st}` present the same linker-visible and compiler-visible interface as the legacy reference build (§4.1): symbols, data objects, layouts, headers, SONAME and loader metadata. The only differences are the registered DV-ABI, DV-BLD and DV-TLS-4 rows.
- **(B) Behavioral identity.** Every scenario a correct application can observe behaves the same. The only exceptions are compat-ledger rows of class FU or DV, and every one of those rows has a test. For TLS this includes the trust decision: under the reference default configuration, the drop-in never trusts a peer that legacy would reject.
- **(C) Robustness.** The Rust core is memory safe, deterministic under test, and never panics on hostile input. Unsafe Rust stays confined to zk-ffi's audited layer and to the pinned, audited third-party closure. The C that remains on the unsafe side (the shim, and above all the Cyrus SASL glue) is fuzzed, sanitized and statically analyzed.

| Rule | Statement |
|---|---|
| P1 Oracle | The reference is the legacy C core (`--with-rust-client=no`) at the **pinned reference commit**, in the four configure variants of §4.1, linked with the frozen OpenSSL 3.0 and 3.5 LTS releases for its TLS builds. The `[diff]` tier compares it with the one shipped drop-in, the Rust core built with the same configure flags. Every case that a fix touches is a DEV test under its DV-FIX row (§4.5), and all other cases stay EXACT. Every black-box assertion must first pass against the reference. If an assertion fails against C, the test is wrong, not the specification. The only exceptions are DEV tests (P5). |
| P2 Compile once | Conformance programs are compiled once against the installed headers and link `libzookeeper_{mt,st}.so.2` by SONAME. Only the loader search path selects the implementation. Windows has only static libraries, so there the objects are compiled once and linked twice. |
| P3 Determinism | Exact timing and ordering are tested in sans-IO tests with injected `Millis`. Black-box fault injection uses the scripted fake server. The real Java server is used only for end-to-end tests. Black-box tests never use sleeps to establish ordering. |
| P4 Golden data from C | ABI goldens (symbols, layouts, needed libraries, log sites) are generated only from the legacy core and are never regenerated from the Rust build. |
| P5 Ledger traceability | Every ledger row whose class is FU or DV, and every register ID of X28, has at least one test that names it. Every DEV-mode test names exactly one ID. `cargo xtask ledger check` enforces both directions (§4.7). A behavior difference without a row fails CI. It is never accepted silently. |
| P6 Trust is never widened | Under the reference OpenSSL's default configuration (no `OPENSSL_CONF`, the build's default security level, and the case's controlled trust locations), a case where the drop-in accepts a peer that the legacy oracle rejects is a blocking defect and can never become a DV row (§5.1). Host policy that is stricter than that default (`openssl.cnf`, crypto-policies, a raised security level) does not apply to the drop-in; that is DV-TLS-2, whose DEV tests (§5.5) expect the Rust core to connect. |

## 3. ABI conformance

### 3.1 Golden export table and derived lists

`abi/symbols.tsv` is the single export source. Its columns are `name kind flavors feature rw size_lp64 size_ilp32 decl note`. It is derived once from `nm` of the reference build. `abi/gen-exports.awk` turns it into the libtool `.sym`, the GNU ld `.map`, the Darwin `.exp`, the Windows `.def` (with `DATA`) and the prelink keep list. The binary checks never generate export lists. They only read built binaries, so generation and checking stay independent. The generators have one comparison of their own: the Linux job of abi-{linux,macos,mingw} (§14) compares the output of `abi/gen-exports.awk` and of `cmake -P` over `ZkExports.cmake` byte for byte for every flavor, feature and format combination of 01 §5.

Required totals, from the reference build:

| Configuration | mt | st |
|---|---|---|
| SSL + SASL | 211 | 188 |
| SASL only | 210 | 187 |
| SSL only | 202 | 179 |
| neither | 201 | 178 |

The mt-only delta is exactly the 23 sync functions. Data objects are the same in every configuration: 30 read-only `const int` plus 6 writable objects (`logLevel`, `ZOO_ANYONE_ID_UNSAFE`, `ZOO_AUTH_IDS`, and three `ACL_vector`). "SSL" has its ABI meaning: it decides whether `zookeeper_init_ssl` is exported. It does not mean that the library links OpenSSL; the drop-in never does (DV-TLS-4). The SSL configurations are exactly those in which legacy builds TLS: the `--with-openssl` / `WITH_OPENSSL` autodetect keeps its names, defaults and probe (`openssl/ssl.h` and `-lssl SSL_CTX_new`), so a build host without OpenSSL headers builds the "SASL only" or "neither" subset, with configure's "cannot build SSL support -- openssl not found" warning, as legacy does. The opt-in `--with-rust-tls=yes` (CMake `WITH_RUST_TLS`) selects an SSL subset without OpenSSL headers. CI builds both cases on one host and checks each against its golden subset with E1.

`abi/static-symbols.tsv` holds the 179 archive-only rows: the 161 header-declared archive-only symbols (154 `serialize_*`/`deserialize_*`, the six recordio archive functions, and `close_zsock`) and the 18 `oa_*`/`ia_*` functions that `recordio.c` defines globally.

`abi/absent.tsv` lists names that **must stay unexported** from the shared libraries, so that link failures stay link failures:

- `close_zsock`;
- every `serialize_*`/`deserialize_*`;
- the recordio archive functions;
- `oa_*`/`ia_*`;
- `deallocate_vector` and `format_log_message`, which are undefined everywhere;
- for st only, the 23 sync functions, including `zoo_remove_all_watches`. That function is declared outside the THREADED block (zookeeper.h:1976) but defined only in mt.

The list is checked in, and CI recomputes it from the reference `.a` minus the reference `.so` to confirm it is complete.

The golden files are produced from the reference build by the steps that `abi/README.md` documents. The Linux and Mach-O results must agree apart from the leading underscore.

### 3.2 Shared-library checks

`cargo xtask abi check <lib> --flavor mt|st --features ssl,sasl` is the one checker. It is written in safe Rust with the `object` crate, reads ELF, Mach-O and COFF from any host (which covers cross-built targets), and shares no code with `gen-exports.awk`. `make abi-check` and the CMake target `abi-check` invoke it when cargo is available. The checker is itself validated on every PR by running it against the reference build, which must pass every check except the rows marked with a DV ID.

### 3.3 Static archives

- **S1.** Every `symbols.tsv` row for the flavor and features is a global definition.
- **S2.** Every `static-symbols.tsv` symbol is present, including the 18 `oa_*`/`ia_*` functions.
- **S3.** No other global is defined. The archive's only member is the pre-linked relocatable object for the flavor. On MSVC (DV-BLD-3), S3 is replaced by S3w: "`zks_*`, Rust std, `zkrs_*` and crypto-provider globals tolerated".

The undeclared legacy internals (`hash`, `do_io`, `get_xid`, `adaptor_*`, `addrvec_*`, `hashtable_*`, …), about 95 symbols, are not reproduced. That is the registered deviation **DV-ABI-1** (00 §5.1). Both goldens are authoritative: S1-S3 keep exactly the golden exports and the `static-symbols.tsv` rows, so every other global of the reference archive is removed. A CI step lists the removed names (reference `.a` globals minus `symbols.tsv` minus `static-symbols.tsv`) for the DV-ABI-1 release note.

### 3.5 Layout tests

**L1: compile-time probes.** `cargo xtask layout gen` emits `abi/layout/probe.c`. It includes the installed headers exactly as an application does and covers:

- every jute record and `*_vector`;
- `clientid_t`;
- `zoo_op_t`, including every member of the anonymous union;
- `zoo_op_result_t` and `zcert_t`;
- `zsock_t`, with and without `HAVE_OPENSSL_H`, and with `WIN32`. The headers still include `<openssl/ossl_typ.h>` when the *application* defines `HAVE_OPENSSL_H` (06 §3.11), so the probe host needs OpenSSL headers; the library does not;
- `zoo_sasl_params_t` and `zoo_sasl_password_t`;
- `struct buffer`, `iarchive` and `oarchive`;
- the enums `ZOO_ERRORS`, `ZooLogLevel` and `ZooWatcherType`.

Expected values are extracted from cross-compiled objects with `object`, so nothing executes on the target. The check build asserts them with `_Static_assert`.

| Fact | LP64 (x86_64, aarch64, s390x) | i686-linux-gnu | armv7-gnueabihf | i686-windows-msvc | x86_64-windows-msvc |
|---|---|---|---|---|---|
| `struct Stat` | 72 (ephemeralOwner@48, dataLength@56, pzxid@64) | **68** (ephemeralOwner@44, dataLength@52, numChildren@56, pzxid@60) | 72 | 72 | 72 |
| `clientid_t` | 24, passwd@8 | 24 | 24 | 24 | 24 |
| `zoo_op_t` | 72; create: path@8 data@16 datalen@24 buf@32 buflen@40 acl@48 flags@56 ttl@64 | per probe | per probe | per probe | 72 |
| `zoo_op_result_t` | 32 | 16 | 16 | 16 | 32 |
| `zsock_t` (no OpenSSL) | 16 | 8 | 8 | 8 | 16 (`SOCKET` = 8 bytes) |
| `ZooLogLevel` | 4, unsigned | same | same | 4, **signed** | signed |

**L2: private ABI.** L2 checks the `zkrs.h` types (CC-28 (00 §4)) and the `abi/legacy.rs` mirrors of the public result records: `shim/zks_layout_check.c` `_Static_assert`s, and a `ctest` comparison against the Rust `repr(C)` definitions. ctest runs in the test-only crate `crates/zk-ffi-layout` (`publish = false`). That crate is its own workspace with its own lockfile and builds on the stable toolchain only, because ctest needs rustc 1.88 (01 §3.9); the workspace-wide `cargo-test` and `rust-lint` runs therefore never compile it, and the MSRV 1.85 build is unaffected. It includes the zk-ffi ABI modules `abi/types.rs` and `abi/legacy.rs` with `#[path = "../../zk-ffi/src/abi/..."]`, because zk-ffi is `staticlib` only (01 §3.2) and a separate crate cannot link it. This covers `zkrs_outbox`, `zkrs_item` and every view type it carries (result, watch, log, the SASL item views with their `zks_bytes` shape of pointer, `uint32_t` length and null flag, and the THREAD item), `zkrs_host_vtable` (exactly the X4 entries, in order), `zkrs_init_args`, `zkrs_request`/`zkrs_op`/`zkrs_acl`, the writer interface types `zkrs_result_dst`, `zkrs_multi_copy`, `zkrs_sync_src` and `zkrs_sync_dst` (05 §10.1, §13), and `zkrs_interest_out`, whose `fd` field must be `intptr_t`-sized so that `SOCKET` fits on Win64. The same crate checks the `abi::raw` mirrors of the public result records that the raw writers build (`struct Stat`, `String_vector`, `ACL_vector`, `ACL`, `Id`, `zoo_op_result_t`; 05 §10.1) against the installed headers on every layout target, including the i686 `Stat` of 68 bytes and the `zoo_op_result_t` sizes of L1. CI also runs the cbindgen drift check (`cbindgen --verify`).

**L3: header identity:**

- installed headers are byte-identical to `include/`;
- `zookeeper.jute.h` is byte-identical to `Rcc -l c` output;
- a side-by-side install has one header tree, identical to a legacy install;
- `ZOO_VERSION` equals `zoo_version_str()`.

C++ mangling of `_zhandle`, `Stat`, `zoo_op` and `clientid_t` then follows from header identity.

## 4. Differential behavioral conformance

### 4.1 Execution model

```
            compile once against ORIGINAL installed headers
cases/*.c ────────────────────────────────────────────► conformance binaries (link -lzookeeper_{mt,st})
                                                            │
  cargo xtask conformance run ── for core in {c, rust} ─────┤ exec directly (no /bin/sh: SIP strips DYLD_*)
     │   LD_LIBRARY_PATH / DYLD_LIBRARY_PATH = <core libdir>  (c: the pinned reference build from the reference image, §15.4; rust: the --with-rust-client=side-by-side install, §15.2)
     │   ZKCONF_TRACE  ZKCONF_HOSTS  ZKCONF_CTL  TZ=UTC  LC_ALL=C
     │   SSL_CERT_FILE / SSL_CERT_DIR pinned per TLS test (§5.4)
     ▼
  zk-fakeserver (fresh per run, same script + seed) ──► transcript.jsonl
     ▼
  trace + stdout/stderr + transcript ──► normalize ──► compare (mode per test) ──► JUnit + HTML diff
```

At startup `libzkconf` records the resolved path of the loaded `libzookeeper_*` (`dl_iterate_phdr`, or `_dyld_get_image_name` on macOS). The runner rejects any run whose loaded library does not match the requested core, so one core can never be tested twice by accident. On Windows (M4) the objects are compiled once and linked twice.

**Reference build.** The legacy core under test is pinned to the commit to which the log-site table is pinned (CC-30): the final legacy C-core commit on main before the Rust core becomes the default. `cargo xtask log-sites` extracts `abi/log-sites.tsv` from the C core at that commit and re-extracts it whenever the pin moves, so the table and the reference build always come from the same commit (05 §16.2). Legacy C-core changes may move or change log sites freely; they reach the table and the reference build only when the pin moves. The reference is built in four configure variants, {with, without} OpenSSL × {with, without} Cyrus SASL, which match the four export totals of §3.1. The TLS oracles are OpenSSL 3.0.x LTS and 3.5.x LTS, at the latest patch release of each line when M3 starts, and then frozen: the CI images pin these two releases (§15.6), the TLS variants of the reference build link them, and O2 (§5.1) runs them.

**The `[diff]` tier.** The tier runs the one shipped drop-in against the reference: every EXACT, PER-ROLE and SET comparison runs on that build, and so does difftest (§4.6). Every case that a fix touches is a DEV test registered under its DV-FIX row (§4.5). It asserts both the legacy behavior of the oracle and the fixed behavior of the Rust core. All other cases stay EXACT.

Every recording callback calls `zkc_frame_check`. Each callback record holds:

- rc;
- the pointer class (NULL or non-NULL) of every pointer argument;
- lengths;
- payload bytes (the first 64 inline, plus a SHA-256 of the whole payload);
- the normalized Stat;
- vector contents in received order;
- the global sequence number, used only by tests that assert a cross-role order (LA-01).

Normalization rules:

| Id | Rule |
|---|---|
| N1 | Session ids become S1, S2, … |
| N2 | zxids and Stat zxid/time fields become ranks |
| N3 | Context pointers become C<n>; library function pointers become LIBFN |
| N4 | Thread ids become roles |
| N5 | pid becomes PID; ports become names |
| N6 | xids are compared only in the transcript, and only as per-handle ranks (X14) |
| N7 | In log lines the timestamp, pid and thread id are replaced; `func@line` and the message text are kept |
| N8 | Durations are bucketed only where the scenario declares a bucket |
| N9 | Certificate and key file paths become names (`<ca>`, `<cert>`, `<key>`) |
| N10 | In TLS transcripts and wire traces, one close_notify alert record at a graceful close of the Rust core is accepted and removed before comparison (ledger TLS-06, 07 P6). Any other extra record is a difference. |

### 4.3 Comparison modes

| Mode | Definition | Used for |
|---|---|---|
| EXACT | The normalized traces are identical | All st scenarios; single-threaded mt scenarios |
| PER-ROLE | Each role's subsequence is identical | mt scenarios where cross-thread interleaving is racy in C |
| SET | Both cores land in a declared outcome set on every repetition | Races that are legal by contract, for example an op racing close: ZOK, ZCLOSING or ZMARSHALLINGERROR (TestClient.cc:338-348, 5f73197a8) |
| DEV | Rust asserts the ledger row's new behavior. For a DV-FIX row the legacy behavior of the oracle is also asserted and gated (§4.5, §4.7 item 5). Repetitions: 3 per PR and 50 nightly per (test, flavor, core), with stress variants under `taskset -c 0` and `stress-ng --cpu`. If the legacy core itself is unstable in a scenario, the test is marked oracle-flaky and runs in SET mode or as a sans-IO test.

### 4.6 Randomized differential testing

`zkconf-interp` is one C program per flavor. It reads a line script and records the same trace as the corpus. Example lines: `aget path=/a/b watch=1 ctx=3`, `amulti ops=[create:/x,check:/y:v=2]`, `close from=completion#4`, `await events=2`. A line that starts with `#` is a comment, which is how a script carries the ASF header.

`cargo xtask difftest` generates seeded (client script, server script) pairs with proptest, runs both cores (§4.1), and compares in PER-ROLE mode. On a mismatch it shrinks the case, rerunning both cores at every step, and writes the reproducer to `tests/conformance/regressions/`, where it becomes a permanent case. The generator emits only contract-valid calls. It produces FU triggers and the triggers of the DV-FIX rows (a failover across more than one server, a port-only or rebalancing `zoo_set_servers`, a SASL failure, a watch set above 128 KiB, sync getconfig under a chroot, `zerror(-15)`, a 1-character path or a sequential create on `"/"` under a chroot, a forced close and an RO→RW switch) only with `--dev`, in which case each case must name the ledger ID it exercises. Budget: 2 hours nightly, 10 minutes on PRs that touch zk-proto, zk-driver, zk-ffi or the shim.

### 4.7 Ledger traceability gate (`cargo xtask ledger check`)

`tests/conformance/ledger.tsv` mirrors the compat ledger (07) and the deviation registers (00 §5), with the columns `id`, `class` (`RE|FU|DV|NO|P6`, where P6 is the 07 P6 class), `knob`, `test_ids`. 07 owns its content. The check fails when:

1. an FU or DV row, or a register ID of X28, has no test;
2. a DEV-mode test names an ID that is missing or of class `RE` or 07 P6;
3. a `Compat::LEGACY_C` field value differs from the knob value the ledger records, or a `Compat` field (`tls_verify` included) has no ledger row. The check reads the constant through a zk-proto `testkit`-feature dump; zk-ffi never enables that feature (E12);
4. a legacy-core conformance run and a Rust-core run disagree on a test not in DEV mode;
5. a DV-FIX row has no DEV test that asserts the legacy behavior of the oracle and the fixed behavior of the Rust core.

RE, NO and 07 P6 rows need no test of their own; a test may still name them. An RE row may list a DEV test of a DV-FIX row when that test compares the RE value on both cores: SAS-08 and RC-15 list `conf.sasl.process_rc`, which names DV-FIX-3. An RE row may also point to the DEV test of a DV-FIX row for a case that the fix takes out of the row: SRV-03 lists `conf.srv.migration_teardown` (DV-FIX-8) and `conf.srv.port_only_change` (DV-FIX-2). This makes it impossible for CI to accept an unregistered deviation quietly.

## 5. TLS verification

### 5.1 Scope, oracles and verdict rules

**Under test.** `zk-driver/src/net/tls/` (modules as in 06 §3.1): `RustlsConn` (`conn.rs`), `RustlsConnector` (`connector.rs`) with `TlsConnector::new_conn(&self, &Unlocked, purpose, &Endpoint)` and the config steps of the zk-proto type `TlsConfigStep {CaFile, DefaultVerifyPaths, ClientCertChain, ClientKey, CheckPrivateKey}`, `legacy_verify.rs` (`LegacyChainOnly`), `v1_leaf.rs` (the v1-leaf verifier of `LegacyChainOnly`, and the OpenSSL path post-check for v3 leaves, 06 §3.5 and §3.14), `trust.rs` (CA file and default verify paths; shared by the drop-in and native `tls-rustls`), `pem.rs` and `x509.rs` (PEM reader, DER view, OpenSSL subject hash), `identity.rs` (client chain, key and key match) and `legacy_pem.rs`. A config failure reaches zk-proto as `TransportFailure::TlsConfig {step, file}` (`file` is for the log line only), a resource failure as `TransportFailure::TlsResource {at, errno}` with `TlsResourceAt {ContextNew, ConnectionNew}`, and a handshake failure as `TransportFailure::TlsHandshake {errno}`. On TCP-connect completion the driver calls `new_conn` first and then `handle_tcp_connected`. The drop-in runs with `Compat::tls_verify = LegacyChainOnly`; the native API with `WebPki`. Every test of this section runs in the `ring` build; §5.4 TI-09 runs it in the `aws-lc-rs` and `aws-lc-rs-fips` builds.

**Oracles.**

- **O1, the legacy core.** It is the TLS variant of the reference build (§4.1), linked with the frozen OpenSSL 3.0.x and 3.5.x releases. It runs end-to-end handshakes against zk-fakeserver. O1 is authoritative wherever both cores can run the case.
- **O2, `openssl verify`.** It is used offline for cases that zk-fakeserver cannot present (for example a server key that rustls cannot sign with). The invocation is `openssl verify -purpose sslserver -CAfile ca.pem -untrusted rest.pem -attime T -auth_level L leaf.pem`, with `SSL_CERT_DIR` pointing at the case's `defaults/` directory (or an empty one) and `SSL_CERT_FILE` at a missing path, so that the host store never leaks into a verdict. `openssl verify -CAfile` does not read `SSL_CERT_FILE`, so a case that places trust in the default file takes its committed verdict from O1 (the `SSL_CERT_FILE` variant of TC-24, TC-25b (b)). L is the default security level of the matching libssl build in the CI container, recorded with the verdict. O2 runs once for each reference OpenSSL release line, which are also the lines the legacy core is built with in CI: 3.0 LTS and 3.5 LTS, at the patch releases frozen when M3 starts (§4.1). OpenSSL 1.1.1 is out of support and is not a reference line.
- **O3, existing fixtures.** The in-tree `ssl/gencerts.sh` set and the `testSSL`, `testSSLNoClientCert`, `testSSLServerOnly` and `testReadOnlyWithSSL` cases.

**Verdict rules.**

| Oracle | Rust | Result |
|---|---|---|
| ACCEPT | ACCEPT | pass |
| REJECT | REJECT | pass, if the failure maps to the same rc and log line |
| REJECT | ACCEPT | Trust decision (§5.2, §5.4): under the reference default configuration, a **blocking defect** (P6). This can never become a DV row. Key loading (§5.3): a defect, except the DV-TLS-2 cases of TK-06 and TK-20, which are DEV under DV-TLS-2 (06 §3.13). |

**Fatal-alert source check (before M3 work begins, against the releases frozen for M3).** The source of the two reference releases frozen for M3 (§4.1) is read to confirm the pending-write alert behavior that 03 §4.3.5 reproduces: a fatal alert that libssl raises inside `SSL_connect` or `SSL_read` (`ssl3_send_alert`) is written to the socket at once when no record write is pending (`RECORD_LAYER_write_pending`), stays queued when one is pending, and is discarded by `SSL_free`; and libssl never sends close_notify without `SSL_shutdown`. The check names the functions and lines read in each release and is recorded with the reference pins (§15.6). TL-13 (c) and (d) then test the same behavior on the wire against the reference build.

### 5.2 Trust-decision differential corpus

**Generation.** `tests/conformance/tls/gencorpus.sh` extends `ssl/gencerts.sh` with the `openssl` CLI, a test-only tool. Serials are deterministic and validity windows are fixed. The gencerts-derived cases are generated twice and tagged by generator version, because `gencerts.sh` signs leaves with `openssl x509 -req` and no extension file (gencerts.sh:82, 113):

- **gen-3.0** (OpenSSL ≤ 3.1): the leaves are X.509 v1 with no extensions. All three certificates use the same DN (gencerts.sh:51-57, 73-79, 104-110), so a v1 leaf has subject = issuer and no AKID, and OpenSSL classifies it as self-signed (`EXFLAG_SS`, defined in full in 06 §3.4). When the CA file holds `root.crt`, such a leaf is not byte-identical to a trust-set certificate. OpenSSL builds no chain past a self-signed leaf and rejects it (error 18, X509_V_ERR_DEPTH_ZERO_SELF_SIGNED_CERT), and path (b) rejects it the same way (06 §3.5, §3.14.4).
- **gen-3.5** (OpenSSL ≥ 3.2): the leaves are v3 with SKID and AKID. The AKID names the root's key, so OpenSSL does not classify the leaf as self-signed.

The corpus has two tiers:

- **Unit tier (every PR).** A committed corpus `tests/conformance/tls/corpus/<case>/{chain.pem, ca.pem, defaults/, verdict.txt}`. A zk-driver test calls `LegacyChainOnly::verify_server_cert` with `now` set to the recorded `-attime` and compares the result with `verdict.txt`, which O2 recorded, or O1 for the default-file cases of §5.1. A nightly job re-runs the recording oracle on every OpenSSL line and fails if a committed verdict changes, which detects oracle drift.
- **End-to-end tier (nightly, and an M3 exit criterion).** Both cores connect to zk-fakeserver presenting each case that rustls can serve (`on tls a: chain=<case>`). Compared: the handshake outcome, rc, state trajectory and log lines (EXACT, or DEV with a DV-TLS ID). Cases with server keys that rustls cannot sign with run in the unit tier only.

### 5.3 Key and identity format tests

Both cores run each case end to end against zk-fakeserver with `client_auth=require`. The fake server records the SPKI of the presented client certificate. A loaded identity means that the handshake succeeds and the server sees the expected client certificate. A load failure means the legacy log line of the failing step, ZSSLCONNECTIONERROR, errno EINVAL, no teardown, and failover after 2/3·T (X10). The client identity is loaded only when cert, key and passwd are all non-NULL, so every case passes a passwd unless it tests that rule. Keys are generated by `tests/conformance/tls/keys/genkeys.sh` (with `-traditional` on OpenSSL 3 for the traditional forms). DES-CBC and the PBES1 forms are generated with `-provider default -provider legacy`, and the script checks for `Proc-Type: 4,ENCRYPTED`. The over-limit scrypt files and the explicit-keyLength files of TK-17 are built by the script itself from a raw derivation and DER encoding, because the `openssl` CLI refuses those parameters or does not write them. The accepted key set is 06 §3.6.

### 5.6 Native verifiers (`WebPki` and the platform verifier)

These tests run on the native API (`apache-zookeeper` with `tls-ring`):

- the hostname is checked against the connect-string host token, not the resolved IP; IP-literal tokens verify against IP SANs;
- SNI is sent for DNS names and never for IP literals (ClientHello capture);
- only the configured roots are trusted, unless system roots are explicitly requested (DefaultRoots, loaded by the shared `trust.rs`; zero usable roots fail `TlsOptionsBuilder::build`, TI-10);
- `TlsOptionsBuilder::danger_disable_hostname_verification` (04 §16.1) keeps chain verification and logs one WARN per client;
- the handshake deadline is 2/3·T from TCP-connect completion;
- the §5.2 corpus runs in `WebPki` mode with a matching host name. TC-15 must REJECT; the chain verdicts of the other cases must equal webpki's documented behavior;
- a graceful `close` sends one close_notify after the CloseSession exchange and never waits for the peer's; a forced or error teardown and the RW probe send none; a verify failure sends the fatal alert once when no earlier ciphertext is waiting (fake-server capture, as TL-13);
- `add_system_roots()` loads the OpenSSL locations through the shared `trust.rs` loader (TI-02 inputs) and never the OS store;
- with the feature `tls-platform-verifier`, `TlsOptionsBuilder::with_platform_verifier()` decides the chain and the host name through `rustls-platform-verifier` with the client's selected provider: a root installed only in the OS trust store of the test image (the Linux system bundle, the macOS keychain, the Windows certificate store) is trusted, a host-name mismatch fails, and combining it with `ca_file`, `add_system_roots` or `danger_disable_hostname_verification` fails `build()` (04 §16.1). The drop-in never uses it: G2 bans `rustls-platform-verifier` from the zk-ffi closure, and its closure has its own native golden (G1). In the TI-05 (c) setuid and setgid native binaries on Linux, `with_platform_verifier()` makes `build()` fail with `TlsConfigError::PlatformVerifier`, and no `SSL_CERT_FILE`/`SSL_CERT_DIR` read happens (TI-04 preload).

## 8. Rust-side testing

### 8.1 Sans-IO test kit (`zk-testkit`)

The kit drives the zk-proto API by its own names (CC-17 (00 §4)): `Connection<T: Tokens>`; the inputs `begin_interest`/`poll_action`/`finish_interest`, `handle_host_resolved(gen: u64, HostResolution, now)` per host then `handle_resolved(gen: u64, shuffle, now)`, `handle_connect_started`, `handle_tcp_connected`, `handle_transport_ready`, `handle_transport_failed(TransportFailure)` (with `TlsConfig {step, file}`, `TlsResource {at, errno}` and `TlsHandshake {errno}`), `handle_rw_probe(ep: Endpoint, outcome: ProbeOutcome, now)`, `handle_sasl_started`/`handle_sasl_stepped` (each with `gen: u32`), `handle_sasl_addr_failed(gen: u32, which: SaslAddr{Local, Peer}, now)`, `handle_read`, `poll_transmit`/`handle_transmitted`, `submit`, `add_auth`, `begin_close`, `resume`; the query `last_teardown_cause() -> Option<Cause>` (`Cause` is public in zk-proto; the resolver generation of `handle_resolved` is a separate `u64` counter); and the outputs `poll_output` (`Output::{Completion, Watch, Session{barrier}, Auth{barrier}, AuthLockpoint, ClientId, Log, DrainPoint, …}`), the SASL actions `SaslCall {gen: u32, kind: Start | Step(Option<SecretBytes>) | Dispose}`, and `into_leftovers`. The tests depend on these properties of the API:

- every input takes `now: Millis`, so tests generate time from integers;
- `Connection` is constructed as `Connection::new(cfg, compat, mode, rng, log, default_watcher, now)` (02 §4), with `compat` = `Compat::LEGACY_C` or `Compat::NATIVE`, and `mode` one of the two `DriverMode` values of X5 (st `{LegacyExact, Inline}`; mt and native `{Precise, Dispatch}`);
- read-only introspection of state, outstanding xids and the watch tables is available only through zk-proto's `testkit` feature, which zk-ffi never enables (E12).

zk-testkit provides:

| Component | Purpose |
|---|---|
| `TestTokens` | A `Tokens` impl with integer completions and `(fn_id, ctx_id)` watchers |
| `MemTransport` | In-memory duplex for zk-driver tests: max write chunk, scheduled `WouldBlock`, RST at byte n, connect refusal or delay, half-close |
| `TlsPeer` | An in-process rustls server over `MemTransport`: corpus chains, client-auth modes, TLS 1.2-only or 1.3-only, stall after ServerHello, EOF or RST in the handshake, several frames per record and frames split across records, plaintext followed by close_notify or an alert in one record |
| `StaticResolver` | Counts calls; scripted failures |
| `LibcRandomClone` | Pure-Rust glibc `random_r` TYPE_3 and the 48-bit LCG behind `srand48`/`drand48`, implementing the proto `Rng` trait. It reseeds in `on_resolution` (in the drop-in that reseed is the driver's `rng_reseed` leaf instead, X25). zk-xcheck validates it bit-exact against host glibc, and against musl and macOS reference vectors. |
| `ManualClock` | Integer-driven `Millis` source for zk-driver tests |
| `ServerSim` | In-memory server model: znodes with versions and cversion, ephemerals, sequential counters, one-shot, persistent and persistent-recursive watches (addWatch 106, SetWatches 101 and SetWatches2 105, RemoveWatches 18 with types 1-5, CheckWatches 17), container and TTL nodes, the native ops getEphemerals 103, getAllChildrenNumber 104, whoAmI 107 and multiRead 22, atomic multi with error results, sessions, expiry, digest auth, the read-only flag, 36- and 37-byte handshake bodies, SASL DIGEST-MD5 server side. **The same `ServerSim` powers zk-fakeserver.** |
| `Harness` | `Harness::st(Compat::LEGACY_C)` / `Harness::mt(…)` / `Harness::native(…)` select the `DriverMode`; `.servers(3).connect().call(op).run_until_idle().outputs()` |

The fault-injecting transport suite runs `RustlsConn` and the plaintext path over `MemTransport` and `TlsPeer`: EAGAIN at every offset, partial writes, a priority insert while the head is pinned, forced close with a partial head and with unacknowledged TLS bytes (no byte of either reaches the next connection, and a request submitted after the trigger arrives whole), one write per frame (`drv::tls_frame_write`, ledger TLS-03), a stalled handshake, EOF and RST in the handshake (ZSSLCONNECTIONERROR), a `read_tls` buffer-full condition with no progress between two errors (the session latches `Data` and `feed` returns; no busy loop, 06 §3.2), a bad record with `ct_out` not empty and a barrier pending, and the same with a SASL result pending (no alert record reaches the wire, and neither `tls_flush` nor `pump_out` sends it before the teardown, 03 §4.3.5), and a TLS config failure on both paths. Two driver contracts are asserted directly (03 §8.2.1). The plaintext latch: when an error arrives together with plaintext, `TlsConn::read_plaintext` first returns the plaintext already decrypted, and returns the latched failure on the next call (TL-09b, F16). The connect order: on TCP-connect completion the driver calls `TlsConnector::new_conn` first and then `handle_tcp_connected` (a call-order recorder in the test connector checks it).

### 8.2 Scripted fake server (`zk-fakeserver`)

The fake server uses `std::net`, with one thread per listener and per connection. Decisions come only from the script and a seeded RNG. Modes: `model` (ServerSim), `script` (rules override the model), and `proxy` (forwards to a real server and records frames to seed fuzz corpora).

```
listen a 127.0.0.1:0
listen b 127.0.0.1:0
session negotiate_timeout=900
on connect a #1: accept
on request a #3: reset
on connect b #1: accept handshake=legacy36 split_at=36
on request * op=SET_DATA path=/slow: delay 400ms
on request * op=AUTH: reply err=-115
on request * op=MULTI: reply header_only err=-119      # ZNOTREADONLY, for MUL-06
on tls a: chain=TC-14 client_auth=require versions=1.2 stall_after=ServerHello
default: model
```

The control socket (`ZKCONF_CTL`) accepts `HOLD`/`RELEASE`, `DROP`, `EXPIRE`, `NOTIFY CHANGED /x zxid=+5`, `RO on|off`, `ISRO rw|ro`, `WINDOW <bytes>` (limits the receive window, for AUT-02), `WAIT op=… path=…` and `TRANSCRIPT`.

The transcript records every decoded client frame: xid, opcode, path, flags, ACL perms, SetWatches contents and relativeZxid, auth scheme order including duplicates, SASL token lengths, CLOSE, and any frame that fails to parse (for AUT-02 and ST-13). For TLS it also records each ClientHello (SNI, offered versions, session ticket or PSK presence), the handshake outcome, the SPKI of the presented client certificate, and whether a close_notify arrived. TLS uses rustls in server mode, with fixtures from `ssl/gencerts.sh` and `tests/conformance/tls/`.

### 8.3 Model-based and property tests of zk-proto

These tests live in `zk-testkit/tests/` (§2). `zk_testkit::LegacyModel` is written directly from §4.4 and the ledger. It is deliberately naive (vectors and linear scans) and shares no code with zk-proto. Its session-event fan-out order comes from the compiled `hashtable.c` oracle in zk-xcheck, not from zk-proto's port.

`proptest-state-machine` checks `zk-proto` with `Compat::LEGACY_C`, together with ServerSim, against the model under these invariants:

| Id | Invariant |
|---|---|
| I1 | Every accepted token leaves exactly once, through `poll_output` or `into_leftovers`. The contract exceptions are local remove-watches and drops after a close from the IO thread, and even those leave exactly once as a leftover discard. |
| I2 | Per-handle xids are strictly increasing and never take a reserved or negative value (X14) |
| I3 | Replies are matched FIFO; a mismatch tears down with ZRUNTIMEINCONSISTENCY |
| I4 | Teardown order: session event (the unrecoverable state's event whenever the state is negative; CONNECTING only if connected, for a forced close connected at the trigger), then failed completions in submission order, then auth with the teardown rc |
| I5 | Frames are atomic under any write chunking; nothing is inserted in front of a partly written frame |
| I6 | Watch registration follows the checker table |
| I7 | Timer formulas: T·2/3, T/3, T/60, ping suppression |
| I8 | Chunking invariance on input |
| I9 | `LEGACY_C` and `NATIVE` agree on sequences that touch no knob (the knob list comes from `ledger.tsv`) |
| I10 | No input sequence panics |
| I11 | `ForcedClose::Teardown` sets state 999 within the same input call with no callback output and takes the pending work as one snapshot, and the next driving call fails exactly that snapshot with ZCONNECTIONLOSS; none of it is replayed, and a request submitted after the trigger stays queued whole, in any order of submit and IO step, unless a close or a later teardown fails it (X8) |
| I12 | The RW switch fails every completion kind with ZCONNECTIONLOSS (X7) |
| I13 | Every SASL call carries the current generation; a result with an older generation changes nothing; at most one SASL call is outstanding per handle; a dispose is ordered after the outstanding step; `Dispose` is yielded only immediately before a `Start` for a previous session's connection and at the final close after `CloseTransport`, never by a teardown alone (SAS-13) |
| I14 | Under `LEGACY_C`, an auth lockpoint precedes the state change and the completion collection at each of the four legacy sites (X17) |
| I15 | Barrier/resume: while a continuation is suspended, `handle_read`, `poll_action` and `handle_transmitted` are never required; API calls made from the callback are seen by the continuation (an st session callback's `begin_close` gives ZCLOSING, not ZCONNECTIONLOSS) |

Case counts: 512 on PRs and 200k nightly. proptest persists failing seeds in its regression files, which later runs replay.

### 8.4 Three-way codec agreement and legacy-algorithm differentials

1. **Java.** A JUnit test writes 64 seeded instances of every `zookeeper.jute` record. zk-jute decodes them and re-encodes them byte for byte.
2. **C.** zk-xcheck compiles `zookeeper.jute.c` and `recordio.c`. Rust `encode` must equal C `serialize_*`, and each side decodes the other's output. Edge cases: null strings and buffers, empty buffers, negative and `i32::MIN` lengths, maximum lengths. Runs on s390x nightly.
3. **Coverage.** The set of records zk-jute implements equals the set in `zookeeper.jute`.
4. **Generator determinism.** zk-jute's sources are generated by the Java `RustGenerator` (`Rcc -l rust`, Maven execution `generate-Rust-Jute`; 01 §8) into `crates/zk-jute/src/generated/zookeeper_jute.rs`, which is git-ignored and listed in Cargo `include`. CI runs the generator twice and fails if the outputs differ. `zk-jute/build.rs` fails with configure's "jute files are missing!" guidance when the generated file is absent; a test runs the build script in a temporary copy without the file and checks the message.
5. **Legacy algorithms.** zk-xcheck compiles verbatim extracts of `hashtable.c`, `addrvec.c`, `isValidPath`, `prepend_string`, `sub_string`, `getaddrs` and `format_endpoint_info`, and checks the zk-proto ports against them:
   - `LegacyWatchTable` iteration order after random insert, remove and expand sequences, for both C-char signedness settings (X6);
   - cursor sequences for N = 1..6 under `SingleAdvance`, with the double-advance sequence that C's `handle_error` and `zoo_cycle_next_server` produce (two `addrvec_next` calls per failure, after a first pass that selects from `addrs_new`, and `addrvec_atend` for the delay), driven over the compiled `addrvec.c`, asserted as the legacy side of the DV-FIX-1 case;
   - `AddrVec::peek` against the compiled `addrvec_peek`, including the end of the list and an empty list;
   - shuffle with a scripted `random()`;
   - path and chroot functions over all strings of up to 3 bytes, plus fuzzing.

### 8.6 Miri

- **Core crates** (`zk-jute`, `zk-proto`, `zk-testkit`) run with `-Zmiri-strict-provenance -Zmiri-symbolic-alignment-check` on every PR. For forbid(unsafe) crates this mostly validates dependencies such as `zeroize` and finds leaks.
- **zk-driver** runs under Miri without the `tls` feature, because the crypto provider's C and assembly cannot run under Miri. The pure-Rust TLS input modules (`trust.rs`, `pem.rs`, `x509.rs`, `identity.rs`, `legacy_pem.rs`, and the path-building and rule checks of `v1_leaf.rs` with a test `SignatureVerificationAlgorithm` in place of the provider) run under Miri on their own, with the RustCrypto software backends forced where the crates offer a configuration for it. Only tests that reach the crypto provider skip Miri. The TLS session paths are covered by ASan, TSan and F14-F16 instead.
- **zk-ffi production modules** run with **strict provenance**. Production code never casts an integer token back to a pointer (05 §1 rule 2), and Miri enforces that.
- **zk-ffi `abi::raw` result writers** run under Miri with strict provenance, through Miri's libc `malloc`/`calloc`/`free` shims. The tests build every legacy result layout (`String_vector`, `ACL_vector`, `Stat`, the string, data and multi results, `Id`/`ACL` contents), free each one as the C deallocators do, and run the sync copy-out into destinations that the tests allocate, covering the `buffer_len` truncation and the `path_buffer` NUL rules. Miri reports any out-of-bounds write, uninitialized read or leak.
- **zk-ffi fake-host tests.** The C side is played by Rust stand-ins: `extern "C"` functions for the X4 vtable entries, plus buffers from `std::alloc`. Stand-ins that turn a `uintptr_t` token back into a pointer, as the real C shim does, use `ptr::with_exposed_provenance` explicitly. The stand-ins are `#[cfg(test)]` modules in `crates/zk-ffi/src/abi/standin/`. They run as a separate invocation, `cargo miri test -p zk-ffi --lib abi::standin` with `-Zmiri-permissive-provenance`; production modules run in another invocation that filters them out, with strict provenance. The flag never applies to production modules. Both Stacked Borrows and Tree Borrows are run. The stand-ins cover token linearity, outbox view lifetimes, handle reference counting, st close inside a callback inside `zkrs_process`, nested close from a ZCLOSING auth completion, foreign close while another thread waits on a sync record, THREAD item ordering, SASL generation handling (including the recorded stale result of 05 §5), `DISPOSE` placement, the LOG-only outbox of a forced close inside `zkrs_submit` and `zkrs_set_servers`, and the abort on a zeroed host.
- **zk-driver threaded steps** run with `MemTransport` under `-Zmiri-many-seeds=0..32`.

Miri runs in full nightly, and on PRs that touch zk-ffi or zk-driver.

### 8.7 loom

The threaded driver imports its primitives through a `crate::sync` facade, which is `loom::sync` under `cfg(loom)`. loom threads stand in for the C IO and dispatch loops and call the same step functions.

| Model | Property |
|---|---|
| LM-1 | The dispatch queue served by `zkrs_wait_dispatch` drains until `close_requested && io_exited`; nothing enqueued before the drain is lost (ZOOKEEPER-3868 class) |
| LM-2 | Close from the app while the IO thread produces items: each item is delivered once; close returns after the drain; no deadlock |
| LM-3 | Close from a dispatch callback: returns at once; the remaining items are delivered afterwards; destroy happens once, on the dispatch thread |
| LM-4 | Close from an IO-thread callback: later items are discarded without invocation; auth tokens are still delivered |
| LM-5 | Native only: a `Slot<T>` (04 §5.2) racing a concurrent teardown resolves exactly once, and nothing writes after the waiter wakes. The drop-in `zks_sync` record is C and is covered by TSan runs of the sync corpus and the close matrix (CL-09). |
| LM-6 | Waker coalescing: no lost wakeup; a wake never fails |
| LM-7 | Handle reference count: the final close runs exactly once, on the expected role |
| LM-8 | **Token linearity.** For each completion token, the count of delivery plus `discard_token` is exactly 1 across every close variant (foreign, dispatch, IO, st-deferred, forked child). Dropping a token before host release calls `discard_token`; a drop after host release aborts. `zkrs_add_auth` retains its token iff it returns `ZKRS_OK` (X18). |
| LM-9 | THREAD items: for every close role, each library thread is joined or detached exactly once, by the role X22 names, and ZCLOSING auth completions are drained before the join |
| LM-10 | SASL serialization: at most one SASL START or STEP item is in flight per handle, and a DISPOSE produced by close is ordered after the in-flight STEP (I13 at the driver level) |
| LM-11 | Native only: the bounded IO-to-application hand-off (`dispatch_queue_capacity`, X30) with a capacity of 1 and 2. When it is full the IO side stops reading frames and still sends queued requests and pings; no item is lost or delivered twice; a consumer that resumes wakes the IO side; close while the hand-off is full completes without deadlock |

`LOOM_MAX_PREEMPTIONS` is 3 on PRs and 4 nightly. LM-8 also runs as a Miri test over the fake host, with the same counting stand-in.

### 8.8 Maven test profiles

Maven drives the Rust tests the same way it drives the C tests (01 §13.3). The Rust module `zookeeper-client/zookeeper-client-rust` is in its own root-pom profile `rust`, which `-Prust` activates and which also activates whenever the `rust-client` property is defined, because a Rust-core C build needs the staticlib. When the `rust-client` property is defined, the `rust-client-dropin` ordering edge makes the reactor build it before `zookeeper-client-c` (01 §13.1); with `-Pfull-build -Prust` and no `rust-client` property, the C module builds the legacy core and needs no ordering. `-Pfull-build` alone builds no Rust code and never needs cargo, so every CI job that tests Rust passes `-Prust` or `-Drust-client=…` (§14). Every execution runs with `CARGO_TARGET_DIR=${project.build.directory}/cargo` (`zookeeper-client-rust/target/cargo`), `ZK_VERSION_H=${basedir}/../zookeeper-client-c/include/zookeeper_version.h`, `ZK_TLS_DEFAULT_CERT_FILE`/`ZK_TLS_DEFAULT_CERT_DIR` from `abi/tls-probe.sh` (01 §13.2), `base_dir=${basedir}/../..` and `CALLER=ANT`, so all output stays under `target/` and `mvn clean` removes it.

## 14. CI topology

**Maven-driven jobs.** The Maven entry points are those of 01 §13.8; this section owns the topology.

- **Rust activation.** `-Pfull-build` alone builds no Rust code and never needs cargo, and every job that tests Rust passes `-Prust` (the root-pom profile of the Rust module) or `-Drust-client=…`, which activates the same profile (01 §6.5, §13.1).
- **Toolchain pinning.** Every job of `.github/workflows/ci.yaml` that passes `-Prust` or `-Drust-client=…` installs two pinned Rust toolchains, MSRV 1.85 and stable, through a toolchain action pinned by commit SHA, with the components `clippy` and `rustfmt`. The MSRV build proves the 01 §3.9 policy; lint and tests run on stable. Jobs that pass `-Prust-supply-chain`, and the `supply-chain` and `advisories` jobs, also install pinned cargo-deny, cargo-vet and cargo-audit; the `lib-package` job, which packages with `rust-client=side-by-side`, installs pinned cargo-about.
- **Cargo cache.** Every such job caches `~/.cargo/registry` and `target/cargo` (the Maven `CARGO_TARGET_DIR`), keyed on `Cargo.lock` and the toolchain versions.
- **Matrix job `full-build-rust-tests`:** `-Pfull-build,rust,rust-supply-chain verify -Dtest=_ -DfailIfNoTests=false -DskipCppUnit`. It runs the cargo tests only: the `cargo-test` profile (§8.8), then `rust-lint` and, because CI enables it, `rust-supply-chain` at verify. `-Dtest=_ -DfailIfNoTests=false` skips the Java tests, and `-DskipCppUnit` skips the C module's `cppunit` profile.
- **Matrix job `full-build-dropin-cppunit`:** `-Pfull-build -Drust-client=yes verify -Dtest=_ -DfailIfNoTests=false`. Until M3 the job also passes `-Dc-client-openssl=no -Dc-client-sasl=no`, because TLS and SASL are M3 work (§15.3); from M3 it takes the root defaults (`yes`). `-Drust-client=yes` activates the `rust` profile, so the Rust module builds the staticlib. The C module's configure gets the four arguments that 01 §13.7 passes in every configuration, `--with-rust-client=yes`, `--with-rust-staticlib=…/zookeeper-client-rust/target/cargo/capi/libzk_ffi.a`, `--with-rust-tls-provider=${rust-tls-provider}` and `--with-rust-tls=${rust-tls}`, and links the Rust-built staticlib, and its `cppunit` profile runs `make check`: the cppunit public-API suite and the conformance corpus (the differential suite runs in the side-by-side `c-client-rust.yaml` jobs, §4.1, §15.2) against the Rust-backed libraries (§7.1).
- **Test logs.** On failure, CI uploads `target/cargo/TEST-*.txt` together with the cppunit logs.
- **Existing jobs.** The other `full-build-*` jobs define no `rust-client` property until M5 (the root default `no` applies) and pass no `-Prust`, so they build no Rust code, need no cargo and keep their current coverage. From M5 they pass `-Drust-client=yes` (the root property keeps the default `no`, 01 §6.5), except `full-build-cppunit-tests`, which keeps the root default and so keeps building and testing the legacy core with `-Pfull-build` alone, without cargo.
- **Other workflows.** `manual.yaml` and `e2e.yaml` keep their steps; where they test Rust they add `-Prust` and the toolchain install.
- **Jenkins.** `Jenkinsfile` and `Jenkinsfile-PreCommit` need no Rust switch: they build `-Pfull-build` without `-Prust`, so the C module builds the legacy core and these jobs keep their current coverage on agents without cargo. They add `-Prust` once their agents have cargo, and from M5, on agents with cargo, they pass `-Drust-client=yes`. An agent without cargo keeps building `-Pfull-build` on the legacy core. `Jenkinsfile-s390x` passes `-Prust` from M2, on agents with cargo ≥ 1.85 (§13, §15.6); s390x is a Rust tier-2 target.

**Verification jobs.** The workflow `.github/workflows/c-client-rust.yaml` is path-filtered to `zookeeper-client/**`, `zookeeper-jute/**` and `zookeeper-assembly/**`. It builds with `--with-rust-client=side-by-side`, so one job has both cores (§15.2); the `[diff]` tier takes its c core from the reference image (§15.4). Until M3 its configure runs also pass `--with-openssl=no --with-sasl=no`, because TLS and SASL are M3 work (§15.3).

## 15. Rollout

### 15.1 Build selection (one spelling per build system)

- **autotools:** `--with-rust-client=no|yes|side-by-side|auto` (`true` means `yes`), default `no` before M5 and `auto` from M5. `yes` and `side-by-side` are mandatory and stop configure when the host cannot build the Rust core; `auto` builds the Rust core when rustc and cargo ≥ 1.85 and its crates (a vendor directory, the system-crates mode or a successful `cargo fetch`) are available and `ring` supports the target (or a provider other than `ring` is named), and otherwise the legacy core with a notice, unless a Rust-only option was given explicitly, which then stops configure; with `--with-rust-client` not given and the default `no` (before M5), a Rust-only option stops configure and names `--with-rust-client=yes` (01 §6.1; BLD-SEL-01). `--with-rust-tls-provider=ring|aws-lc-rs|aws-lc-rs-fips` selects the crypto provider (default `ring`). `--with-openssl` keeps its name, default (`yes`, which means autodetect) and probe: TLS is built only when `openssl/ssl.h` and `-lssl SSL_CTX_new` are found; otherwise configure warns "cannot build SSL support -- openssl not found" and builds without TLS, as legacy does. The probe only decides the feature (whether `zookeeper_init_ssl` is exported and the zk-ffi features `tls,tls-${provider}` are on); OpenSSL is never linked (DV-TLS-4). The opt-in `--with-rust-tls=yes` enables TLS without OpenSSL headers; it is additive and off by default. `--with-rust-tls-default-paths=FILE:DIR` sets the build default trust locations (default: the OPENSSLDIR recorded at configure time from the `openssl` binary of the installation the legacy probe selected, else the 01 §6.1 platform list; TI-02). `--with-rust-workspace=DIR` names the Rust workspace (default auto: `$srcdir/rust`, then `$srcdir/../zookeeper-client-rust`). `--with-rust-staticlib=PATH` links a staticlib that Maven built, and `--with-rust-target=TRIPLE` passes `--target` to cargo for cross builds. `--with-system-rust-crates[=DIR]` builds offline from distribution crates (G1), and `--with-cargo-vendor=DIR` from a `cargo vendor` directory (G7). `--disable-werror` drops `-Werror`, which is on by default (G-S3). `--enable-debug` adds the handle registry (X29). `--with-sasl` keeps its legacy autodetect: SASL is built only when the Cyrus headers and `-lsasl2 sasl_client_init` are found, and otherwise configure warns "cannot build SASL support -- sasl2 not found" and builds without SASL (configure.ac:176-179). SASL support needs libsasl2-dev, because SASL stays on Cyrus in C. As in legacy, the library CPPFLAGS carry `-DHAVE_OPENSSL_H` when TLS is built (Makefile.am OPENSSL_CPPFLAGS) and `-DHAVE_CYRUS_SASL_H` when SASL is built.
- **CMake:** CMake 3.15 or later for every configuration (DV-BLD-4, 01 §6.3), `-DWITH_RUST_CLIENT=ON|OFF|AUTO` (unset: `OFF` before M5, `AUTO` from M5; the configure rule, 01 §6.3), `-DZK_RUST_TLS_PROVIDER`, `-DWITH_RUST_TLS` (opt-in, off by default), `-DZOOKEEPER_BUILD_SHARED`, `-DZK_RUST_TLS_DEFAULT_PATHS`, `-DZKRS_WORKSPACE=DIR`, `-DZKRS_STATICLIB=PATH`, `-DRust_TARGET=TRIPLE`, `-DZK_SYSTEM_RUST_CRATES=DIR`, `-DZOOKEEPER_CARGO_VENDOR=DIR` and `-DZK_WERROR=ON|OFF` (default ON). A CMake Debug configuration (`CMAKE_BUILD_TYPE=Debug`, or the Debug configuration of a multi-config generator; 01 §4.4) adds the handle registry (X29). `WITH_OPENSSL` keeps its default ON, gated on `OPENSSL_FOUND`. As in legacy (CMakeLists.txt:213, 227), `target_compile_definitions(zookeeper PUBLIC HAVE_OPENSSL_H)` applies when TLS is built and `PUBLIC HAVE_CYRUS_SASL_H` when SASL is built. "TLS is built" means that the legacy autodetect found OpenSSL, or that `--with-rust-tls=yes` / `WITH_RUST_TLS=ON` is given. The shim's own translation units do not depend on `HAVE_OPENSSL_H`. Side-by-side is autotools-only.
- **Maven:** `-Prust` (the root-pom profile of the Rust module; also activated by any `-Drust-client=…`), `-Drust-client=no|yes|side-by-side` (no `auto`: under Maven the Rust module stays opt-in), `-Drust-tls-provider=ring|aws-lc-rs|aws-lc-rs-fips`, `-Drust-tls=no|yes` (root property `rust-tls`, default `no`, which maps to `--with-rust-tls` and to the zk-ffi feature set), `-Drust-system-crates=DIR`, `-Drust-cargo-vendor=DIR` (a `cargo vendor` directory; excludes `rust-system-crates`; the offline crate source of any build, a release build included, 01 §13.4), `-Dcargo.executable`, `-Dcargo.offline`, `-DskipCargoTest`, `-DskipRustLint`; `c-client-openssl` and `c-client-sasl` pass through unchanged. `-Pfull-build` alone builds no Rust code and never needs cargo, and a build with `-Prust` or `-Drust-client=…` needs cargo ≥ 1.85 (DV-BLD-4); `side-by-side` also needs `cargo about` at package (01 §13.5). The Rust module takes the same TLS autodetect decision as configure: `abi/tls-probe.sh` reproduces configure.ac:42-67 for the Maven build and emits the default trust paths (01 §13.7).
- Every build system's outputs go through the same `cargo xtask abi` checks, so the build systems cannot diverge.
- **No runtime switch.** No environment variable selects the core.

### 15.2 Side-by-side install

`side-by-side` installs the legacy core into `$(libdir)`, as a legacy install does, and the Rust core into `$(libdir)/zookeeper-rs/` with the same SONAME (macOS: the same install-name leaf, `libzookeeper_mt.2.dylib`). There is one header tree. An operator opts a process in with `LD_LIBRARY_PATH=$(libdir)/zookeeper-rs` or `DYLD_LIBRARY_PATH`, without relinking. That is exactly the mechanism the conformance runner uses, so field trials run the tested configuration. `make check` in side-by-side mode runs the public tests against both trees; the differential comparisons use the pinned reference build of §4.1 as the c core.

### 15.4 Differential oracle

The differential oracle is the pinned reference build of §4.1: the legacy core at the log-site pin commit, in its four configure variants, with the frozen OpenSSL 3.0 and 3.5 releases for the TLS variants. The legacy core stays in the tree as a supported, buildable configuration, so every EXACT, PER-ROLE and SET comparison and every O1 verdict runs against a live run of that build, for the existing corpus and for every scenario added later. The reference container image holds the variants prebuilt, so the jobs of the `[diff]` tier and O1 run the oracle without rebuilding it. O2 stays available for new TLS cases, because it needs only the `openssl` CLI.

### 15.5 Rollback

SONAME and headers are identical, so rollback means reinstalling with `--with-rust-client=no`, dropping the side-by-side `LD_LIBRARY_PATH`, or, with the convenience lib package from M5, setting the loader path to its `usr/lib/zookeeper-c` (01 §13.5). Nothing ever needs relinking.

## Decisions

| Decision | Rationale | Alternatives |
|---|---|---|
| The document opens with a contract table (X1-X30) that states, for every point that affects a test expectation, the contract that the key decisions (00 §3), the cross-cutting contracts (00 §4) and the owning documents fix, and tests are written only against those contracts. | Each test expectation needs one stated contract. A single table makes each assumed contract explicit and lets the ledger gate enforce it. | Leaving expectations as "per the owning document": CI would either fail or silently accept deviations without a ledger entry. |
| A ledger traceability gate (`cargo xtask ledger check`) covers ledger rows and the register IDs of 00 §5, requires a test per FU/DV row and per register ID, requires a DEV test per DV-FIX row that asserts both behaviors, and checks every `Compat` field against the ledger. 07 P6 rows such as TLS-03 need no test; TLS-05 keeps its RE parity test. | It enforces the requirement to list every deviation mechanically, including the `tls_verify` field and the DV-TLS rows, and keeps the gate's classes equal to the ledger's. | Manual review of DEV tests only; treating the OpenSSL-specific rows as having no counterpart (hides the RE behavior that TLS-05 owns). |
| For TLS, the legacy core in end-to-end handshakes is the primary oracle, `openssl verify` on each reference OpenSSL line (3.0 LTS and 3.5 LTS) is the secondary oracle, and, under the reference default configuration, a Rust ACCEPT against an oracle REJECT is a blocking defect that can never become a DV row (P6). | Legacy uses OpenSSL and this design uses rustls, so the trust engines differ. Under the reference default configuration, the only safe direction for a difference is "rejects more", and only within the registered DV-TLS classes; stricter host policy does not apply to the drop-in (DV-TLS-2). Running both reference lines catches verdicts that depend on the OpenSSL version or security level. OpenSSL 1.1.1 is out of support and is not a reference. | Comparing only against `openssl verify` (it does not apply every libssl client rule), or accepting any difference that a DV row names. |
| The TLS corpus has a committed unit tier with frozen verdicts and injected time, and a nightly end-to-end tier against both cores. The gencerts-derived cases exist in two generator versions (v1 and v3 leaves). | The unit tier is fast, deterministic and survives certificate expiry; the end-to-end tier proves the whole path. The generator version changes the legacy verdict (TC-01a ACCEPT, TC-01b REJECT), so both are gating parity cases. | Only end-to-end tests (slow, time-dependent), only unit tests (misses integration), or one unpinned generator (the verdict then depends on the CI image). |
| Trust-input and key-format expectations follow 06 §3.4-§3.6: three certificate PEM labels with aux trust rules; a CA file that yields at least one certificate or at least one CRL loads, and one that yields neither fails the CaFile step; hash-named directory files only; DefaultVerifyPaths fails only on a resource error; the environment is honored only when `tls_env_allowed` is set; the default locations are compile-time constants; PBKDF2 with HMAC-SHA1, -SHA224, -SHA256, -SHA384 or -SHA512, PBES2 DES-EDE3-CBC and traditional DES-CBC load (DES-CBC is DV-TLS-2, because the reference OpenSSL decrypts single DES only with its legacy provider); client chain files are not checked against the OpenSSL security level (DV-TLS-2); PBES1 fails in both cores under the reference default providers; PKCS#12 PBE and ciphers or PRFs outside the accepted sets are under DV-TLS-5; the passphrase is min(strlen, 1024) bytes; scrypt parameters are bounded at 32 MiB; a same-type key/certificate mismatch fails at ClientKey. | These rules match OpenSSL's verified behavior on the reference lines (`X509_load_cert_crl_file`, `SSL_CTX_set_default_verify_paths`, the by_dir lookup, PBES2 and `PEM_def_callback`), so the tests are EXACT and P6 holds. | Coarser rules (CERTIFICATE blocks only, every file in a directory), which widen or narrow trust relative to legacy. |
| SASL verification adds object-level structural gates (isolation, banned functions, hardening flags, global state, interface) on top of fuzzing, sanitizers, Valgrind, MSan and static analysis. G-S3 checks the exact flag set on the CI reference toolchain and the probed set elsewhere. | The SASL engine stays Cyrus in C (K10). Rules that a person must remember erode; object-level checks catch macros and new includes mechanically. The build probes flags (01 §4.9), so an exact-set check on every toolchain would fail on correct builds. | Enforcement of the 06 §4.7.9 and §4.7.10 rules by code inspection only; an exact-set check everywhere. |
| DAT-13 is tested as FU (TSan, two handles sharing a block while the password file rotates, plus a direct Cyrus user of the block), the in-contract sharing case is tested EXACT, and SU-07/SU-09 assert that no ZooKeeper lock is held while the library password callback runs. | No internal lock is ever held across application code (K2, DSP-13; CC-25 (00 §4)). The library callback writes only a per-session sink, and the process-wide mutex guards only the short in-block copy of the direct Cyrus path, so a handle waiting at a password prompt never delays another handle, and unwinding needs no cleanup handler. | — |
| LA-01 is parity at all four lockpoint sites. `auth_lock` keeps legacy's default attributes, so a same-thread relock is undefined in both cores and has no test. | CC-7 (00 §4): AUTH_LOCKPOINT reproduces legacy's lock-then-process order without an inversion. The mutex is initialized exactly as legacy initializes its auth lock: `pthread_mutex_init(&zh->auth_lock, 0)` (default attributes; legacy `pthread_mutex_init(&zh->auth_h.lock, 0)`, mt_adaptor.c:253), and does not use ERRORCHECK, so legacy behavior is kept exactly. The `zoo_lock_auth`/`zoo_unlock_auth` interposition call counts are not an ABI contract, so AR-06 excludes them. | An IO side that never takes the lock (visible change). |
